## 받고, 조립하기

llama.cpp는 설계도(소스 코드)로 공개되어 있어서, 받아서 이 서버에 맞게 조립(빌드)해야 쓸 수 있습니다. 명령 네 줄이면 됩니다.

<Code title="터미널, 서버">

```sh
$ git clone https://github.com/ggml-org/llama.cpp   # 설계도 받기
$ brew install cmake                                # 조립 도구 설치
$ cd llama.cpp
$ cmake -B build                                    # 이 서버에 맞는 조립 순서 정하기
$ cmake --build build --config Release -j 10        # 일꾼 10명이 동시에 조립
```

</Code>

| 단계 | 걸린 시간 | 결과 |
| --- | --- | --- |
| 설계도 받기 | `26초` | `671 MB`, 오늘 낮에 올라온 최신본 |
| 조립 도구 설치 | `5초` | `cmake 4.4.5` |
| 조립 준비 | `5초` | GPU를 쓰는 Metal이 자동으로 켜짐 |
| 조립 | `1분 4초` | 프로그램 `136개` |

조립 준비 때 `OpenSSL not found` 경고가 하나 나왔는데, llama.cpp가 인터넷에서 모델을 직접 받는 기능만 꺼진다는 뜻이라 그냥 넘어갔습니다. 모델은 1단계에서 이미 받아 두었습니다.

## 첫 질문

<Code title="터미널, 서버">

```sh
$ ./build/bin/llama-cli -m ~/models/Qwen3.8-27B-UD-Q4_K_M.gguf \
    -c 8192 -n 300 -st --reasoning-budget 0 --simple-io \
    -p "안녕? 너는 누구야? 한국어로 두 문장으로 답해 줘."

안녕하세요, 저는 알리바바 그룹에서 개발한 다목적 언어 모델 Qwen입니다.
궁금한 점이 있거나 도움이 필요하시면 언제든 편하게 말씀해 주세요.

[ Prompt: 33.1 t/s | Generation: 6.2 t/s ]
```

</Code>

| 옵션 | 뜻 |
| --- | --- |
| `-m` | 모델 파일 |
| `-c 8192` | 기억할 글 길이, 토큰 수 |
| `-n 300` | 답은 최대 300토큰까지 |
| `-st` | 한 번 묻고 끝냄 |
| `--reasoning-budget 0` | 답하기 전에 속으로 생각하지 않고 바로 답함 |

## 속도 재기

짧은 답 하나로 잰 속도는 대략적이라 `llama-bench`로 다시 쟀습니다. 각각 5번씩 재서 평균을 냅니다. 출력 표에서 몇 칸은 줄여서 옮겼습니다.

<Code title="터미널, 서버">

```sh
$ ./build/bin/llama-bench -m ~/models/Qwen3.8-27B-UD-Q4_K_M.gguf -p 512 -n 128
| model                    |       size |  test |          t/s |
| qwen35 27B Q4_K - Medium |  15.42 GiB | pp512 | 62.04 ± 0.02 |
| qwen35 27B Q4_K - Medium |  15.42 GiB | tg128 |  6.27 ± 0.01 |
```

</Code>

질문을 읽는 속도(`pp512`)는 초당 62토큰, 답을 쓰는 속도(`tg128`)는 초당 6.27토큰입니다. 쓰기가 10배 느린 이유는 두 가지입니다.

- 읽을 때는 토큰 여러 개를 한꺼번에 계산하지만, 쓸 때는 한 토큰을 써야 다음 토큰을 쓸 수 있다.
- 토큰 하나를 쓸 때마다 모델 파일 16.5GB를 메모리에서 한 번 통째로 훑는다.

이 칩이 메모리를 읽는 속도가 초당 약 120GB이니, 이론상 최고 속도는 120 ÷ 16.5 ≈ **초당 7.3토큰**입니다. 실제로 나온 6.27은 그 한계의 85% 정도입니다. 같은 칩에서 더 빨리 답하게 하려면 모델을 더 작게 만드는 수밖에 없습니다.

## 얼마나 긴 글을 기억하나

1단계에서 토큰 하나에 기억 자리가 64KB씩 든다고 계산했습니다. 기억할 글 길이를 바꿔 가며 실제 메모리를 확인했습니다.

<Code title="터미널, 서버">

```sh
$ ./build/bin/llama-cli -m ~/models/Qwen3.8-27B-UD-Q4_K_M.gguf -c 16384 -n 1 -st --simple-io -v -p "hi"
offloaded 66/66 layers to GPU
KV buffer size =  1024.00 MiB
MTL0 (Apple M4) | 18186 = 1054 + (16136 = 14769 + 1173 + 193) + 995
```

</Code>

마지막 줄은 GPU 메모리 18,186MB가 남은 1,054MB와 쓰는 16,136MB(모델 14,769 + 기억 1,173 + 계산 193)로 나뉘었다는 뜻입니다. 대화 기억(`KV`)은 64KB × 16,384 = 1,024MB로 계산과 똑같았습니다.

| 기억할 글 길이 | GPU에 올라간 층 | 남는 메모리 | 결과 |
| --- | --- | --- | --- |
| `16,384` | 66층 전부 | `1,054 MB` | 문제없음 |
| `32,768` | 66층 중 64층 | `1,167 MB` | 2층이 CPU로 밀려나 조금 느려짐 |
| 자동, `31,232` | 66층 전부 | `52 MB` | 끝날 때 GPU 오류 |

옵션을 주지 않으면 엔진이 모델의 26만 토큰을 메모리에 맞게 31,232로 스스로 줄이는데, 엔진이 세지 못한 메모리가 1GB쯤 있어서 GPU 메모리를 거의 다 쓰고 오류가 났습니다. 그래서 앞으로는 **`-c 16384`**로 직접 정해서 씁니다. 설명서의 26만 토큰보다 한참 짧지만, 한국어로 A4 수십 장 분량입니다.

## 생각 모드

이 모델은 답하기 전에 속으로 생각할 수 있습니다. 생각을 막는 옵션을 빼고 간단한 문제를 냈습니다.

<Code title="터미널, 서버">

```sh

    -p "사과가 3개 있었는데 2개를 먹고 5개를 더 샀다. 그중 절반을 친구에게 줬다면 몇 개가 남았나? 답만 짧게."
[Start thinking]
... Compute: 3 - 2 = 1. +5 = 6. half = 3. left = 3. ...
[End thinking]

3개
```

</Code>

정답이고, 25초 걸렸습니다. 한국어로 물었는데 생각은 영어로 하고 답만 한국어로 했습니다. 생각하는 글이 길어질수록 초당 6토큰씩 기다려야 하니, 간단한 대화는 생각을 끄고 어려운 문제에만 켜는 편이 낫겠습니다.

## 인텔 노트북에서 돌리기

노트북에서는 직접 조립하지 않고, llama.cpp가 미리 조립해 올려 둔 윈도우용 **Vulkan** 판을 받았습니다. 서버의 Metal처럼, Vulkan은 인텔 GPU로 계산하게 해 주는 방식입니다. 버전은 서버와 한 단계 차이인 b12340입니다.

<Code title="명령 프롬프트, 노트북">

```sh
> curl.exe -L -o llama-vulkan.zip https://github.com/ggml-org/llama.cpp/releases/download/b12340/llama-b12340-bin-win-vulkan-x64.zip
> tar.exe -xf llama-vulkan.zip -C llama-vulkan
> llama-cli.exe -m ..\models\Qwen3.8-27B-UD-Q4_K_M.gguf -c 4096 -ngl 65 -n 300 -st --reasoning-budget 0 --simple-io -f q1.txt
```

</Code>

윈도우 터미널은 한글을 그대로 넘기면 깨지기 쉬워서, 질문은 UTF-8 파일(`q1.txt`)에 담아 `-f`로 넘겼습니다.

## 노트북에 Qwen을 다 올리면 멈춘다

서버처럼 66층을 전부 GPU에 올리자, 첫 계산에서 `device lost`가 나며 멈췄습니다. 윈도우 시스템 기록에는 GPU가 다시 시작된 흔적이 없었습니다. GPU에 올리는 층 수(`-ngl`)를 줄여 가며 경계를 찾았습니다.

| GPU에 올린 층 | 결과 |
| --- | --- |
| `66` (전부) | 멈춤 |
| `65` | 됨, 마지막 출력층 하나만 CPU에 남음 |
| `60` 이하 | 됨, CPU에 남는 층이 많을수록 느려짐 |

출력층은 약 1,000MB입니다. 66층 전부일 때 GPU가 쓰려던 양은 엔진 기록으로 15,331MB였고, 출력층을 빼면 약 14,340MB입니다.

## 공유 GPU 메모리, 간단한 분석

1단계에서 본 대로 노트북 GPU는 윈도우가 허용한 공유 GPU 메모리 **18,392MB** 안에서 컴퓨터 메모리를 빌려 씁니다. 그런데 실제로는 그보다 3,000MB나 적은 15,331MB에서 멈췄습니다. 측정 결과를 GPU가 쓰려던 양 순서로 모아 보면 이렇습니다.

| 조합 | GPU가 쓰려던 양 | 결과 |
| --- | --- | --- |
| Gemma 26B-A4B 전부, 기억 길이 16,384 | 약 `13,800 MB` | 됨 |
| Qwen 65층, 기억 길이 4,096 | 약 `14,340 MB` | 됨 |
| Qwen 66층 전부, 기억 길이 4,096 | `15,331 MB` | 멈춤 |
| Qwen 65층, 기억 길이 32,768 | 약 `16,130 MB` | 멈춤 |

- 같은 몫을 **윈도우 화면 표시와 화면 공유 프로그램도 빌려 씁니다.** 측정 중 노트북에 켜 둔 화면 공유가 끊긴 일도 있었고, 그 뒤로는 측정할 때 화면 공유를 껐습니다.
- 되고 안 되는 경계가 14,340MB와 15,331MB 사이에 있습니다. 18GB 한도를 다 쓸 수는 없고, 실제로 안정적인 선은 **이름표의 16GB에서 화면 몫을 뺀 15,000MB 근처**로 보입니다. 아직 확인하지 못한 추정이었고, 아래에서 한도를 올려 보니 틀린 것으로 드러났습니다.
- 서버(맥)는 한도 19.07GB에서 1GB를 남기고 안정적으로 돌았습니다. 한도 숫자를 그대로 믿기보다 1~2GB는 여유를 두는 게 맞다는 점은 두 기계가 같았습니다.

## 한도를 24GB로 올려 보니

인텔 그래픽 설정 앱(Intel Graphics Software)의 **그래픽 → 일반 → 공유 GPU/NPU 메모리 재정의**에서 GPU가 빌릴 몫을 정할 수 있습니다. 처음 값은 메모리의 57%인 18GB였습니다. 윈도우 몫으로 8GB는 남기기로 하고 76%인 23.9GB로 올린 뒤 노트북을 다시 켰습니다.

<Code title="명령 프롬프트, 노트북">

```sh
> llama-cli.exe --list-devices
Vulkan0: Intel(R) Arc(TM) 140V GPU (16GB) (24522 MiB, 23754 MiB free)
```

</Code>

한도가 18,392MB에서 24,522MB로 늘었습니다. 이 상태에서 Qwen을 66층 전부 GPU에 올리고, 기억 길이를 늘려 가며 다시 쟀습니다.

| 기억 길이 | GPU가 쓰려던 양 | 결과 | 답 쓰기 (초당 토큰) |
| --- | --- | --- | --- |
| 4,096 | `15,331 MB` | 됨, 예전 한도에서는 멈춤 | |
| 16,384 | `16,111 MB` | 됨 | `4.3` |
| 32,768 | `17,151 MB` | 됨 | `4.3` |
| 65,536 | `19,231 MB` | 됨 | `4.6` |
| 98,304 | `21,311 MB` | 됨, 느려짐 | `2.2` |
| 131,072 | 약 `23,300 MB` (계산) | 5분 넘게 응답 없어 끊음 | |

4,096은 다시 켠 직후 첫 실행이라 백신 검사 같은 일이 겹쳐서 속도를 뺐습니다.

- **예전 추정은 틀렸다.** 이름표의 16GB가 진짜 한계였다면 한도를 올려도 15,331MB에서 멈췄어야 한다. 그런데 됐다. 한계는 공유 GPU 메모리 한도였다.
- **이번에도 한도를 끝까지 쓰지는 못했다.** 98,304부터는 노트북 메모리 32GB가 98%까지 찼다. 윈도우가 모자란 만큼을 디스크(페이지 파일)로 밀어내면서 답 쓰는 속도가 반으로 떨어졌다. GPU 몫은 미리 떼어 두는 칸이 아니라 쓸 때 가져가는 몫이라서, GPU가 많이 쓰면 그만큼 윈도우 몫이 준다.
- 그래서 노트북에서 실제로 쓸 기억 길이는 **65,536**으로 잡는다. 예전 16,384의 4배다.

마지막 1층(출력층)까지 GPU에 올리면 빨라지는지도 `llama-bench`로 쟀습니다. 3번씩 잰 평균입니다.

| 조합 | 질문 읽기 (pp512) | 답 쓰기 (tg128) |
| --- | --- | --- |
| 65층, 출력층은 CPU | `193.37` | `4.22` |
| 66층 전부 | `204.26` | `4.44` |

읽기는 6% 빨라졌습니다. 쓰기는 오전에 65층으로 잰 `4.45`와 같아서, 차이가 없다고 보는 게 맞습니다. 한도를 올려도 메모리를 읽는 속도는 그대로이기 때문입니다. 한도를 올려서 얻은 것은 속도가 아니라 **기억할 수 있는 길이**였습니다.

## 네 가지 조합의 속도

같은 파일, 같은 `llama-bench` 측정입니다. 단위는 초당 토큰입니다.

| 조합 | 질문 읽기 (pp512) | 답 쓰기 (tg128) |
| --- | --- | --- |
| 서버, Qwen 3.8 27B | `62.04` | `6.27` |
| 노트북, Qwen 3.8 27B (65층) | `190.35` | `4.45` |
| 서버, Gemma 4 26B-A4B | `417.06` | `26.41` |
| 노트북, Gemma 4 26B-A4B | `770.81` | `20.62` |

- **모델 구조가 기계보다 큰 차이를 냈다.** 전문가 혼합인 Gemma는 두 기계 모두에서 Qwen보다 답을 4배 넘게 빨리 썼다. 초당 20~26토큰이면 대화하기에 충분하다.
- **노트북은 읽기가 2~3배 빠르고, 쓰기는 서버의 70~78%였다.** Arc GPU의 계산 능력 덕에 한꺼번에 읽는 일은 빠르지만, 한 토큰씩 쓰는 일은 메모리 읽는 속도에 달려 있다.
- **메모리가 빨라도 답이 빨라지지는 않았다.** 노트북 메모리가 숫자로는 더 빠른데(초당 136GB), Qwen에서 실제로는 그 54%만 썼다. 서버는 85%를 썼다.
- 노트북도 기억할 글 길이는 처음에 16,384토큰까지 됐고, 32,768토큰에서는 멈췄다. 공유 메모리 한도를 올린 뒤에는 65,536토큰까지 제 속도로 됐다(위).

## Gemma는 26만 토큰까지

Qwen은 기억 길이를 늘리면 금방 메모리가 찼습니다. 같은 방법으로 Gemma도 두 기계에서 늘려 봤습니다. 노트북은 한도를 24GB로 올린 상태입니다.

| 기억 길이 | 서버, 한도 18,185MB | 노트북, 한도 24,522MB |
| --- | --- | --- |
| 32,768 | `14,156 MB` 됨 | `14,025 MB` 됨 |
| 65,536 | `14,956 MB` 됨 | `14,697 MB` 됨 |
| 131,072 | `16,556 MB` 됨 | `16,041 MB` 됨 |
| 262,144 | `19,756 MB` 멈춤 | `18,729 MB` 됨 |

262,144는 이 모델이 받을 수 있는 최대 길이입니다. 노트북은 모델의 최대치를 그대로 쓸 수 있었고, 서버는 한 칸 아래인 131,072까지였습니다. 서버도 한도를 올린 뒤에는 262,144가 됐습니다(아래). 이때도 답 쓰는 속도는 서버가 초당 24토큰, 노트북이 19토큰으로 짧을 때와 거의 같았습니다.

- **기억할 자리를 Qwen의 3분의 1만 쓴다.** 엔진 기록을 보면 Gemma의 기억할 자리는 두 칸으로 나뉩니다. 글 길이에 따라 커지는 칸은 토큰마다 약 20KB이고(Qwen은 64KB), 나머지 한 칸은 길이와 상관없이 300MB로 고정입니다. 일부 층만 글 전체를 기억하고, 나머지 층은 최근 일부만 기억하는 구조라서 그렇습니다.
- **같은 일을 해도 계산 공간은 서버가 더 컸다.** 262,144에서 계산 공간이 서버(Metal)는 1,384MB, 노트북(Vulkan)은 357MB였다. 서버가 멈춘 데에는 이 차이도 한몫했다.
- 긴 문서를 통째로 넣을 일이 있다면 Gemma가 맞다. 빠르고, 길게 기억한다.

## 서버도 한도를 올려 보니

macOS에도 GPU가 쓸 수 있는 몫을 정하는 설정이 있습니다. 서버는 다른 프로그램을 거의 돌리지 않는 전용 기계라서, macOS 몫을 2GB만 남기고 22GB로 올렸습니다. 관리자 암호가 필요해서 이 명령은 제가 직접 쳤습니다. 다시 켜면 원래 값으로 돌아갑니다.

<Code title="터미널, 서버">

```sh
$ sudo sysctl iogpu.wired_limit_mb=22528
iogpu.wired_limit_mb: 0 -> 22528
$ ./build/bin/llama-cli --list-devices
  MTL0: Apple M4 (22528 MiB, 22527 MiB free)
```

</Code>

한도가 18,185MB에서 22,528MB로 늘었습니다. Gemma 262,144는 19,757MB로 됐고, 답 쓰는 속도도 초당 24.9토큰으로 그대로였습니다. Qwen은 기억 길이를 늘려 가며 다시 쟀습니다.

| 기억 길이 | GPU가 쓰려던 양 | 결과 | 답 쓰기 (초당 토큰) |
| --- | --- | --- | --- |
| 16,384 | `16,137 MB` | 됨 | `6.1` |
| 32,768 | `17,241 MB` | 됨, 예전 한도에서는 멈춤 | `6.3` |
| 49,152 | `18,345 MB` | 됨 | `5.7` |
| 65,536 | `19,449 MB` | 됨 | `6.2` |
| 81,920 | `20,553 MB` | 됨 | `6.1` |
| 98,304 | `21,657 MB` | 멈춤, GPU 오류 | |

- **서버도 기억 길이가 16,384에서 81,920으로 5배가 됐다.** 노트북(65,536)보다 조금 더 길다.
- **두 기계는 한도 앞에서 다르게 행동했다.** 노트북(윈도우)은 메모리가 모자라도 디스크로 밀어내며 느리게나마 돌았다. 서버(macOS)는 한도를 넘는 순간 GPU 오류로 멈췄다. 대신 한도 안에서는 길이를 늘려도 속도가 끝까지 초당 6토큰이었다.
- 98,304가 멈춘 것은 앞에서 본 「엔진이 세지 못하는 1GB」 때문으로 보인다. 21,657MB에 1GB를 더하면 한도 22,528MB를 넘는다.

## 배운 것

- 답 쓰는 속도는 모델 크기와 칩이 메모리를 읽는 속도가 정한다. 16.5GB 모델이면 이 서버에서 초당 6토큰 남짓이다.
- 기억할 글 길이는 직접 정한다. 엔진에 맡겼더니 GPU 메모리를 다 쓰고 오류가 났다.
- 생각 모드는 정확하지만 그만큼 기다린다.
- 전문가 혼합 모델은 비슷한 크기에서 4배 빠르다. 실제로 쓸 모델은 이쪽이 유력하다.
- 내장 GPU의 메모리 한도는 다 쓸 수 없다. 화면 몫과 여유를 남겨야 한다.
- GPU가 빌릴 몫은 두 기계 모두 올릴 수 있다. 윈도우는 인텔 설정 앱에서, macOS는 `sysctl`로 올린다. 더 긴 글을 기억하게 되지만 빨라지지는 않는다.
- 한도를 넘으면 윈도우는 디스크로 밀어내며 느려지고, macOS는 그 자리에서 멈춘다.
