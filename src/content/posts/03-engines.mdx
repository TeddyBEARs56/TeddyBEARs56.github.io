## 이번에 할 일

1. **견줄 엔진을 정하고, 재는 방법은 2단계와 똑같이 둔다.** 엔진 말고는 바뀌는 게 없어야 차이를 엔진 탓으로 볼 수 있다.
2. **서버에서 MLX와 llama.cpp를 견준다.** 애플 칩에서는 애플이 만든 엔진이 더 빠를지 본다.
3. **노트북에서 SYCL·OpenVINO·CPU판을 Vulkan판과 견준다.** 인텔 칩에서도 칩 회사 쪽 엔진이 더 빠를지 본다.
4. **작은 모델로 NPU까지 돌린다.** NPU는 정해진 압축 방식과 검증된 작은 모델만 돌린다.
5. **기계마다 쓸 엔진을 하나씩 고른다.** 4단계에서 모델을 서버로 띄울 때 쓸 엔진이다.

## 엔진만 바꿔 끼운다

2단계에서 모델 파일은 악보, 엔진은 연주자에 비유했습니다. 엔진은 모델 파일을 읽어 실제로 답을 만드는 프로그램입니다. 이번에는 악보는 그대로 두고 연주자만 바꿉니다.

측정 방법은 2단계와 같습니다. 질문 512토큰을 읽는 속도와 답 128토큰을 쓰는 속도를 잽니다. 토큰은 모델이 글을 잘게 나눠 다루는 조각입니다. 3번씩 재서 평균을 내고, 단위는 초당 토큰입니다.

| 기계 | 지금까지 쓴 엔진 | 견준 엔진 |
| --- | --- | --- |
| 서버 | llama.cpp + Metal | **MLX**, 애플이 만든 엔진 |
| 노트북 | llama.cpp + Vulkan | **SYCL**, **OpenVINO**, 인텔 쪽 방식 / CPU만 |

Metal과 Vulkan은 GPU에게 일을 시키는 범용 통로입니다. MLX·SYCL·OpenVINO는 칩 회사가 자기 칩에 맞춰 만든 전용 길입니다. 전용 길이 더 빠를 거라고 예상했습니다.

## 서버: 애플의 MLX

MLX는 모델 파일 형식이 달라서, llama.cpp가 쓰는 GGUF 파일을 그대로 쓸 수 없습니다. 그래서 같은 모델을 4비트 MLX 형식으로 다시 받았습니다. 받는 데 Qwen은 7분 21초, Gemma는 8분 18초 걸렸습니다.

<Code title="터미널, 서버" wrap>

```sh
$ uv tool install --python 3.12 mlx-lm
$ uv tool install --python 3.12 huggingface_hub
$ hf download mlx-community/Qwen3.8-27B-4bit --local-dir ~/models/mlx/Qwen3.8-27B-4bit
$ hf download mlx-community/gemma-4-26b-a4b-it-4bit --local-dir ~/models/mlx/gemma-4-26b-a4b-it-4bit
$ mlx_lm.benchmark --model ~/models/mlx/gemma-4-26b-a4b-it-4bit -p 512 -g 128 -n 3
Averages: prompt_tps=427.671, generation_tps=40.459, peak_memory=14.753
```

</Code>

| 파일 | llama.cpp용 GGUF | MLX용 |
| --- | --- | --- |
| Qwen 3.8 27B | `16.56 GB` (Q4_K_M) | `16.07 GB` (4bit) |
| Gemma 4 26B-A4B | `13.60 GB` (IQ4_XS) | `15.37 GB` (4bit) |

같은 날 같은 서버에서 두 엔진을 차례로 쟀습니다.

| 조합 | 질문 읽기 (pp512) | 답 쓰기 (tg128) | 쓴 메모리 |
| --- | --- | --- | --- |
| Qwen, llama.cpp | `61.13` | `6.29` | |
| Qwen, **MLX** | `65.37` | `6.91` | `16.27 GB` |
| Gemma, llama.cpp | `415.09` | `27.03` | |
| Gemma, **MLX** | `427.67` | `40.46` | `14.75 GB` |

- **Gemma는 답 쓰기가 50% 빨라졌다.** 초당 27토큰에서 40토큰이 됐다. 16:28에 한 번 더 재도 `40.36`으로 같았다. MLX 파일이 1.8GB 더 큰데도 더 빨랐다.
- **Qwen은 10% 빨라졌다.** 1단계에서는 메모리 읽는 속도를 토큰마다 읽는 양으로 나눠 최고 속도를 계산했다. 그 계산으로 보면, 메모리가 초당 읽는 120GB 중 llama.cpp는 87%, MLX는 92%를 썼다. 이미 천장에 가까워서 더 올라갈 자리가 적었다.
- 질문 읽기는 두 모델 모두 3~7%만 빨라졌다. 차이는 답을 한 토큰씩 쓸 때 났다.
- Gemma는 한 토큰을 쓸 때 모델의 일부만 꺼내 쓰는 전문가 혼합 모델이다. 이런 모델에서 차이가 크게 난 이유까지는 확인하지 못했다.

## 노트북: 인텔 쪽 엔진 세 가지

노트북은 서버와 달리 모델 파일을 다시 받을 필요가 없었습니다. llama.cpp는 같은 버전을 엔진별로 따로 조립해 올려 둡니다. 그래서 2단계에서 쓴 Vulkan판과 같은 b12340 버전으로 엔진 세 가지만 더 받았습니다.

<Code title="명령 프롬프트, 노트북" wrap>

```sh
> curl.exe -L -o llama-sycl.zip https://github.com/ggml-org/llama.cpp/releases/download/b12340/llama-b12340-bin-win-sycl-x64.zip
> curl.exe -L -o llama-openvino.zip https://github.com/ggml-org/llama.cpp/releases/download/b12340/llama-b12340-bin-win-openvino-2026.4.1-x64.zip
> curl.exe -L -o llama-cpu.zip https://github.com/ggml-org/llama.cpp/releases/download/b12340/llama-b12340-bin-win-cpu-x64.zip
```

</Code>

| 엔진 | 무엇인가 | 노트북에서 잡힌 장치 |
| --- | --- | --- |
| SYCL | 인텔 GPU 전용 통로 | Arc 140V |
| OpenVINO | 인텔이 만든 AI 엔진 | CPU, Arc 140V, **NPU** 셋 중 고름 |
| CPU | GPU 없이 CPU만 | Core Ultra 7 258V, 8코어 |

<Code title="OpenVINO판이 찾은 장치">

```sh
> llama-cli.exe --list-devices
  OPENVINO0: GGML_OPENVINO_DEVICE=CPU (selected) - Intel(R) Core(TM) Ultra 7 258V (32266 MiB, 24171 MiB free)
  OPENVINO1: GGML_OPENVINO_DEVICE=GPU - Intel(R) Arc(TM) 140V GPU (16GB) (iGPU) (22601 MiB, 22601 MiB free)
  OPENVINO2: GGML_OPENVINO_DEVICE=NPU - Intel(R) AI Boost (NPU 4000) (16384 MiB, 16384 MiB free)
```

</Code>

같은 모델 파일로 엔진만 바꿔 쟀습니다. 공유 GPU 메모리 한도는 2단계에서 올려 둔 24GB 그대로입니다.

| 엔진 | Qwen 읽기 | Qwen 쓰기 | Gemma 읽기 | Gemma 쓰기 |
| --- | --- | --- | --- | --- |
| **Vulkan** | `204.26` | `4.44` | `769.09` | `20.43` |
| SYCL | `54.41` | `3.63` | `154.45` | `12.71` |
| CPU만 | `15.37` | `3.44` | `63.89` | `13.21` |
| OpenVINO GPU | 멈춤 | | 지원 안 됨 | |

- **인텔 전용 통로인 SYCL이 오히려 느렸다.** 읽기는 3~5배, 쓰기는 18~38% 느렸다. Gemma 쓰기는 CPU만 쓸 때보다도 느렸다. 아래 작은 모델에서는 쓰기 속도가 Vulkan과 같았다. 이번 두 모델은 구조가 새로워서, SYCL 쪽 최적화가 아직 따라오지 못한 것으로 보인다.
- **CPU만 써도 답 쓰기는 GPU의 77%였다.** 읽기는 GPU가 13배 빨랐다. 쓰는 속도는 메모리를 읽는 속도가 정한다는 2단계의 결론 그대로다. CPU와 GPU가 같은 메모리를 나눠 쓰니, 쓰는 속도도 비슷해진다.
- **OpenVINO는 두 모델을 아직 돌리지 못했다.** Qwen은 계산 중에 프로그램이 죽었다. Gemma는 처리하지 못하는 계산이 있다는 오류가 났다. OpenVINO판 설명서의 검증 목록에도 두 모델은 없다.

## 작은 모델로 NPU까지

NPU는 AI 계산만 하는 작은 칩입니다. llama.cpp에서는 OpenVINO판으로만 쓸 수 있습니다. 앞에서 큰 모델 둘을 돌리지 못한 바로 그 엔진입니다. 설명서에 따르면 정해진 압축 방식(주로 Q4_0)과 검증된 작은 모델만 돌아갑니다. 처음에는 Gemma로 해 봤지만, Gemma 파일의 압축 방식인 IQ4_XS를 처리하지 못했습니다. 그래서 검증 목록에 있는 **Qwen3 4B**를 받았습니다. Q4_K_M으로 압축한 2.50GB 파일입니다. 이 모델을 여섯 가지 엔진으로 모두 쟀습니다.

<Code title="명령 프롬프트, 노트북">

```sh
> set GGML_OPENVINO_DEVICE=NPU
> llama-bench.exe -m ..\models\Qwen3-4B-Q4_K_M.gguf -ngl 99 -fa 1 -p 512 -n 128 -r 3
```

</Code>

| 엔진 | 질문 읽기 (pp512) | 답 쓰기 (tg128) |
| --- | --- | --- |
| Vulkan | `1,363.68` | **`33.53`** |
| SYCL | `398.37` | **`34.12`** |
| OpenVINO GPU | **`1,897.11`** | `21.02` |
| OpenVINO **NPU** | `323.51` | `11.99` |
| CPU만 | `103.19` | `20.51` |
| OpenVINO CPU | `88.65` | `9.47` |

- **NPU로 LLM이 돌았다.** 읽기는 CPU의 3배였지만, 쓰기는 CPU보다도 느렸다. NPU의 장점은 빠르기보다 전기를 적게 쓰는 데 있다. 이번에는 전력을 재지 못했다.
- **OpenVINO GPU는 읽기가 가장 빨랐다.** Vulkan보다 39% 빨랐다. 대신 쓰기는 Vulkan의 63%였다.
- 이 모델로 낼 수 있는 이론상 최고 쓰기 속도는 초당 약 55토큰이다. Vulkan과 SYCL이 그 61%까지 냈다.

<Note title="참고">
OpenVINO판으로 잴 때는 `-fa 1`(flash attention) 옵션을 꼭 붙여야 합니다. 설명서에도 그렇게 적혀 있습니다. 처음에는 이 옵션 없이 재서, 다시 재야 했습니다.
</Note>

## 배운 것

- 같은 모델 파일도 엔진에 따라 답 쓰는 속도가 50%까지 달라진다.
- 칩 회사의 엔진이 늘 빠른 건 아니다. 애플의 MLX는 빨랐고, 인텔의 SYCL은 새 모델 구조에서 느렸다.
- 답 쓰는 속도는 엔진보다 메모리가 먼저 정한다. CPU만 써도 GPU의 77%가 나왔다.
- NPU는 작은 모델을 느리게 돌린다. 쓸모는 속도가 아니라 전기 쪽에 있다.
- 새 엔진은 지원하는 모델 목록부터 확인한다. OpenVINO는 이번 두 모델을 아직 돌리지 못했다.

## 다음 단계로

기계마다 쓸 엔진은 정했지만, 모델은 아직 그 기계 안에서만 돌아 다른 기계에서는 쓸 수 없습니다. 그래서 4단계에서는 서버에서 MLX로 모델을 띄워, 다른 기계에서도 질문을 보낼 수 있게 합니다. MLX에도 llama.cpp처럼 질문을 받는 서버 기능 `mlx_lm.server`가 있습니다.
