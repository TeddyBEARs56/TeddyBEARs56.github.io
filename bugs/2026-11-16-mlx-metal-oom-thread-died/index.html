웹 UI를 붙이자 MLX 서버가 GPU 메모리 부족으로 멈추고, 다시 뜨지도 않는다

24GB Mac mini에서 27B 모델을 돌리던 MLX 서버에 웹 UI를 붙이자 1분 만에 「generation thread died」로 멈췄습니다. 프로그램은 살아 있어서 자동 재시작도 되지 않았습니다.

상태
우회
대상
mlx_lm.server 0.32.2
환경
macOS 27.0, Apple M4 24GB, mlx-lm 0.32.2, Open WebUI 0.13.3, Python 3.12
올린 날
2026-11-16
고친 날
2026-11-18
읽는 시간
약 3분

증상

Mac mini에서 늘 켜 둔 mlx_lm.server 앞에 웹 UI인 Open WebUI를 붙였습니다. 첫 질문을 보낸 지 1분 만에 화면에 「generation thread died」가 나왔고, 그 뒤로는 어떤 질문에도 답이 오지 않았습니다. 서버 기록에는 이렇게 남았습니다.

모델 목록 요청(/v1/models)에는 계속 정상으로 답했습니다. 겉으로는 살아 있는 서버가 질문에만 실패한 것입니다.

재현 순서

같은 조건에서 두 번 일어났습니다.

  1. 24GB Mac에서 sysctl iogpu.wired_limit_mb=22528로 GPU 몫을 22GB로 올리고, 4비트 27B 모델(약 15GB)로 mlx_lm.server를 기본 설정으로 띄운다.
  2. 같은 Mac에 Open WebUI를 설치해 이 서버를 모델로 연결한다.
  3. 웹 UI에서 질문한다. 웹 UI는 답과 대화 제목을 동시에 요청한다.
  4. 몇 번 오가다 보면 프롬프트를 읽는 도중 위 오류로 멈춘다.

원인

확인한 것

  • 오류는 프롬프트 여러 개를 한꺼번에 읽는 단계(BatchGenerator)에서 Metal 메모리를 더 받지 못해 났습니다.
  • mlx_lm.server는 지난 질문을 다시 읽지 않으려고 프롬프트 캐시에 기억해 둡니다. 기본값에는 크기 한도가 없습니다.
  • Open WebUI는 macOS에서 PyTorch의 MPS(Metal)를 찾으면 문서 검색용 모델을 GPU에 올립니다(open_webui/env.py). 같은 GPU 메모리를 MLX와 나눠 쓰게 됩니다.
  • 답을 만드는 스레드만 죽고 프로세스는 살아 있었습니다. 그래서 launchd의 KeepAlive가 다시 띄우지 않았습니다.

추정한 것

  • 세 가지가 각각 얼마를 차지했는지는 나눠 재지 않았습니다. 화면을 찍으려고 띄운 시험용 Open WebUI가 한 벌 더 있었던 것도 보탰을 것입니다.

해결

설정으로 피해 갔습니다. 처음에는 MLX 쪽만 고쳤는데(캐시 2GB, 질문은 한 번에 하나씩 읽기) 5분 뒤 다시 멈췄습니다. 두 번째에 아래처럼 고친 뒤로는 멈추지 않았습니다.

고친 곳 설정
Open WebUI가 GPU를 쓰지 않게 환경 변수 USE_SLIM_DOCKER=true (macOS에서 MPS를 찾는 단계를 건너뛴다)
프롬프트 캐시 한도 --prompt-cache-bytes 1073741824 (1GB)
한 번에 읽는 질문 --prompt-concurrency 1
한 번에 쓰는 답 --decode-concurrency 2

고친 뒤 긴 질문(2,423토큰)과 짧은 질문을 동시에 보내 둘 다 답을 받았습니다. 대신 짧은 질문은 긴 질문이 다 읽힐 때까지 기다려 39.8초가 걸렸습니다.

11월 18일에 더 알게 된 것

처음에는 캐시 한도를 1GB로 걸었는데도 기록에 「Prompt Cache: 6 sequences, 2.38 GB」가 찍혀, 한도가 언제 적용되는지 몰랐습니다. 이틀 뒤 코딩 에이전트 시험에서 같은 오류로 여섯 번 더 멈췄습니다. 이번에는 웹 UI가 아니라 긴 대화가 원인이었습니다.

mlx-lm 0.32.2의 코드를 읽어 보니 두 가지가 있었습니다.

  • 캐시 한도는 저장할 때 적용되지 않는다. --prompt-cache-bytes는 여러 요청을 묶어 처리하는 경로에서 새 요청을 받을 때만 저장된 캐시를 줄인다. 시험 동안 기록된 캐시 크기 979번 가운데 744번이 1GB를 넘었고, 가장 클 때 4.62GB였다.
  • 같은 대화를 이어 갈 때는 대화 기억 전체를 새 자리로 옮겨 쓴다. 여러 요청을 묶어 처리하는 자리로 옮기거나 자리를 늘릴 때 새로 쓰므로, 대화가 길면 그 순간 같은 기억이 잠깐 두 벌이 된다. 꺼낼 때 부르는 copy.deepcopy 자체는 메모리를 새로 잡지 않는다.

그래서 1GB 한도는 긴 대화에는 우회가 되지 못합니다. 시험에서는 과제를 시작할 때마다 한 토큰을 먼저 요청해 보고, 답이 없으면 서버를 다시 띄우게 했습니다. 늘 켜 둔 서버에는 이런 감시가 아직 없어서 상태는 「우회」로 둡니다. 자세한 내용은 로컬 모델에게 코딩 맡기기 3편에 적었습니다.
