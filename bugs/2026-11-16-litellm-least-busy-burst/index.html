LiteLLM의 least-busy 라우팅이 한꺼번에 온 요청을 목록의 첫 서버로 몰아 보낸다

두 서버로 나눠 보내라고 했는데, 한꺼번에 보낸 요청 4개 중 3개가 느린 쪽으로 갔습니다. 수가 같으면 목록의 첫 서버를 고르기 때문이었습니다.

상태
우회
대상
LiteLLM 1.106.6 라우터 (least-busy)
환경
LiteLLM 1.106.6 (macOS 27.0), 모델 서버 둘 — Apple M4의 mlx_lm.server와 Windows 노트북의 llama.cpp 서버
올린 날
2026-11-16
읽는 시간
약 2분

증상

빠르기가 다른 모델 서버 둘을 LiteLLM의 한 이름으로 묶고, 처리 중인 요청이 적은 쪽으로 보내게(least-busy) 했습니다. 서로 다른 긴 질문 4개를 한꺼번에 보내자 3개가 느린 서버로, 1개만 빠른 서버로 갔습니다.

보낸 곳 나뉜 결과 4개가 모두 끝날 때까지
느린 서버만 4개 99.0초
빠른 서버만 4개 41.3초
한 이름으로 묶음, 느린 서버를 먼저 적음 느린 쪽 3개, 빠른 쪽 1개 84.5초
한 이름으로 묶음, 빠른 서버를 먼저 적음 2개씩 48.5초

재현 순서

  1. 같은 model_name으로 서버 둘을 적고 least-busy를 고른다.
  1. 스레드 4개로 auto에 같은 순간 요청을 보낸다. 답이 몇 초 걸리는 긴 질문이어야 한다.
  2. 응답 헤더 x-litellm-model-api-base로 어느 서버가 답했는지 본다. 첫 서버로 쏠린다.

원인

확인한 것

  • 서버를 고르는 함수는 처리 중인 요청 수가 가장 적은 서버를 고르고, 수가 같으면 목록의 첫 서버를 고른다(1.106.6의 litellm/router_strategy/least_busy.py).
  • 그 수는 서버를 고른 뒤, 요청을 실제로 보내기 직전(log_pre_api_call)에 늘어난다.
  • 이 방식은 서버가 얼마나 빠른지는 보지 않는다.

추정한 것

  • 한꺼번에 온 요청은 앞선 요청의 수가 늘기 전에 서버를 골라서 같은 수로 보고, 첫 서버로 쏠린 것으로 본다. 다시 해 보니 빠른 서버를 먼저 적었을 때 2개씩 나뉘었다. 늘 같은 비율로 쏠리지는 않는다.

해결

빠른 서버를 목록 앞에 적었습니다. 수가 같으면 빠른 쪽으로 가니, 한꺼번에 오는 요청도 한가할 때 오는 요청도 빠른 서버가 먼저 받습니다. 4개가 모두 끝나는 시간이 84.5초에서 48.5초가 됐습니다. 빠른 서버 하나에 다 보낸 41.3초보다는 여전히 느립니다. 빠르기를 따지려면 latency-based-routing 같은 다른 방식을 봐야 하는데, 이번에는 시험하지 않았습니다.

빠른 서버가 꺼져 있을 때

빠른 쪽은 잠들 수 있는 노트북이었습니다. 그런데 LiteLLM은 연결이 안 되는 오류(APIConnectionError)가 나도 그 서버를 잠시 쉬게 하지 않습니다(litellm/router_utils/cooldown_handlers.py). 앞에 적은 서버가 꺼지면 요청이 계속 그쪽으로 갈 수 있습니다. 그래서 세 가지를 더했습니다.

  • background_health_checks와 health_check_interval: 60: 노트북만 1분마다 확인한다. 늘 켜진 쪽은 disable_background_health_check: true로 뺐다.
  • enable_health_check_routing: true: 확인에서 떨어진 서버로는 보내지 않는다.
  • fallbacks: 그래도 실패하면 늘 켜진 서버의 이름으로 넘긴다.

연결을 거절하는 가짜 서버를 앞에 적어 시험했습니다. 3번 모두 뒤의 서버가 답했고, 넘기기만 걸어 둔 이름은 0.9초 만에 다른 서버가 대신 답했습니다.
