모델 일곱 개에게 맡겨 보기

10단계까지 Mac mini와 노트북에 로컬 LLM 서버를 세웠습니다. 11단계부터는 그 모델에게 코딩을 맡깁니다. Claude Code는 파일을 찾아 읽고, 고치고, 명령을 실행해 확인까지 하는 코딩 에이전트입니다. 여기서 모델만 로컬 모델로 바꿔, 이 블로그의 코드로 만든 과제 세 개를 풀게 했습니다.

올린 날
2026-11-18
읽는 시간
약 12분

이번에 할 일

  1. 과제를 만든다. 이 블로그의 코드로 찾기, 고치기, 더하기 세 가지를 만든다. 맞았는지는 시험 프로그램이 가린다.
  2. 모델을 고른다. Mac mini의 GPU 메모리에 들어가는 모델 일곱 개를 고르고, 그중 넷은 노트북에서도 돌린다.
  3. 여러 번 돌린다. 같은 과제를 Mac mini에서 두 번, 노트북에서 세 번 돌린다. 매번 새 사본에서 시작한다.
  4. 실패를 읽는다. 대화 기록을 열어 어디서 틀렸는지 본다.

과제 세 개

과제마다 이 블로그의 원본을 새로 복사해 주었습니다. 11월 17일의 원본이라 연재 글 11편과 Cybug 버그 기록 8개가 들어 있습니다. 고치기 과제를 위해 한 곳은 일부러 틀리게 해 두었습니다. Cybug 목록 페이지가 상태별 건수를 셀 때 b.data.status를 읽어야 하는데 b.status를 읽게 바꿨습니다. 그러면 건수가 모두 0이 됩니다.

Claude Code에게는 아래 말을 그대로 보냈습니다.

  • 찾기: 「이 블로그에서 글을 읽는 데 걸리는 시간(읽기 시간)은 어느 파일에서 어떻게 계산하나요? 파일 경로와 계산 방식을 알려 주세요. 파일은 고치지 마세요.」
  • 고치기: 「Cybug 목록 페이지(/bugs/) 위쪽의 상태 설명에 건수가 모두 0건으로 나옵니다. 실제 상태별 건수가 나오도록 원인을 찾아 고쳐 주세요. 고친 뒤 npm run build로 확인해 주세요.」
  • 더하기: 「RSS 피드(/rss.xml)에는 지금 연재 글만 들어갑니다. Cybug 버그 기록도 함께 넣어 주세요. 글과 버그 기록을 날짜가 최신인 것부터 섞어서 넣어 주세요. 고친 뒤 npm run build로 확인해 주세요.」
과제 맞았다고 본 것
찾기 답에 posts.ts, 500, 220이 모두 나오고, 바뀐 파일이 없다
고치기 다시 빌드한 목록 페이지에 상태별로 0건, 6건, 2건이 나온다
더하기 다시 빌드한 피드에 글 11편과 버그 기록 8개의 주소가 모두 있고, 최신순이며, 날짜가 RSS 형식이다

읽기 시간은 src/lib/posts.ts에서 한글은 1분에 500자, 영어는 1분에 220단어로 계산합니다. 고치기와 더하기는 에이전트가 무엇이라고 답하든, 시험 프로그램이 사본을 처음부터 다시 빌드해서 확인했습니다. 「빌드가 성공했다」고 답해도 결과물이 틀리면 실패입니다.

어떻게 돌렸나

Claude Code는 원래 Anthropic의 Claude와 이야기합니다. 보낼 주소를 9단계에서 세운 게이트웨이로 바꾸면, 게이트웨이가 요청을 로컬 모델 서버가 알아듣는 형식으로 바꿔 전해 줍니다. 자세한 설정은 12단계에 씁니다.

Claude Code는 늘 Mac mini에서 돌았고, 노트북 차례에는 모델만 노트북에서 돌았습니다. 결과에 넣은 시도는 두 기계가 겹치지 않게 차례로 돌렸습니다. 다만 노트북 1회차는 Mac mini가 결과에서 뺀 시도를 돌리던 때와 겹쳤습니다. Claude Code와 빌드는 Mac mini에서 돌기 때문에, 노트북 1회차는 조금 느려졌을 수 있습니다. 시험하는 동안 Mac mini의 웹 UI, 웹 검색, 임베딩 서버는 멈춰 메모리를 비웠고, 노트북의 웹 UI용 모델 서버도 내렸다가 끝난 뒤 다시 켰습니다.

설정 값
기억할 글 길이 49,152토큰, 그중 답 한 번에 4,096토큰까지
쓸 수 있는 도구 명령 실행, 파일 찾기·읽기·고치기·쓰기
막은 것 인터넷, 웹 검색, MCP, 서버의 설정 폴더
한도 모델이 40번 답하거나 45분이 지나면 멈춤
생각(추론) 두 기계 모두 끄는 설정

처음 일곱 번은 결과에서 뺐습니다. 끝까지 돈 다섯 번과 도중에 멈춘 두 번입니다. 기억할 글 길이를 32,768로 두었더니 대화가 1만 1천 토큰쯤 쌓일 때마다 요약을 해서, 49,152로 늘렸습니다(12단계). 그다음에는 Mac mini의 메모리가 빠듯하고 시스템 프로세스 둘(audiomxd, configd)이 CPU를 붙잡고 있어서, 다시 켠 뒤 처음부터 돌렸습니다. 다시 켠 뒤에도 두 프로세스는 CPU를 계속 썼습니다. Mac mini는 한 바퀴에 세 시간쯤 걸려 두 번까지 돌렸습니다.

고른 모델

Mac mini는 GPU가 쓸 수 있는 몫이 22GB입니다(2단계). 4비트로 줄인 파일이 그 안에 들어가고, 기억할 글을 담을 자리가 남는 모델 가운데 일곱 개를 골랐습니다. 다섯 개는 MoE(전문가 혼합) 모델입니다. 안에 작은 신경망(전문가)을 여러 개 두고 토큰마다 몇 개만 골라 계산해서, 전체 크기보다 훨씬 가볍게 돕니다. 나머지 둘은 토큰마다 숫자 전부를 계산하는 dense 모델입니다.

숫자 개수는 모델 이름에 적힌 값입니다. 파일 크기와 GPU 몫은 1GB를 1,024MB로 센 값입니다.

  • Qwen3.8 27B와 Gemma 4 26B-A4B는 10단계까지 각각 Mac mini와 노트북이 늘 돌리던 모델이다.
  • Qwen3-Coder, Devstral Small 2, Laguna XS 2.1은 코딩용으로 나온 모델이다. Laguna는 로컬 기계에서 에이전트 코딩을 하라고 만든 모델이라고 소개돼 있다. Qwen3-Coder는 2025년 7월에 나와 이번 모델 가운데 가장 오래됐다.
  • Qwen3.6 35B-A3B와 GLM-4.7-Flash는 코딩도 하는 범용 모델이다.

Mac mini에는 mlx-community가 변환한 4비트 MLX 파일을 받아 지문(SHA-256)을 맞춰 보고 썼습니다. 노트북에는 같은 모델의 GGUF 파일을 썼고, 압축 방식은 Qwen3.6과 Gemma가 UD-IQ4_XS, Qwen3.8이 UD-Q4_K_M, Devstral이 Q4_K_M입니다. 노트북에는 Mac mini와 견줄 네 개만 올렸습니다. 10단계까지 쓰던 두 모델, MoE 대표인 Qwen3.6, 코딩용 dense인 Devstral입니다.

칸의 숫자는 통과한 횟수입니다. 결과물이 맞고, 에이전트가 스스로 일을 끝내야 통과입니다. 괄호는 끝이 어떻든 마지막 파일이 맞았던 횟수이고, 통과와 다를 때만 적었습니다. Devstral은 대화 형식을 고친 사본의 결과입니다. 원래 파일로는 두 기계 모두 세 과제가 다 첫 요청에서 오류로 끝났습니다(12단계).

  • Qwen3.6 35B-A3B가 가장 나았다. 결과물은 두 기계에서 15번 모두 맞았다. Mac mini에서 한 번은 결과물을 다 만든 뒤 서버가 메모리 부족으로 멈춰 통과로 세지 않았다.
  • 노트북이 더 안정적이었다. 같은 모델 넷으로 견주면 노트북은 36번 중 34번, Mac mini는 24번 중 15번 통과했다. 결과물만 보면 Mac mini도 24번 중 20번 맞았다.
  • Mac mini에서는 고치기와 더하기가 어려웠다. 일곱 모델이 각 과제를 14번씩 풀어, 찾기는 11번, 고치기는 6번, 더하기는 5번 통과했다. 노트북은 고치기와 더하기 24번이 모두 통과했고, 찾기에서만 두 번 실패했다.

걸린 시간

과제 세 개를 한 바퀴 도는 데 걸린 시간(분)입니다. 실패한 시도도 들어 있고, 45분 한도에 걸린 시도는 45분으로 셌습니다.

Qwen3.8 27B의 Mac mini 1회차 53분에는 45분 한도에 걸린 고치기와 서버가 멈춘 더하기가 들어 있어, 셋 중 하나만 통과했습니다.

  • MoE가 빨랐다. Mac mini에서 MoE 다섯은 한 바퀴에 4~34분, dense 둘은 36~62분 걸렸다. 양 끝에는 끊긴 시도가 들어 있다. 62분과 53분에는 45분 한도에 걸린 고치기가, 4분에는 서버가 멈춘 고치기가 있다. Qwen3-Coder가 빨랐던 데는 같은 일을 빠르게 되풀이하다 40번 한도에 일찍 닿은 탓도 크다.
  • 같은 모델이라도 기계마다 달랐다. 통과한 고치기만 보면 Qwen3.6은 Mac mini 3분 28초(1번), 노트북 2분 25초~8분 12초로 비슷했다. Gemma는 Mac mini에서 5분과 19분, 노트북에서 3분 28초~3분 42초였다. 까닭은 아래 「두 기계의 차이」에 적었다.

원래 형식의 Devstral을 빼고, Mac mini는 42번 중 20번, 노트북은 36번 중 2번 통과하지 못했습니다.

「서버 멈춤」은 MLX 서버가 메모리 부족으로 멈춘 경우입니다. 대화 기록을 열어 보니 실패에는 몇 가지 모양이 있었습니다.

같은 일을 되풀이했다

실패로 센 40번 한도 여섯 번 가운데 다섯 번은 글자까지 같은 명령을 18~176번 되풀이했습니다.

  • Qwen3-Coder는 고치기에서 **/BugListPage.tsx라는 파일을 176번 찾았다. 한 번 답할 때마다 같은 찾기를 여러 개씩 보냈다. 이 블로그는 Astro로 만들어 .tsx 파일이 하나도 없다. 다른 고치기에서도 없는 .tsx 파일을 29번 찾았고, 찾기에서는 있지도 않은 도구 Ggrep을 32번 불렀다.
  • Qwen3.8 27B는 Mac mini의 고치기 두 번 모두, 빌드된 HTML에서 class 이름을 뽑는 grep을 조금씩 바꿔 가며 한 번은 22번, 한 번은 27번 실행했다. 앞의 것은 45분 한도에, 뒤의 것은 40번 한도에 걸렸다. 고칠 곳은 빌드 결과가 아니라 원본 코드에 있었다.
  • GLM-4.7-Flash는 작업 폴더 이름을 agent-glm-4.7-flash가 아니라 agent-glm-7-flash로 잘못 적은 명령을 19번 실행했다.
  • Laguna XS 2.1은 되풀이 없이 이것저것 35가지를 하다가 40번에 닿았다.

다 해 놓고 끝내지 못했다

Devstral은 Mac mini에서 결과물을 6번 모두 맞게 만들었지만, 스스로 끝낸 것은 찾기 두 번뿐이었습니다. 고치기 한 번은 시작 9분 만에 고쳐 놓고도 확인을 이어 가다가, 마지막 요청 하나가 30분 동안 끝나지 않아 45분 한도에 걸렸습니다. 더하기 한 번은 피드의 항목 수를 세는 grep -c "<item>" dist/rss.xml을 18번 실행하다 40번 한도에 걸렸습니다. 빌드된 피드는 줄바꿈이 없는 한 줄짜리 파일이라, 몇 번을 세도 1이 나왔습니다. 나머지 두 번은 서버가 멈췄습니다.

틀리고도 됐다고 했다

  • Laguna XS 2.1은 버그 기록 8개를 피드에 넣었지만 주소를 모두 글 주소(/posts/…)로 만들었다. 버그 기록인지 가리는 조건이 실제 데이터와 맞지 않았다. 그러고는 「RSS 피드가 성공적으로 업데이트되었습니다」라고 답했다.
  • Qwen3-Coder는 한 번은 빌드가 읽지 않는 곳에 피드 파일을 따로 만들어, 실제 피드는 그대로였다. 다른 한 번은 사이트의 피드 코드를 두고 따로 스크립트를 짜서 고정된 피드 파일을 만들었다. 그 피드에는 없는 주소 https://cybug.com, RSS가 아닌 날짜 형식, 버그 기록의 틀(_template)까지 들어갔고, 사본 안에 MEMORY.md와 memory/ 폴더도 만들었다. 두 번 다 영어로 성공했다고 답했다.
  • Gemma 4는 Mac mini에서 한 번, 읽기 시간을 묻자 src/components/Reading.astro라고 답했다. 이 파일은 홈 화면의 「대표 기록」 상자에서 글자 너비를 재는 코드다. 이름에 Reading이 들어간 다른 파일을 짚고, 그 코드를 읽기 시간 계산이라고 설명했다.

파일을 안 보고 답했다

  • Devstral은 노트북에서 두 번, 파일을 하나도 열지 않고 답했다. 한 번은 「파일 itself를 고치지 말라고 하셨기 때문에 파일 내용을 확인하지 않겠습니다」라며 흔한 계산법(1분에 200~250단어)을 늘어놓았다. 「고치지 마세요」를 「보지 마세요」로 받아들인 셈이다. 다른 한 번은 「일반적으로 콘텐츠 길이를 바탕으로 계산한다」는 두 문장으로 끝냈다.
  • Laguna XS 2.1은 Mac mini에서 한 번, 찾아보지 않고 파일 경로를 알려 달라고 되물었다. 답에는 생각을 끝내는 표시인 </think>가 섞여 같은 문단이 두 번 나왔다.

서버가 멈췄다

Mac mini의 MLX 서버는 시험 동안 메모리가 모자라 6번 멈췄습니다. 그중 5번은 결과물을 이미 맞게 만든 뒤였습니다. 멈춘 서버는 프로세스가 살아 있는 채로 모든 요청에 404를 돌려주고, Claude Code는 「There’s an issue with the selected model」이라고 띄웁니다. 노트북은 한 번도 멈추지 않았습니다. 왜 그런지는 13단계에 씁니다.

두 기계의 차이

같은 모델이라도 두 기계는 엔진(MLX와 llama.cpp), 파일의 압축 방식, 메모리를 잡는 방식이 다릅니다. 기록을 읽다가 하나를 더 찾았습니다.

  • 노트북의 Gemma만 생각했다. 생각(추론)은 두 기계 모두 끄게 했다. 끄는 방법은 엔진마다 달라서, MLX에는 enable_thinking: false를, llama.cpp에는 --reasoning-budget 0을 줬다. 그런데 노트북의 Gemma는 과제마다 1,400~9,900자씩 생각한 글을 남겼고, Mac mini의 Gemma는 많아야 156자였다.
  • 생각하지 않은 Gemma는 더 많이 헤맸다. Mac mini의 Gemma는 고치기에서 25번과 39번 답했고, 노트북의 Gemma는 11~13번이었다. Mac mini에서는 한 파일을 고치려다 열 번 이상 거절당한 시도가 셋 있었다. 바꿀 부분을 파일에 없는 모양으로 적거나 바뀌는 것이 없는 수정을 보냈고, 결국 파일을 통째로 다시 썼다.

생각한 쪽이 덜 헤맸다고 볼 수도 있지만, 엔진과 파일도 달라서 이것 하나로 가리지는 못했습니다. 두 기계에서 함께 돌린 나머지 셋(Qwen3.6, Qwen3.8, Devstral)은 어느 쪽에서도 생각한 글이 없었습니다. 한 칸에 두세 번씩만 돌려서, 한 번의 차이는 우연일 수도 있습니다.

알게 된 것

  • Mac mini에서도 코딩 에이전트가 돈다. Qwen3.6 35B-A3B는 Mac mini에서 과제 세 개를 6분 만에 모두 끝냈다. 결과물은 Mac mini 6번, 노트북 9번 모두 맞았다.
  • MoE가 빨랐다. Mac mini에서 토큰마다 30억~40억 개만 계산하는 모델은 한 바퀴를 4~34분에, 전부 계산하는 dense 모델은 36~62분에 돌았다.
  • 코딩용이라는 이름이 결과를 정하지 않았다. 코딩용 셋 가운데 Qwen3-Coder는 6번 중 1번, Laguna는 3번 통과했고, Devstral은 대화 형식을 고쳐야 돌았다.
  • 「성공했다」는 답을 믿으면 안 된다. 틀린 결과 네 번 가운데 세 번은 성공했다고 답했다. 결과물은 빌드해서 기계로 확인해야 한다.
  • 실패에는 모양이 있다. 같은 명령 되풀이, 파일을 안 보고 답하기, 엉뚱한 파일 짚기, 다 해 놓고 끝내지 못하기.
  • Mac mini는 메모리가 먼저 모자랐다. 노트북은 한 번도, Mac mini는 6번 멈췄다.
  • 기계를 견줄 때는 생각 설정까지 확인한다. 두 기계 모두 생각을 끄게 했지만 끄는 방법이 엔진마다 달랐고, 노트북의 Gemma만 생각했다.

시험 도중에 바꾼 것

Mac mini 1회차 뒤에 시험 스크립트를 고쳤습니다. 과제마다 서버가 살아 있는지 먼저 묻고 멈췄으면 다시 켜게 했고, 45분 한도에 걸린 과제 뒤에도 서버를 다시 켜게 했습니다. 1회차에는 모델을 바꿀 때만 확인했습니다. 1회차의 Qwen3.8 27B 더하기는 고치기가 45분 한도에 걸린 바로 뒤에 시작해 2분 만에 서버가 멈췄는데, 끝나지 않은 고치기의 요청이 서버에 남아 있었을 수 있습니다. 모델과 한도는 바꾸지 않았습니다. 또 Qwen3-Coder의 더하기 2회차는 검사 코드가 RSS가 아닌 날짜를 읽다가 오류를 내서 기록이 빠졌습니다. 대화 기록으로 되살리고(결과는 실패), 검사 코드도 고쳤습니다.
