Claude Code를 Ollama에 바로 붙이기

2편과 3편에서 Claude Code는 게이트웨이를 거쳐 Ollama와 이야기했습니다. Ollama는 Claude 형식 API도 내주니, 이번에는 게이트웨이를 빼고 바로 붙여 같은 과제를 맡겼습니다.

올린 날
2026-11-19
읽는 시간
약 12분

이번에 할 일

  1. Claude Code를 Ollama에 바로 붙인다. 게이트웨이를 빼고, Ollama가 안내하는 설정을 쓴다.
  2. 2편, 3편과 같은 과제를 맡겨 견준다. Mac mini와 노트북에서 같은 모델 네 개로 돌려, 게이트웨이를 거칠 때와 견준다.
  3. 바로 붙이면 무엇이 달라지는지 찾는다. Claude Code가 보내는 요청을 받아 보고, Ollama가 그 요청을 어떻게 읽는지 소스에서 확인한다.

바로 붙이는 법

Ollama는 OpenAI 형식 API와 함께 Claude 형식 API(/v1/messages)도 냅니다. Claude Code가 요청을 보낼 주소를 Ollama로 바꾸면 됩니다. Ollama 문서의 안내는 이렇습니다.

Ollama는 API 키를 확인하지 않습니다. 토큰은 Ollama 문서가 「꼭 넣되 무시된다」고 적은 자리라 아무 글자나 넣습니다.

ollama launch claude 명령은 이 설정에 몇 가지를 더해 Claude Code를 띄웁니다. Ollama 0.40.16 소스에서 더하는 것은 이렇습니다.

  • 모델 이름: Opus, Sonnet, Haiku, 하위 에이전트 모델을 모두 고른 모델로 둔다. Claude Code가 뒤에서 작은 모델에게 보내는 요청도 같은 모델로 간다.
  • 청구 머리말: Claude Code가 시스템 프롬프트 맨 앞에 붙이는 청구 머리말(billing header)을 끈다. 이 머리말에는 첫 질문에 따라 바뀌는 글자 세 개가 들어 있어, 대화마다 프롬프트 맨 앞이 달라진다.
  • 보고와 설문: 오류 보고, 피드백 명령과 설문을 끈다.
  • 길이: 기억할 글 길이와 답 길이는 클라우드 모델에만 정해 준다. 로컬 모델에는 정하지 않는다.

이번 시험은 ollama launch claude가 넣는 설정을 그대로 쓰고, 2편의 시험 조건을 더했습니다. Claude Code의 기억할 글 길이 49,152토큰, 한 번에 쓰는 답 4,096토큰, 40번 주고받기, 45분 제한입니다. 2편에서 생각을 끄려고 넣었던 MAX_THINKING_TOKENS=0은 빼고, Claude Code가 보내는 그대로 두었습니다. 넣어도 생각이 꺼지지 않는 까닭은 아래에서 다룹니다. 두 기계의 Ollama도 2편, 3편처럼 49,152토큰으로 띄웠습니다. 기계마다 모델 네 개에 과제 셋을 2회씩, 24번 돌렸습니다. Claude Code는 2편, 3편처럼 Mac mini에서 돌았고, 노트북의 Ollama에는 같은 네트워크로 붙었습니다.

길이를 정하지 않으면 요청이 잘린다

ollama launch claude만 따르면 기억할 글 길이를 아무 데서도 정하지 않습니다. 그러면 Ollama가 GPU 메모리를 보고 길이를 정하는데, Mac mini에서는 4,096토큰이었습니다.

Claude Code의 첫 요청은 시스템 프롬프트와 도구 설명만으로 이보다 훨씬 깁니다. 시험의 도구 여섯 개만 줘도 6,700~7,000토큰입니다. 이 상태로 찾기 과제를 두 모델에 한 번씩 맡겼습니다. Claude Code에도 길이를 알려 주지 않았습니다.

  • Qwen3.6 35B: 첫 요청 6,743토큰 가운데 앞 4토큰과 뒤 2,046토큰만 남았다. 질문을 잃은 모델은 무엇을 도와줄지 말해 달라고 영어로 답했고, Claude Code는 이것을 마지막 답으로 받아 12초 만에 끝냈다.
  • Qwen3.8 27B: 잘리지 않았다. 7,007토큰짜리 첫 요청을 다 읽었고, 대화가 8,871토큰까지 길어져도 그대로 읽었다. 4분 6초 만에 찾기를 통과했다.

Ollama는 두 모델 모두 오류 없이 200으로 답했습니다. 차이는 엔진에서 났습니다. 2편에서 본 대로 Ollama는 모델 파일 형식에 따라 엔진을 고릅니다. Qwen3.6은 llama.cpp 엔진으로, Qwen3.8은 MLX 엔진으로 돌았고, 길이를 넘긴 요청을 자른 것은 llama.cpp 엔진뿐이었습니다. 그것도 기억할 글 길이 4,096토큰이 아니라 그 절반쯤인 2,050토큰만 남겼습니다. 노트북의 Ollama는 모든 모델을 llama.cpp 엔진으로 돌립니다.

작은 모델에 Claude Code의 기본 도구를 다 붙였을 때는 더 이상했습니다. qwen3:0.6b는 12,057토큰 가운데 2,050토큰만 받았고, 첫 답을 32,000토큰 한도까지 쓰느라 5분을 보냈습니다. 그다음에는 a.txt를 읽어 달라는 부탁 대신 script.js라는 파일을 새로 만들었습니다. 파일 내용은 Claude Code의 한 도구 설명에 든 예시를 닮아 있었습니다.

그래서 바로 붙일 때는 길이를 양쪽에 정해야 합니다. Ollama에는 OLLAMA_CONTEXT_LENGTH로 모델이 기억할 길이를, Claude Code에는 CLAUDE_CODE_MAX_CONTEXT_TOKENS로 그 길이를 알려 줍니다. Claude Code는 이 값을 보고 대화가 길어지면 앞부분을 요약합니다. Ollama 문서는 코딩 에이전트에 64k 이상을 권하고, 이번 시험은 2편처럼 49,152토큰으로 맞췄습니다.

생각을 끌 수 없었다

2편에서는 Claude Code를 MAX_THINKING_TOKENS=0으로 띄워 생각 요청을 뺐습니다. 게이트웨이를 거칠 때는 이것으로 생각이 꺼졌습니다. 바로 붙이면 꺼지지 않습니다.

Claude Code가 보내는 요청을 가짜 서버로 받아 보면, 생각에 관한 값이 둘입니다. 생각을 켜 달라는 thinking과, 얼마나 애쓸지를 정하는 output_config.effort입니다. 설정을 바꿔 가며 받아 본 첫 요청은 이랬습니다.

Claude Code 설정 thinking effort
그대로 adaptive high
MAX_THINKING_TOKENS=0 없음 high
설정 파일의 alwaysThinkingEnabled: false 없음 high
CLAUDE_CODE_EFFORT_LEVEL=auto adaptive 없음
위의 둘째와 넷째를 함께 없음 없음

--effort low처럼 정도를 바꾸면 effort 값만 바뀌었습니다. 생각을 끄라는 thinking: disabled는 어느 설정에서도 보내지 않았습니다.

Ollama 0.40.16은 이 두 값을 이렇게 읽습니다.

  1. thinking이 enabled면 생각을 켜고, disabled면 끈다.
  2. 그 밖에는 effort 값으로 생각의 정도를 정한다.
  3. effort도 없으면 모델의 기본값을 쓴다.

시험한 모델의 기본값은 생각할 수 있는 모델이면 모두 「켬」이었습니다.

모델 Ollama가 받는 값 기본값
Qwen3.8 27B false, low, medium, xhigh medium
Gemma 4 26B false, true true
Qwen3.6 35B false, true true
Devstral 24B 생각 기능 없음 -

그래서 Claude Code를 바로 붙이면 Qwen과 Gemma는 늘 생각합니다. Claude Code가 보내는 high는 Qwen3.8의 목록에 없어서 기본값 medium이 됩니다. qwen3:0.6b에 같은 질문을 보내 확인했습니다. 아무 값 없이 보내도, effort high로 보내도 생각하다가 답 한도 600토큰에 걸렸고, disabled일 때만 생각 없이 16토큰으로 답했습니다.

게이트웨이를 거칠 때는 달랐습니다. 게이트웨이(LiteLLM)는 thinking 값만 모델에 맞게 바꿔 넘기고, effort 값으로는 생각을 켜지 않았습니다. 그래서 thinking을 빼면 생각이 꺼졌습니다.

Devstral은 반대로 바로 붙인 덕을 봤습니다. 생각 기능이 없는 모델에 생각 요청이 오면, Ollama는 OpenAI 형식 API에서는 400 오류로 거절하지만 Claude 형식 API에서는 요청에서 생각을 지우고 넘깁니다. 2편 첫 회차에서 Devstral이 받은 400 오류는 바로 붙이면 나지 않습니다. 이번에 두 기계에서 Devstral을 12번 돌리는 동안 400 오류는 한 번도 없었습니다.

통과 수는 줄지 않았다

두 기계에서 통과한 수입니다. 게이트웨이 칸은 2편, 3편에서 생각을 끄고 돌린 결과이고, 바로 칸이 이번 결과입니다. 「생각한 글」은 바로 붙였을 때 과제 하나에 쓴 생각의 가운데 값입니다.

  • 노트북의 Gemma 4: 3편에서는 고치기 도구를 18번 불러 17번 거절당하고 40번 한도에 걸린 실행이 있었다. 이번에는 거절이 한 번도 없었다. 생각이 도왔을 수 있지만, 두 번씩 돌린 결과라 단정할 수 없다.
  • 노트북의 Devstral: 한 번 실패했다. 찾기 2회차에서 도구를 쓰지 않고 첫 답으로 끝냈다.
  • Qwen3.6: 실패는 두 기계 모두 더하기에서 틀린 결과로 끝난 것이었다. 2편의 게이트웨이 때도 같은 과제에서 한 번 틀렸다.
  • Mac mini의 Devstral: 더하기 두 번이 모두 45분 제한에 걸렸다. 파일은 맞게 고쳐 둔 채였다. 아래에서 따로 다룬다.

생각하는 세 모델은 두 기계 모두 찾기와 더하기가 늘었고, 고치기는 줄었습니다. 고치기에서는 주고받은 횟수도 모든 칸에서 줄었습니다. 생각이 헤매는 일을 줄였을 수 있지만, 두 번씩 돌린 결과입니다. 생각하지 않는 Devstral도 같은 과제에서 시간이 7~38% 달라졌습니다.

2편에서 게이트웨이를 거쳐 생각을 켜고 돌린 결과와 견주면, 시간은 길보다 생각한 양을 따라갔습니다. Qwen3.8은 바로 붙였을 때 세 과제 모두 더 많이 생각했고, 모두 느렸습니다. Gemma는 찾기만 더 많이 생각해 느렸고, 고치기와 더하기는 덜 생각해 빨랐습니다.

길을 바꾼 것 자체로 느려지지는 않았습니다. Mac mini에서 Ollama가 앞서 읽은 대화를 다시 쓴 비율은 실행마다의 가운데 값으로 게이트웨이를 거칠 때 81~88%, 바로 붙일 때 81~89%였고, 읽는 속도도 같았습니다.

Devstral은 요약할 때 대화를 처음부터 다시 읽었다

Mac mini의 Devstral은 더하기 두 번 모두 Claude Code가 대화를 요약하려던 때에 멈춰 있었습니다. 2편에서 「대화를 왜 처음부터 다시 읽었는지 기록에 없었다」고 적은 일도 같은 일이었습니다. 순서는 이렇습니다.

  1. Claude Code가 요약을 요청한다. 대화가 기억할 글 길이에 가까워지면 Claude Code는 지금까지의 대화를 요약해 달라고 요청한다. 이번 설정에서는 3만 2천 토큰 안팎에서였다. 이 요청은 대화 전체에 6,361자짜리 요약 지시문을 덧붙이는데, 지시문은 마지막 도구 결과와 같은 메시지 안에 들어간다. 가짜 서버로 받아 확인했다.
  2. Ollama가 그 메시지를 둘로 나눈다. 도구 결과와 글이 함께 든 메시지를 도구 결과 메시지와 새 사용자 메시지로 가른다. Ollama 0.40.16의 소스에서 확인했다. 2편에서는 게이트웨이(LiteLLM)가 요청을 OpenAI 형식으로 바꾸며 이 일을 했다.
  3. Devstral의 대화 형식이 도구 목록을 옮긴다. 이 대화 형식은 도구 목록을 마지막 사용자 메시지 바로 앞에 넣는다. 도구 결과는 사용자 메시지가 아니므로, 평소의 마지막 사용자 메시지는 첫 질문이고 도구 목록도 대화 앞쪽에 머문다. 요약 요청에서는 새 사용자 메시지가 맨 끝에 생기고, 도구 목록도 맨 끝으로 간다.
  4. 시스템 프롬프트 뒤가 모두 달라진다. Ollama는 앞서 읽은 것과 앞부분이 같은 만큼만 다시 쓴다. 같은 것은 시스템 프롬프트까지의 1,235토큰뿐이었다. 나머지 3만 2천여 토큰을 다시 읽어야 했고, Mac mini는 이 길이의 Devstral을 초당 26~50토큰으로 읽었다.

시험이 끝난 뒤 따로 재현했습니다. 가짜 서버로 받아 둔 Claude Code의 요청 두 개를 Devstral에 그대로 보냈습니다. 하나는 도구 결과로 끝나는 보통 요청이고, 하나는 같은 대화에 요약 지시문을 더한 요청입니다.

요약 지시문을 더한 요청 7,965 1,254 6,711

요약 지시문이 더한 길이는 시험 때와 같은 1,323토큰이었는데, 다시 읽은 것은 6,711토큰이었습니다. 다시 쓴 앞부분이 시험 때(1,235토큰)와 조금 다른 것은, 시스템 프롬프트에 든 작업 폴더 경로 같은 값이 달라서로 보입니다. 2편에서 다시 쓴 1,264토큰도 시스템 프롬프트까지로 보입니다. 2편은 청구 머리말을 끄지 않았고 작업 폴더 이름도 달라, 그 길이가 조금 달랐습니다.

Qwen과 Gemma는 이번 시험에서 요약 문턱에 닿은 실행이 없었습니다. Ollama 0.40.16의 소스를 보면 두 모델의 렌더러는 도구 목록을 맨 앞 시스템 자리에 두므로, Devstral처럼 도구 목록이 옮겨 가지는 않습니다.

더하기 1회차의 기록을 맞춰 보면 이렇습니다.

  1. 15:06:01: 32,467토큰 요청을 마쳤다. 요약 문턱을 넘었다.
  2. 15:06:01: Claude Code가 요약 요청을 보냈다. 앞 요청보다 1,323토큰 긴 33,790토큰으로, 요약 지시문의 길이쯤이다. Ollama는 1,235토큰만 다시 쓰고 나머지를 읽기 시작했다.
  3. 15:11:46: 5분 40초 만에 Claude Code가 연결을 끊었다. Ollama는 500을 기록하고 곧바로 읽기를 멈췄다. 18,643토큰까지 읽은 때였다.
  4. 15:11:47~15:17:47: Claude Code가 같은 요청을 다시 보냈다. Ollama는 앞에서 읽어 둔 18,643토큰부터 이어 읽었지만, 이 요청도 6분 만에 끊겼다. 29,907토큰까지 읽은 때였다.
  5. 15:21:44: 세 번째 요청이 나머지를 읽고 요약을 쓰기 시작했을 때, 45분 제한으로 시험이 멈췄다.

2회차도 같았습니다. 32,951토큰 요청 다음에 1,323토큰 긴 요약 요청이 왔고, 1,235토큰만 다시 썼고, 5분 50초와 6분 만에 끊겼고, 세 번째 요청이 요약을 쓰던 중에 45분 제한에 걸렸습니다.

2편과 다른 것은 끊긴 다음이었습니다. 2편에서 게이트웨이는 Claude Code가 끊은 요청을 Ollama에 그대로 붙잡아 두었고, 다시 보낸 요청은 동시 요청 한도에 걸려 429를 받았습니다. 바로 붙이면 Ollama가 끊긴 요청을 곧바로 멈추고, 다시 보낸 요청이 읽어 둔 데부터 이어 읽습니다. 그래서 세 번째 요청은 처음부터가 아니라 29,907토큰부터 읽어, 요약을 쓰기 시작할 수 있었습니다. 다만 Mac mini는 이 길이의 Devstral로 초당 2토큰 안팎을 썼습니다. 요약 천 토큰에 8분쯤 걸리는 셈입니다.

노트북에서는 이 일이 없었습니다. 노트북의 Devstral은 가장 긴 대화가 30,717토큰이라 요약 문턱에 닿지 않았고, 5/6을 통과했습니다.

Claude Code는 첫 응답을 6분까지만 기다렸다

Claude Code는 왜 6분 안에 요청을 끊었을까요. 시험에서는 API_TIMEOUT_MS로 요청 시간 제한을 30분으로 두었습니다. 2편에서는 까닭을 찾지 못했습니다.

응답을 늦게 주는 가짜 서버로 재 봤습니다. 첫 요청을 받고 9분 동안 한 바이트도 보내지 않는 서버입니다. Ollama도 긴 요청을 읽는 동안에는 응답 머리조차 보내지 않는 것으로 보입니다. 끊긴 요청이 Ollama 기록에 200이 아니라 500으로 남았기 때문입니다.

Claude Code 설정 첫 요청
시험과 같음 6분 0초에 끊고 곧바로 다시 보냄
여기에 API_FORCE_IDLE_TIMEOUT=0 9분을 다 기다림

API_FORCE_IDLE_TIMEOUT은 Claude Code 2.1.326의 실행 파일에서 찾은 환경 변수입니다. 이 값을 0으로 두면 Claude Code가 요청을 보낼 때 fetch의 시간 제한을 끄는(timeout: false) 것을 실행 파일의 코드에서 확인했습니다. 시험 기록에서 끊긴 때가 5분 12초에서 6분까지 조금씩 달랐던 까닭은 확인하지 못했습니다.

느린 기계에서 긴 대화를 다룰 때는 이 값을 함께 주는 편이 낫습니다. 다만 끊기지 않는다고 빨라지지는 않습니다. 이번 Devstral의 요약 요청은 세 번에 걸쳐 읽는 데만 14분쯤 걸렸고, 요약은 초당 2토큰 안팎으로 썼습니다.

게이트웨이를 빼면 빠지는 것

게이트웨이(LiteLLM)는 Claude Code와 Ollama 사이에서 몇 가지 일을 했습니다. 바로 붙이면 이 일도 같이 빠집니다.

게이트웨이가 하던 일 바로 붙이면
API 키 확인 없다. Ollama는 키를 보지 않아, 포트에 닿기만 하면 누구나 쓴다
키마다 동시 요청 한도 없다. Ollama 전체의 동시 요청 수만 있고, 넘는 요청은 줄을 선다
키마다 사용량 기록 없다. Ollama 기록에는 요청마다 시각, 응답 코드, 걸린 시간, 보낸 주소가 남는다
두 기계를 한 주소로 없다. 기계마다 주소를 따로 적는다
생각 끄기 안 된다. 앞에서 본 대로다
끊긴 요청 붙잡아 두어 다시 보낸 요청이 429를 받았다. 바로 붙이면 곧바로 멈추고 이어 읽는다

그래서 이번에는 Ollama에 아무나 닿을 수 없게 두었습니다. Mac mini의 Ollama는 127.0.0.1에서만 받아 같은 기계 안의 Claude Code만 쓸 수 있고, 노트북의 Ollama는 방화벽 규칙으로 Mac mini에서 오는 연결만 받게 했습니다.

알게 된 것

  • 바로 붙여도 통과 수는 줄지 않았다. 두 기계, 모델 네 개의 여덟 칸 가운데 다섯 칸이 같았고, 두 칸이 늘었고, 한 칸이 줄었다.
  • 바로 붙이면 생각을 끌 수 없다. Claude Code는 생각을 끄라는 값을 보내지 않고, Ollama는 effort 값만으로도 생각을 켠다.
  • 길이는 양쪽에 정해야 한다. 정하지 않으면 Mac mini의 Ollama는 4,096토큰으로 띄우고, llama.cpp 엔진은 넘치는 요청을 그 절반쯤인 2,050토큰으로 오류 없이 잘라 읽는다.
  • Devstral은 요약 요청마다 대화를 처음부터 다시 읽는다. Ollama가 요약 지시문을 새 사용자 메시지로 떼어 내고, Devstral의 대화 형식이 도구 목록을 그 앞으로 옮긴다.
  • Claude Code는 첫 응답을 6분까지만 기다린다. API_TIMEOUT_MS와 상관없었고, API_FORCE_IDLE_TIMEOUT=0을 주면 기다렸다.
  • 게이트웨이를 빼면 키, 한도, 기록도 빠진다. 바로 붙인 Ollama는 네트워크에서 막아 둬야 한다.
