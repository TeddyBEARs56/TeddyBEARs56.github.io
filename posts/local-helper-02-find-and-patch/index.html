코드 찾기와 몇 줄 고치기를 로컬 모델에게 맡기면

1편에서는 빌드 로그를 로컬 모델에게 대신 읽혔습니다. 이번에는 클라우드 코딩 에이전트가 손으로 하는 일 두 가지, 코드가 어디 있는지 찾는 일과 정해진 대로 몇 줄을 고치는 일을 맡깁니다. 둘 다 답이 정해져 있어 사람의 채점 없이 자동으로 맞았는지 가렸습니다.

올린 날
2026-11-24
읽는 시간
약 5분

이번에 할 일

  1. 코드 찾기. 「이 화면의 이 숫자는 어디서 만드나」 같은 질문 8개를 내고, 모델이 도구로 저장소를 뒤져 파일과 줄을 답하게 한다.
  2. 몇 줄 고치기. 무엇을 어떻게 고칠지 적은 지시서 6개를 주고, 모델이 낸 수정안을 실제로 적용해 빌드와 검사를 돌린다.

모델과 설정은 1편과 같습니다. Mac mini의 Qwen3.6 35B와 Qwen3.8 27B, 노트북의 Gemma 4 26B를 Ollama 0.40.16에서 온도 0, 생각 끔으로 돌렸고, 문항마다 한 번씩 돌렸습니다. 저장소는 이 블로그의 11-23 시점이고, 고치기 1~3번만 그 커밋들의 바로 앞 시점입니다.

코드 찾기

방법

모델에게 도구 셋을 줬습니다. 파일 목록 보기(list_files), 글 찾기(grep), 파일 읽기(read_file)입니다. 모델이 도구를 부르면 시험 스크립트가 저장소에서 실행해 결과를 돌려주고, 모델은 12번까지 부를 수 있습니다.

번호 질문
1 홈의 「7편 중 7편」 문구를 만드는 곳
2 _로 시작하는 초안을 숨기는 곳
3 표 칸의 낱말 묶기 최대 글자 수
4 Cybug 상태별 개수를 세는 곳
5 바닥글 방문자 수를 가져오는 함수
6 「읽는 시간」을 계산하는 함수
7 「다음 글」 카드의 금색 스타일
8 Google Analytics 측정 ID

답의 파일이 정답과 같고, 줄 번호가 정답 범위의 앞뒤 15줄 안이면 맞은 것으로 셌습니다.

결과

모델 맞힘 도구 걸린 시간
Qwen3.8 8/8 3번 67.5초
Qwen3.6 7/8 3번 12.3초
Gemma 4 6/8 3번 20.5초

도구 횟수와 시간은 문항 하나의 가운데 값입니다. Qwen 둘은 보통 grep 한두 번으로 후보를 좁힌 뒤 파일 하나를 읽고 답했습니다. Gemma 4는 1, 7, 8번을 파일을 읽지 않고 grep 결과만으로 답했습니다.

  • 3번(표 칸의 최대 글자 수)이 가장 어려웠다. 정답은 src/lib/keep-words.ts의 MAX_CELL = 9다. Qwen3.8은 max를 찾는 grep이 빈 결과를 내자(시험 도구가 {astro,ts} 같은 중괄호 glob을 읽지 못했다), 파일 목록에서 keep-words.ts라는 이름을 보고 열어 맞혔다. Qwen3.6은 CSS의 word-break: keep-all을, Gemma 4는 CSS의 .nb { white-space: nowrap; }를 답했다. 둘 다 줄바꿈을 막는 스타일이지 글자 수가 아니다.
  • Gemma 4는 2번에서 이 저장소에 맞지 않는 규칙을 댔다. 「Astro의 기본 규칙에 따라 _로 시작하는 파일은 제외된다」며 posts.ts를 답했다. Astro의 src/pages에는 그런 규칙이 있지만, 이 블로그의 글은 src/content.config.ts의 glob 패턴 [^_]*가 막는다. Qwen 둘은 이 파일을 읽고 맞혔다.

몇 줄 고치기

방법

지시서 여섯 개를 썼습니다. 1~3번은 이 블로그의 실제 커밋 셋을 되돌린 자리에서, 그 커밋이 한 일을 지시서로 다시 적은 것입니다.

번호 할 일 파일
1 타이틀 그림자 위치 조정 CSS 1
2 Safari 그림자 버그 고침 CSS 1
3 홈 카드 그림 크기 조정 CSS 1
4 연재 목록에 항목 하나 더함 TS 1
5 심어 둔 버그 찾아 고침 Astro 1
6 초안 숨기기 칸 더함 TS 2

5번만 원인을 알려 주지 않았습니다. 「Cybug의 상태별 개수가 모두 0으로 나온다. 버그 글의 머리말에는 status가 제대로 적혀 있다. 이 파일에서 원인을 찾아 고쳐라」고만 적었고, 실제로는 b.data.status여야 할 곳을 b.status로 바꿔 두었습니다.

모델에게는 고칠 파일의 내용을 통째로 주고, 수정안을 JSON으로 받았습니다.

old를 찾아 new로 바꾸는 방식은 Claude Code의 Edit 도구와 비슷합니다. 시험 스크립트가 수정안을 저장소의 새 작업 사본에 적용하고, 다음을 모두 지나면 통과로 셌습니다.

  1. old가 파일에 정확히 한 번 나온다.
  2. npm run build가 성공한다.
  3. 정답에 있어야 할 줄이 있고, 없어야 할 줄이 없다(정규식으로 검사).
  4. 지시서에 없는 파일은 바뀌지 않았다.
  5. 바뀐 줄 수(더한 줄과 뺀 줄의 합)가 문항마다 정한 상한(2~12줄)을 넘지 않는다.

결과

모델 통과 걸린 시간
Qwen3.6 6/6 27.5초
Qwen3.8 6/6 132.7초
Gemma 4 3/6 48.8초

걸린 시간은 모델이 수정안을 쓰는 데 걸린 시간의 가운데 값이고, 적용과 빌드는 들어 있지 않습니다. Qwen 둘은 여섯 문항 모두 지시서와 같은 줄을 고쳤고, 바뀐 줄은 문항마다 1~10줄이었습니다. 원인을 찾아야 했던 5번도 둘 다 b.data.status로 고쳤습니다.

Gemma 4는 셋이 실패했습니다.

  • JSON 문자열에 탭을 그대로 넣었다(4번, 6번). 이 블로그의 TS 파일은 탭으로 들여 씁니다. Gemma 4는 old에 탭을 \t가 아니라 탭 글자 그대로 넣었고, JSON은 문자열 안에 탭 글자를 허용하지 않아 읽지 못했다. Qwen 둘은 \t로 적었고, 6번에서는 pubDate 줄 다음의 주석 줄까지 old에 넣어 한 번만 나오게 했다. 탭을 너그럽게 받아 다시 적용해 보면 4번은 통과했다. 6번은 old로 고른 pubDate: z.coerce.date(),가 파일에 두 번 나와(posts와 bugs) 여전히 실패했다.
  • 주석을 잘못 옮겨 적었다(3번). CSS 파일의 /* … */ 주석을 old에 // …로 적어, 파일에서 찾지 못했다.

클라우드 에이전트에 붙인다면

  • 몇 줄 고치기는 맡길 만하다. 원인, 고칠 곳, 기대하는 모습이 다 정해진 수정이라면 Qwen3.6이 문항 하나에 가운데 값 30초쯤(문항마다 4~50초)으로 여섯 개를 모두 해냈다. 클라우드 에이전트가 지시서를 쓰고, 적용과 빌드는 스크립트가, 결과 확인은 에이전트가 하는 식을 생각해 볼 수 있다. 다만 이 흐름은 아직 해 보지 않았고, 이번 지시서 가운데 넷(1, 3, 4, 6번)은 넣을 코드를 글자 그대로 적어 준 것이었다. 과제도 모두 10줄 이하였다.
  • 코드 찾기도 쓸 만하지만 덜 믿음직하다. 가장 빠른 Qwen3.6이 8개 가운데 7개였고, 틀린 답도 그럴듯한 파일과 줄을 댔다. 찾은 자리를 에이전트가 직접 한 번 읽어 확인하는 편이 낫다.
  • JSON 형식은 모델을 가린다. Gemma 4의 실패 셋 가운데 둘은 JSON 문자열에 탭을 그대로 넣어 읽히지 않았고, 탭을 너그럽게 읽었다면 그중 하나는 통과했다. 수정안을 받는 쪽에서 탭을 너그럽게 읽거나, old가 두 번 나오면 다시 묻게 하는 방법을 생각해 볼 수 있다(해 보지는 않았다).

걸린 시간과 기다림

모델 찾기 8개 고치기 6개
Qwen3.6 1분 41초 2분 40초
Gemma 4 3분 48초 5분 17초
Qwen3.8 8분 25초 13분 26초

문항마다 걸린 시간을 더한 값입니다. Qwen3.8은 둘 다 모두 맞혔지만 Qwen3.6보다 5배쯤 느렸습니다. 고치기 문항 하나에 길게는 4분 26초가 걸려, 에이전트가 기다리기에는 깁니다.

알게 된 것

  • 정해진 몇 줄 고치기는 Qwen3.6으로 충분했다. 여섯 개를 모두 통과했고, 문항 하나에 가운데 값 27.5초였다.
  • 코드 찾기는 Qwen3.8이 가장 정확했다. 8개를 모두 맞혔지만 문항 하나에 가운데 값 1분이 넘었다.
  • 틀린 찾기 답도 그럴듯했다. 줄바꿈을 막는 CSS를 「최대 글자 수」라고 하거나, 없는 Astro 규칙을 댔다.
  • 고칠 내용이 맞아도 출력 형식에서 넘어질 수 있다. Gemma 4는 4번을 맞게 고쳤는데도 JSON에 탭을 그대로 넣어 놓쳤다.
  • 이번 결과는 한 번씩 잰 것이다. 이 블로그 저장소의 질문 8개와 과제 6개뿐이다.
