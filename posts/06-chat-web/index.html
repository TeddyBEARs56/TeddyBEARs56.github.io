웹 UI 붙이기

5단계까지 만든 MLX 서버는 늘 켜져 있지만, 쓰려면 터미널이나 코드가 필요했습니다. 이번에는 그 앞에 웹 UI를 붙여, 같은 네트워크의 누구나 브라우저로 로그인해 대화하게 합니다. 웹 UI는 ChatGPT처럼 브라우저에서 대화하는 화면이고, 여기서는 Open WebUI를 씁니다. 구조를 먼저 정하고, 설치한 뒤, 관리자 설정을 하고, 함께 쓸 사람에게 보낼 쓰는 법을 정리합니다. 붙이자마자 서버가 두 번 멈췄는데, 그 원인과 고친 설정도 함께 남깁니다.

올린 날
2026-11-16
읽는 시간
약 12분

이번에 할 일

  1. 구조를 정한다. 웹 UI를 어느 기계에 두고 모델 서버와 어떻게 잇는지 먼저 정해야, 설치할 곳과 바깥에 열어 둘 포트가 정해진다.
  2. Open WebUI를 설치하고 띄운다. 늘 켜진 Mac mini에, MLX 서버와 같은 방식으로.
  3. 관리자 설정 네 가지를 한다. 기본값 그대로면 다른 사람은 가입도 못 하고, 가입해도 모델이 보이지 않는다.
  4. 쓰는 법을 정리한다. 함께 쓸 사람에게는 이 글의 「쓰는 법」만 보내면 되게.
  5. 멈춘 원인을 고친다. 붙이자마자 서버가 두 번 멈췄다. 여러 사람이 쓰려면 이것부터 막아야 한다.
  6. 노트북 모델도 목록에 넣는다. 꼼꼼하지만 느린 Mac mini와 빠른 노트북 가운데 골라 쓰게.

구조

웹 UI는 Mac mini에 둡니다. 늘 켜져 있고, 모델 서버와 같은 기계라 둘 사이가 가깝습니다. 모델 서버는 두 대입니다. Mac mini의 MLX 서버에 더해, 뒤에서 노트북의 llama.cpp 서버도 붙였습니다. 아래 그림과 표의 번호는 포트입니다. 포트는 한 기계 안에서 프로그램마다 나눠 받는 접속 번호입니다.

부분 하는 일 어디에
Open WebUI 채팅 화면, 로그인, 대화 기록 저장 Mac mini 3000번 포트, 데이터는 ~/open-webui-data
MLX 서버 질문을 읽고 답을 쓴다 Mac mini 8080번 포트 (5단계에서 늘 켜 둠)
llama.cpp 서버 질문을 읽고 답을 쓴다 노트북 8081번 포트, Mac mini만 들어올 수 있음

브라우저는 MLX 서버와 직접 이야기하지 않습니다. Open WebUI가 가운데서 전해 줍니다. 그래서 나중에는 MLX 서버를 바깥에서 막고 Open WebUI 하나만 열어 둘 수 있습니다. 지금 MLX 서버는 API 키를 확인하지 않아서 같은 네트워크의 누구나 질문을 보낼 수 있는데, 이걸 막을 길이 생기는 셈입니다.

Open WebUI는 로컬 LLM용으로 가장 널리 쓰이는 공개 웹 UI입니다. 계정, 대화 기록, 모델 고르기, 마크다운과 코드 표시를 직접 만들지 않고 바로 얻으려고 골랐습니다.

설치하고 띄우기

5단계처럼 uv로 설치했습니다. 설치 크기는 1.9GB이고 몇 분 걸렸습니다.

띄우는 일은 시작 스크립트 ~/llm-service/start-openwebui.sh에 맡겼습니다. 핵심은 환경 변수입니다.

환경 변수 값 왜
DATA_DIR ~/open-webui-data 계정과 대화 기록을 둘 폴더를 정해 둔다
WEBUI_NAME 원하는 이름 화면 위에 보이는 서비스 이름
OPENAI_API_BASE_URLS http://127.0.0.1:8080/v1;http://192.168.x.x:8081/v1 같은 기계의 MLX 서버와 노트북 서버를 모델로 쓴다. 노트북은 뒤에서 붙였다
OPENAI_API_KEYS none;(노트북 서버의 API 키) 위 주소와 같은 순서로 보낼 API 키. MLX 서버는 확인하지 않으니 아무 글자나
AIOHTTP_CLIENT_TIMEOUT_MODEL_LIST 3 노트북이 꺼져 있어도 모델 목록을 3초 넘게 기다리지 않는다
ENABLE_OLLAMA_API false Ollama는 없으니 찾지 않게
DEFAULT_USER_ROLE pending 새로 가입한 사람은 관리자가 승인해야 쓴다
ENABLE_TAGS_GENERATION 외 3개 false 답마다 따라붙는 태그·후속 질문·자동 완성 요청을 끈다. 모델이 느려서 그만큼 다음 사람이 기다린다
ANONYMIZED_TELEMETRY 외 2개 끔 사용 통계를 바깥으로 보내지 않는다
USE_SLIM_DOCKER true Open WebUI가 GPU를 쓰지 않게 한다. 아래 「두 번 멈춘 서버」에서 찾은 설정

처음 켜기까지 약 70초 걸렸고, 메모리는 0.9GB를 썼습니다. 늘 켜 두는 방법은 5단계와 같은 launchd 데몬입니다. 이 글을 쓰는 지금은 손으로 띄워 둔 상태이고, 아래 한 줄로 맡깁니다.

처음 열기: 관리자 계정

브라우저로 처음 열면 이름, 이메일, 비밀번호를 묻습니다. 처음 가입한 사람이 관리자가 됩니다. 네트워크에 열려 있으니, 띄우자마자 직접 열어 관리자 계정부터 만들었습니다. 이메일은 로그인 아이디로만 쓰이고 메일은 가지 않습니다.

관리자 설정 네 가지

관리자 계정으로 들어가 보니, 기본값으로는 다른 사람이 쓸 수 없는 상태였습니다. 왼쪽 아래 프로필에서 설정을 열고, 아래쪽 「관리자」 묶음에서 네 가지를 고쳤습니다.

1. 가입 열기

첫 관리자가 생기면 Open WebUI가 가입을 스스로 닫습니다. 모르는 사람이 관리자가 되는 일을 막는 안전장치입니다. 시작 스크립트에 가입 허용을 넣어 두었는데도 로그인 화면에 「가입」 링크가 없었던 이유입니다.

인증에서 신규 가입을 켰습니다. 「기본 사용자 역할」은 보류 중 그대로 둡니다. 가입은 누구나 하되, 쓰는 건 관리자가 승인한 사람만 하게 하려는 것입니다.

2. 모델 이름과 공개

모델의 연필 아이콘을 누르면 모델 편집 화면이 나옵니다. 고칠 곳은 두 군데입니다.

  • 이름: 기본 이름은 서버의 폴더 경로 /Users/(내 사용자 이름)/models/mlx/… 그대로입니다. 길기도 하고 사용자 이름까지 드러나서 Mac mini · Qwen 3.8 27B로 바꿨습니다.
  • 접근: 기본이 비공개라 관리자만 모델을 볼 수 있습니다. 오른쪽 위 접근에서 공개 범위를 공개로 바꿨습니다. 그대로 두면 승인받은 사용자의 모델 목록이 비어 있습니다.

3. 기능 정리

같은 편집 화면 아래 기능을 펼치면 스위치가 아홉 개 있습니다. 네 개를 끄고 하나를 켠 뒤 저장 및 업데이트를 눌렀습니다.

스위치 바꾼 값 왜
내장(빌트인) 도구 끔 켜 두면 짧은 질문에도 도구 설명이 붙어 7,226토큰이 된다. 우리 서버는 1초에 60여 토큰을 읽으니 읽기만 2분
코드 인터프리터 끔 이 서버에서 코드를 돌려 줄 곳이 없다
비전 끔 MLX 서버(mlx_lm)는 글만 읽는다. 켜 두면 그림을 올릴 수 있는 것처럼 보인다
메모리 끔 기억해 둔 내용을 질문마다 덧붙인다. 느린 서버에서는 그만큼 늦어진다
사용량 켬 답 아래 ⓘ에 읽은 토큰과 쓴 토큰이 나온다

내장 도구를 끄자 같은 질문이 7,226토큰에서 30토큰으로 줄었습니다. 2분 넘게 걸리던 답이 25초 안에 끝까지 나왔습니다.

4. 가입한 사람 승인

다른 사람이 가입하면 관리자 패널의 사용자 목록에 보류 중으로 올라옵니다. 그 글자를 누르면 편집 창이 열립니다. 역할을 사용자로 바꾸고 저장하면 바로 쓸 수 있습니다.

노트북 모델 붙이기

Mac mini 모델은 꼼꼼하지만 답을 1초에 6토큰쯤 씁니다. 짧게 빨리 묻고 싶을 때도 있어서, 노트북의 Gemma 4 26B도 모델 목록에 넣었습니다. 2단계에서 잰 대로 이 모델은 노트북에서 1초에 20토큰 가까이 씁니다. 노트북에는 2단계에서 쓴 llama.cpp(Vulkan판)가 이미 있어서, 거기 딸린 서버 프로그램 llama-server를 띄웠습니다.

옵션 뜻
-ngl 99 모델 전부를 GPU에 올린다
-c 32768 -np 2 기억할 글 길이 32,768토큰을 두 몫으로 나눠, 두 사람에게 동시에 답한다
--reasoning-budget 0 답하기 전에 길게 생각하는 단계를 건너뛴다. 채팅에서 첫 글자가 빨리 나오게
--api-key-file 아래의 API 키를 이 파일에서 읽고, 맞는 요청에만 답한다
--no-webui llama.cpp에 딸린 채팅 화면은 끈다. 화면은 Open WebUI 하나로

노트북은 개인 파일이 있는 컴퓨터라, 늘 네트워크에 열어 둔 Mac mini보다 더 막았습니다.

  • API 키: 서버에 질문을 보낼 때 함께 보내야 하는 비밀 문자열입니다. 48자리 무작위 문자열을 만들어 노트북 서버와 Mac mini의 Open WebUI 두 곳에만 파일로 넣었고, 화면에는 한 번도 출력하지 않았습니다. 이 문자열이 없는 요청은 서버가 401(인증 실패)로 거절합니다.
  • 방화벽: 윈도우 방화벽에 8081번 포트를 Mac mini 한 대에만 여는 규칙을 넣었습니다. 다른 컴퓨터에서 보내면 연결부터 되지 않습니다.
  • 사람은 Open WebUI를 거쳐서: 사용자들은 노트북 서버에 직접 묻지 않습니다. API 키를 아는 건 Open WebUI뿐입니다.

늘 켜 두는 일은 윈도우 작업 스케줄러에 맡겼습니다. 노트북이 켜질 때 서버를 띄우고, 아무도 로그인하지 않아도 창 없이 뜹니다. 5단계의 launchd와 같은 역할입니다.

Open WebUI에는 노트북 서버의 주소와 API 키를 연결로 더하고, 모델 이름을 노트북 · Gemma 4 26B로 붙여 공개했습니다. 관리자 설정의 연결과 모델에서 할 수 있는 일입니다. 이번에는 Open WebUI의 설정 데이터베이스를 백업한 뒤 직접 고치고 다시 띄웠습니다.

쓰는 법

함께 쓸 사람에게는 이 단락만 보내면 됩니다.

  1. 가입: 브라우저에서 안내받은 주소(http://192.168.x.x:3000)를 열고, 로그인 화면 아래 가입을 누릅니다. 이름, 이메일, 비밀번호를 넣습니다. 이메일은 아이디로만 쓰이니 메일을 받을 수 있는 주소가 아니어도 됩니다.
  2. 승인 기다리기: 「계정 활성화 대기」 화면이 나옵니다. 관리자에게 말한 뒤, 승인되면 다시 확인을 누릅니다.
  3. 모델 고르기: 위쪽 모델 이름을 눌러 고릅니다. 꼼꼼한 답이 필요하면 Mac mini · Qwen 3.8 27B, 빨리 받고 싶으면 노트북 · Gemma 4 26B입니다.
  4. 대화: 아래 칸에 질문을 쓰고 Enter를 누릅니다. 왼쪽의 연필 아이콘은 새 대화이고, 지난 대화는 왼쪽 목록에 남습니다.

알아 둘 것도 있습니다.

  • Mac mini 모델은 느립니다. 답은 1초에 6토큰 정도로 나옵니다. 긴 글을 붙여 넣으면 읽는 데만 오래 걸립니다(3천 토큰이면 50초 안팎). 노트북 모델은 1초에 18토큰 정도입니다.
  • Mac mini는 한 번에 한 질문만 읽습니다. 누가 긴 글을 보내고 있으면, 짧은 질문도 그게 다 읽힐 때까지 기다립니다.
  • 노트북이 꺼지거나 잠들면 목록에서 노트북 모델이 빠집니다.
  • 비밀번호는 다른 곳과 다르게 정하세요. 주소가 http라서 네트워크 안에서는 비밀번호가 암호화되지 않은 채로 오갑니다.
  • 관리자는 대화를 열어 볼 수 있습니다. Open WebUI의 기본값입니다. 막으려면 시작 스크립트에 ENABLE_ADMIN_CHAT_ACCESS=false를 넣습니다.
  • 대화 기록은 바깥 서비스가 아니라 Mac mini 안에만 저장됩니다.

붙이자마자 두 번 멈춘 서버

관리자 계정을 만들고 처음 질문을 보낸 지 1분 만에 답이 끊겼습니다. 화면에는 「generation thread died」가 나왔고, 그 뒤로는 어떤 질문에도 답이 오지 않았습니다. MLX 서버 기록에 원인이 있었습니다.

GPU 메모리가 모자라 답을 만드는 스레드가 죽은 것입니다. 24GB 가운데 모델이 15GB를 차지하고, 나머지에 세 가지가 겹쳤습니다.

  • 프롬프트 캐시: MLX 서버는 지난 질문을 다시 읽지 않으려고 기억해 둡니다. 기본값에는 크기 한도가 없습니다.
  • 동시 요청: Open WebUI는 답과 대화 제목을 동시에 요청합니다. 서버는 둘을 한꺼번에 읽습니다.
  • Open WebUI의 GPU 사용: Mac에서는 문서 검색용 작은 모델을 GPU(Metal)에 올립니다. 코드를 열어 보고 알았습니다. 같은 GPU 메모리를 MLX 서버와 나눠 쓴 셈입니다. 화면을 찍으려고 띄운 시험용 Open WebUI까지 한 벌 더 있었습니다.

처음에는 MLX 서버 쪽만 고쳤습니다. 캐시 한도를 2GB로 걸고, 질문을 한 번에 하나씩 읽게 했습니다. 그런데 5분 뒤 같은 오류로 또 멈췄습니다. 두 번째에는 아래처럼 고쳤고, 그 뒤로는 멈추지 않았습니다.

고친 곳 전 후
Open WebUI GPU에 모델을 올림 USE_SLIM_DOCKER=true로 CPU만 쓴다 (메모리 0.9GB에서 0.74GB)
MLX 프롬프트 캐시 한도 없음 --prompt-cache-bytes 1073741824 (1GB)
한 번에 읽는 질문 여러 개 --prompt-concurrency 1
한 번에 쓰는 답 여러 개 --decode-concurrency 2

고친 뒤 긴 질문(2,423토큰)과 짧은 질문(28토큰)을 동시에 보냈습니다. 둘 다 답이 왔고, 긴 질문은 48.3초, 짧은 질문은 39.8초 걸렸습니다. 짧은 질문이 오래 걸린 건 긴 질문이 다 읽힐 때까지 기다렸기 때문입니다. 한 번에 하나씩 읽게 한 대가입니다.

죽어도 다시 뜨지 않는 죽음

5단계의 launchd는 서버 프로그램이 꺼지면 다시 띄웁니다. 이번에는 프로그램은 살아 있고 그 안의 스레드만 죽었습니다. 그래서 launchd는 아무것도 하지 않았고, 서버는 살아 있는 채로 모든 질문에 실패했습니다. 직접 프로그램을 끝내자 launchd가 새 설정으로 4초 안에 다시 띄웠습니다. 이런 죽음을 알아채고 다시 띄우는 감시는 아직 없습니다.

다음 단계로

이제 같은 네트워크의 누구나 브라우저로 로컬 LLM과 대화할 수 있습니다. 다만 모델은 학습이 끝난 시점까지만 압니다. 연재는 다음 7단계에서 이 웹 UI에 웹 검색을 붙여, 최근 정보를 찾아 읽고 답하게 합니다. 그 밖에 남은 일은 셋입니다.

  • MLX 서버 막기: 이제 질문은 Open WebUI를 거쳐 들어오니, API 키 없이 네트워크에 열려 있는 MLX 서버를 바깥에서 막을 차례입니다. 연재 9단계 「여러 사람 대비」가 이 일입니다.
  • 노트북 대기 모드 확인: 노트북은 화면이 꺼지면 네트워크를 붙든 채 대기 모드로 들어갑니다. 그 상태에서도 노트북 서버가 답하는지 아직 보지 못했습니다.
  • 스레드만 죽는 경우 감시: 위 상자의 죽음을 알아채고 다시 띄우는 장치가 필요합니다.
