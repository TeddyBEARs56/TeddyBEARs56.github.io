웹 UI를 Ollama로

지난 연재 9단계부터 웹 UI는 게이트웨이를 거쳐 MLX 서버에 묻습니다. Open WebUI에는 Ollama를 바로 붙이는 연결이 따로 있습니다. 이번에는 그 연결을 켜고, 웹 UI가 Ollama에 무엇을 보내는지 중간에서 기록하면서 모델을 고르고, 바꾸고, 받고, 내려 봤습니다.

올린 날
2026-11-21
읽는 시간
약 8분

이번에 할 일

  1. 웹 UI에 Ollama를 붙인다. 관리자 설정의 Ollama 연결을 켠다.
  2. 웹 UI가 보내는 요청을 기록한다. 웹 UI와 Ollama 사이에, 요청을 그대로 넘기면서 적어 두는 작은 중계 프로그램을 둔다.
  3. 모델을 고르고, 바꾸고, 받고, 내린다. 관리자와 일반 사용자 양쪽에서 본다.

모두 Mac mini(24GB)에서 했습니다. Ollama 0.40.16은 7편에서 launchd에 맡긴 그대로입니다. 기억할 글 길이는 32,768토큰이고, 한 번에 모델 하나만 올리며, 쉬어도 모델을 내리지 않습니다. 웹 UI는 Open WebUI 0.13.3입니다.

화면을 누르는 대신, 웹 UI의 API를 관리자 API 키로 불렀습니다. 연결 설정, 모델 항목, 대화, 제목 만들기, 모델 받기와 내리기 모두 웹 UI가 제공하는 API입니다. 시험이 끝난 뒤 웹 UI 설정은 원래대로 돌려놓았습니다.

연결은 설정 두 개

Open WebUI의 연결은 두 종류입니다. OpenAI 형식 API 연결과 Ollama 연결입니다. 지난 연재 6단계에서는 OpenAI 형식 연결로 MLX 서버를 붙이고, Ollama 연결은 꺼 두었습니다(ENABLE_OLLAMA_API=false). 9단계에서 OpenAI 형식 연결의 주소를 게이트웨이로 바꿨습니다. 이번에는 Ollama 연결을 켜고 주소를 중계 프로그램으로 주었습니다. 관리자 설정의 연결 화면에서 하는 일과 같습니다.

11435번 포트가 중계 프로그램입니다. 받은 요청을 11434번의 Ollama에 그대로 넘기고, 요청 내용과 걸린 시간, Ollama가 마지막 줄에 알려 주는 토큰 수와 올리기 시간을 한 줄씩 적습니다. Mac mini 안에서 오는 요청만 받습니다.

관리자에게만 보였다

연결을 켜자 관리자의 모델 목록에 Ollama의 모델 15개가 모두 나왔습니다. 게이트웨이 모델 하나를 더해 16개입니다. 같은 때 일반 사용자 계정의 목록에는 게이트웨이 모델 하나뿐이었습니다. 시험용 일반 사용자를 잠시 만들어 확인했습니다.

누가 보인 모델
관리자 16개
일반 사용자 1개
일반 사용자, 항목 공개 뒤 2개

웹 UI는 모델마다 「모델 항목」을 따로 둡니다. 보이는 이름, 시스템 프롬프트, 매개변수, 누가 쓸 수 있는지를 담습니다. 항목이 없는 모델은 관리자에게만 보입니다(utils/models.py의 “only admins can see unconfigured models”). 지난 연재 6단계에서 Mac mini 모델의 접근을 공개로 바꾼 것과 같은 일입니다. Qwen3.8에 항목을 만들고 모든 사용자에게 읽기 권한을 주자, 일반 사용자에게도 보였고 대화도 됐습니다.

그래서 Ollama에 모델을 새로 받아도 사용자의 목록은 저절로 늘지 않습니다. 관리자가 쓸 모델을 골라 항목을 만들어 주면 됩니다. 거꾸로 관리자의 목록에는 시험하려고 받아 둔 국산 모델, 같은 모델의 다른 태그, 임베딩 모델까지 모두 섞여 나옵니다.

웹 UI가 Ollama에 보낸 것

한 일 경로 웹 UI가 붙인 값
그냥 대화 /api/chat 없음
생각 끈 대화 /api/chat think: false
글 길이 바꾼 대화 /api/chat num_ctx: 8192
제목 만들기 /api/chat num_predict: 1000
모델 받기 /api/pull insecure: true
모델 내리기 /api/generate keep_alive: 0
  • 그냥 대화에는 아무 값도 붙지 않았다. 기억할 글 길이와 쉬는 시간은 Ollama 서비스 설정(32,768토큰, 내리지 않음)을 따르고, 생각은 모델의 기본값을 따른다.
  • 대화 설정에서 고른 값은 Ollama의 값으로 바뀌어 갔다. 생각 끄기는 think: false, 기억할 글 길이는 options.num_ctx가 됐다.
  • 제목 만들기는 같은 모델로 한 번 더 묻는 요청이었다. 스트리밍 없이 답 길이만 1,000토큰으로 묶었다. 제목을 맡을 모델을 따로 정하지 않으면 대화하던 모델이 맡는다(utils/task.py).
  • 모델 내리기는 빈 질문이었다. 질문 없이 쉬는 시간을 0으로 보내면 Ollama가 모델을 내린다.

생각이 새로 켜졌다

Ollama에서 Qwen3.8은 생각하는 것이 기본입니다(4편). 지난 연재 4단계부터 MLX 서버는 대화 틀에 enable_thinking: false를 주어 생각을 꺼 두었습니다. 그러니 웹 UI를 Ollama로 바꾸면 생각이 새로 켜집니다. 첫 대화에서 Qwen3.8은 546자를 생각한 뒤 두 문장으로 답했습니다. 34.9초 가운데 모델 올리기가 9.0초, 올린 직후 질문 읽기가 8.9초였습니다. 모델이 올라 있는 상태에서 생각을 끄고 같은 질문을 하자 5.1초였습니다.

제목 만들기도 생각했습니다. 아래는 모델이 올라 있는 상태에서 같은 대화로 제목을 두 번씩 만든 것입니다.

제목 만들기 생각 쓴 토큰 걸린 시간
항목 없음 1 514자 152 17.3초
항목 없음 2 469자 133 9.1초
생각 끔 1 0자 11 1.2초
생각 끔 2 0자 11 1.1초

첫 번째 17.3초에는 제목을 만들라는 긴 지시문(356토큰)을 처음 읽는 5.8초가 들어 있습니다. 두 번째부터는 앞에서 읽은 것을 다시 써서 0.2초 안팎이었습니다. 그래서 생각을 켜고 끈 차이는 9.1초와 1.2초로 보는 것이 맞습니다.

모델 항목의 매개변수에 think: false를 넣으면, 그 모델로 가는 요청에 모두 붙습니다. 대화뿐 아니라 제목 만들기에도 붙었습니다. 제목은 세 번 「Ollama 설명」이었고, 생각을 끈 두 번째만 「Ollama Introduction」으로 영어였습니다.

모델을 바꾸면 기다렸다

7편의 서비스는 한 번에 모델 하나만 올립니다. 다른 모델을 고르면 앞의 모델을 내리고 새로 올립니다. 아래 「첫 조각」은 생각이든 답이든 스트리밍으로 처음 받은 조각까지의 시간입니다.

바꾼 것 올리기 첫 조각
Qwen3.8 → Gemma 4 6.6초 7.8초
Gemma 4 → Qwen3.8 8.5초 12.0초
Qwen3.8 → Gemma 4 GGUF 11.3초 11.9초
Gemma 4 GGUF → Qwen3.8 8.3초 13.3초

Qwen3.8과 Gemma 4는 Mac mini에서 Ollama가 고르는 기본 태그(MLX 엔진)이고, Gemma 4 GGUF는 5편의 gemma4:26b-a4b-it-mtp-q4_K_M입니다. 여러 사람이 서로 다른 모델을 고르면, 고를 때마다 이만큼 기다리게 됩니다.

글 길이를 바꾸면 GGUF는 다시 올라갔다

대화 설정에서 기억할 글 길이를 8,192로 바꿔 보냈습니다.

모델 기억할 글 길이 올리기 Ollama가 보고한 길이
Gemma 4 GGUF, 올라 있음 기본 0초 32,768
Gemma 4 GGUF 8,192 9.0초 8,192
Gemma 4 GGUF 다시 기본 10.6초 32,768
Qwen3.8 MLX, 올라 있음 8,192 0초 32,768

llama.cpp 엔진은 모델을 올릴 때 기억할 글 길이만큼 메모리를 잡아 둡니다(6편). Ollama는 요청의 실행기 설정이 올려 둔 것과 다르면 모델을 다시 올립니다. 8,192로 바꿀 때 한 번, 기본으로 돌아올 때 또 한 번 올렸습니다. MLX 엔진 모델은 이 비교에서 빠져 있어서(server/sched.go의 needsReload, !loaded.IsMLX()) 다시 올리지 않았고, 보고한 길이도 32,768 그대로였습니다.

그러니 누군가 대화 설정에서 길이를 바꾸면, GGUF 모델은 그 사람과 다른 사람이 번갈아 물을 때마다 다시 올라갈 것으로 보입니다. 두 사람이 번갈아 묻는 것은 시험하지 않았습니다. 웹 UI에는 사용자가 대화 매개변수를 바꿀 수 있는지 정하는 권한이 있습니다(USER_PERMISSIONS_CHAT_PARAMS, 기본은 켬). 이번에는 시험하지 않았습니다.

받기와 내리기

모델 받기, 내리기, 지우기는 관리자만 할 수 있습니다(routers/ollama.py의 get_admin_user). 웹 UI에서 bge-m3(1.2GB)를 받는 데 33.5초 걸렸습니다. 9편에서 쓰려고 받은 임베딩 모델입니다.

  • 임베딩 모델도 대화 목록에 나왔다. 고르고 물으면 바로 오류였다("bge-m3:latest" does not support chat).
  • 내리기는 바로 됐다. 내린 뒤 Ollama의 모델 목록(/api/ps)은 비었고, 다음 대화에서 모델을 다시 올리느라 첫 조각이 13.6초에 왔다.
  • 받기에는 insecure: true가 늘 붙었다. 웹 UI가 받기 요청에 이 값을 덧붙인다(routers/ollama.py, {**form_data, 'insecure': True}). Ollama는 이 값이 있으면 레지스트리 주소를 https에서 http로 바꾸고, 다른 호스트로 넘기는 리디렉션도 막지 않는다(server/images.go). 원래는 자기 네트워크 안의 레지스트리에서 받을 때 쓰는 값이다.

실제로 http로 나가는지 보려고, 서로 다른 작은 임베딩 모델 두 개를 Ollama의 받기 API로 받으며 Ollama가 연 연결을 0.2초마다 적었습니다. 받기 전에는 100초씩 쉬어 앞의 연결이 남지 않게 했습니다. 레지스트리(registry.ollama.ai)의 주소는 104.18.17.170이었고, 다른 하나는 레지스트리가 아닌 주소였습니다.

받기 레지스트리 80번 레지스트리 443번 다른 주소 443번
insecure 없음 없음 있음 있음
insecure: true 있음 있음 있음

80번은 http, 443번은 https입니다. 값을 붙이지 않으면(ollama pull의 기본과 같습니다) https로만 오갔습니다. 웹 UI처럼 insecure: true를 붙이면 레지스트리에 http로도 요청했습니다. 레지스트리가 http 요청에 https 주소로 가라고 답해서(301) 받기는 성공했습니다. 하지만 Ollama는 레지스트리로 가는 요청을 모두 http로 바꿔 보내므로(server/images.go), 그 요청들은 먼저 암호화되지 않은 채 나갑니다.

바로 붙일까, 게이트웨이를 거칠까

바로 붙이기 게이트웨이 거치기
모델 받기·내리기 웹 UI에서 명령으로
게이트웨이 사용량 기록 없음 사람별로 남음

바로 붙이면 웹 UI에서 모델을 받고 내릴 수 있고, 모델 항목의 매개변수가 Ollama의 값으로 그대로 갑니다. 대신 웹 UI의 요청은 게이트웨이를 지나지 않습니다. 지난 연재 9단계에서 웹 UI는 게이트웨이 키 하나로 묻고, 묻는 사람의 이메일을 헤더로 실어 보내 사람별 사용량을 남기게 했습니다. 바로 붙이면 웹 UI 대화가 이 기록에 잡히지 않습니다. 게이트웨이를 거쳐 Ollama에 붙이는 길은 이번에 웹 UI로는 시험하지 않았습니다. 어느 쪽으로 할지는 10편에서 엔진과 함께 정합니다.

알게 된 것

  • 연결만 켜면 관리자에게만 보인다. 사용자에게 줄 모델은 모델 항목을 만들어 공개한다. 받아 둔 시험용 모델이 사용자 목록에 섞이지 않는 것은 장점이다.
  • 웹 UI는 Ollama에 거의 아무 값도 보내지 않는다. 기억할 글 길이와 쉬는 시간은 Ollama 서비스 설정을, 생각은 모델의 기본값을 따른다. Ollama 쪽 설정이 곧 웹 UI의 설정이다.
  • Qwen3.8은 생각이 새로 켜진다. MLX 서버에서는 꺼 두었던 것이다. 제목 만들기도 생각해서 9초쯤 걸렸다. 모델 항목에 think: false를 넣으면 대화와 제목 모두 꺼지고, 제목은 1초 남짓이 된다.
  • 모델을 바꾸면 8~13초 기다린다. 한 번에 하나만 올리기 때문이다. GGUF 모델은 기억할 글 길이를 바꿀 때도 다시 올라가므로, 길이는 모델 항목이나 서비스 설정에서 하나로 정해 두는 편이 낫다.
  • 웹 UI에서 받기는 편하지만 insecure: true가 붙는다. 레지스트리 요청이 http로 바뀐다. 받기는 Mac mini에서 ollama pull로 하는 편이 낫다.
