빌드 로그를 로컬 모델에게 대신 읽히면

클라우드 코딩 에이전트에게 실패한 빌드 로그를 통째로 넘기면, 그 로그는 대화에 남아 매번 다시 읽힙니다. 이 연재는 그런 단순하지만 토큰이 많이 드는 일을 집에 있는 로컬 모델에게 떼어 줄 수 있는지 봅니다. 첫 편은 빌드 로그를 세 줄로 줄여 원인을 짚게 하는 일입니다.

올린 날
2026-11-24
읽는 시간
약 6분

이 연재에서 할 일

Claude Code 같은 클라우드 코딩 에이전트는 똑똑하지만, 쓴 만큼 토큰이 듭니다. 그런데 에이전트가 하는 일 가운데에는 머리보다 손이 많이 드는 일이 있습니다. 긴 로그 읽기, 파일 찾기, 정해진 대로 몇 줄 고치기 같은 일입니다. 로컬 LLM 처음부터 11단계에서는 에이전트의 모델을 통째로 로컬 모델로 바꿨습니다. 이번에는 클라우드 에이전트는 그대로 두고, 옆에서 로컬 모델이 일부를 맡게 합니다.

네 가지 일을 시험했습니다.

편 일 문항
1편 실패한 빌드 로그 읽기 13
2편 도구로 코드 찾기 8
2편 지시서대로 몇 줄 고치기 6
3편 diff 먼저 훑기 8

모두 이 블로그의 저장소(Astro)에서 냈고, 정답은 시험 전에 적어 두었습니다.

시험 방법

모델

모델 기계
Qwen3.6 35B Mac mini
Qwen3.8 27B Mac mini
Gemma 4 26B 노트북
  • Qwen3.6 35B-A3B(UD-IQ4_XS GGUF)는 한 번에 일부(3B)만 계산하는 MoE 모델이라, Mac mini에서 답을 초당 28토큰쯤으로 빠르게 쓴다.
  • Qwen3.8 27B(Ollama의 qwen3.8:27b)는 Mac mini의 웹 UI가 늘 쓰는 모델이고, Ollama가 MLX 엔진으로 돌린다.
  • Gemma 4 26B-A4B(UD-IQ4_XS GGUF)는 웹 UI에서 고를 수 있는 노트북(Arc 140V 내장 GPU, 메모리 32GB) 모델이다. 이번에는 같은 파일을 노트북의 Ollama로 돌렸다.

세 모델 모두 Ollama 0.40.16에서 온도 0, 기억할 글 길이 32,768토큰으로 돌렸고 생각은 껐습니다. 문항마다 한 번씩 돌렸습니다.

빌드 로그 13개

이 블로그에 고장 여섯 가지를 하나씩 심고 npm run build를 돌려 로그를 받았습니다.

번호 심은 고장
1 국산 7편 글의 <Code>를 닫지 않음
2 국산 6편 머리말의 필수 칸을 뺌
3 국산 5편이 없는 컴포넌트를 import
4 series.ts 항목의 }를 뺌
5 posts.ts가 없는 칸을 읽음
6 버그 글의 분류 값에 오타

「국산」은 국산 LLM 견주기의 글입니다.

  • 짧은 로그 6개는 빌드 출력 그대로로, 760~1,570자다.
  • 긴 로그 6개는 이 블로그의 실제 GitHub Actions 배포 로그(321줄)에서 빌드 단계의 출력을 같은 고장 출력으로 바꿔 끼운 것이다. 클라우드 에이전트가 gh run view --log로 받는 모양으로, 222~240줄, 2만 3천 자쯤이고, 지시문까지 모델에게는 1만 1천~1만 3천 토큰이었다.
  • **실제 실패 하나(7번)**는 11-17에 이 블로그의 배포가 실패한 GitHub Actions 로그다. GitHub Pages 배포가 404로 실패했다.

모델에게는 이렇게 지시했습니다.

채점

모델 이름을 가리고 새 대화의 Claude가 채점했습니다. 답마다 파일, 원인, 고칠 것을 ○ △ ✕로 매기고, 파일과 원인이 ○이고 고칠 것이 ✕가 아니면 쓸 만한 답으로 셌습니다. 이 답만 보고 고치러 갈 수 있다는 뜻입니다. 채점 묶음에는 긴 로그의 가운데를 줄여 실었고, 긴 로그의 고장 출력은 같은 번호의 짧은 로그와 글자까지 같아 그것을 보고 매겼습니다.

11-23에 한 번 채점했는데, 채점 노트가 담긴 임시 폴더가 지워졌습니다. 그래서 11-24에 같은 답 묶음을 새로 쓴 기준표로 다시 채점했고, 아래는 두 번째 채점입니다. 첫 채점은 합계만 남아 있어 견줄 수 있는 것은 합계뿐인데, Qwen3.6의 긴 로그 쪽이 첫 채점보다 하나 적었습니다(5개 → 4개).

결과

모델 짧은 로그·7번 긴 로그 합
Qwen3.8 6/7 5/6 11
Qwen3.6 6/7 4/6 10
Gemma 4 6/7 4/6 10

열세 문항 가운데 열 문항은 세 모델이 모두 쓸 만하게 답했습니다. 1, 2, 3, 6번은 짧은 로그와 긴 로그 모두, 4번은 짧은 로그, 그리고 7번입니다. 셋 다 쓸 만하지 않았던 것은 5번의 두 로그, 갈린 것은 4번 긴 로그입니다.

  • 5번은 셋 다 못 맞혔다. 로그에는 빌드가 만든 파일(dist/.prerender/chunks/posts_….mjs:797)과 함수 이름 getBugs만 나오고, 원래 소스 파일 posts.ts와 잘못 읽은 칸 이름은 나오지 않는다. 세 모델 모두 「getBugs 안에서 undefined를 읽었다」는 증상 너머로 가지 못했고, 고칠 것으로는 「undefined가 아닌지 확인하라」, 「null 검사를 더하라」 같은 말을 내놓았다. getBugs 안에 검사를 넣으면 빌드는 지나가도 칸 이름이 틀린 채로 남고, 부르는 쪽에서 검사하거나 빌드 결과물을 고치라는 답은 빌드도 고치지 못한다. 파일 칸은 모델마다 달랐다. 짧은 로그에서 Qwen3.8은 「모름」을 썼지만 긴 로그에서는 없는 파일을 「추정」으로 댔고, Gemma 4는 반대로 긴 로그에서 「모름」을 썼다. Qwen3.6은 두 번 다 빌드 결과물의 경로를 댔다.
  • 4번 긴 로그는 Qwen3.8만 맞혔다. 같은 고장의 짧은 로그는 셋 다 맞혔다. 긴 로그에서 Qwen3.6은 「} 대신 ]를 썼다」며 「62행을 },나 }]로 고치라」고 했는데, },로 고치면 배열이 닫히지 않는다. Gemma 4는 「}나 쉼표가 빠졌다」고 흐리게 답했다. 둘 다 원인과 고칠 것이 △였다.

7번 실제 실패는 셋 다 「Pages가 켜져 있지 않다」고 읽었습니다. 채점 기준의 정답에 「Pages 설정에서 소스를 GitHub Actions로 골라 켠다」고 적어 두어, 그렇게 말한 Qwen3.8만 고칠 것이 ○, 「Pages를 켜라」에서 멈춘 둘은 △였습니다. 그런데 나중에 기록을 다시 보니, 그 무렵 이 블로그는 배포할 저장소를 옮기는 중이었고 실제로는 배포 방식을 바꿔 해결했습니다. 로그만으로는 알 수 없는 사정이라, 이 문항의 ○와 △ 차이는 크게 볼 것이 없습니다. 3번에서 Gemma 4도 「import 경로가 맞는지 확인하라」고만 해 고칠 것이 △였습니다. 이 답들은 모두 파일과 원인이 맞아 쓸 만한 답으로 셌습니다.

걸린 시간

모델 짧은 로그·7번 긴 로그
Qwen3.6 5.1초 36.4초
Gemma 4 7.5초 70.2초
Qwen3.8 14.1초 84.4초

문항 하나에 걸린 시간의 가운데 값입니다. 긴 로그는 거의 다 로그를 읽는 데 쓰는 시간입니다. Qwen3.8은 1번 긴 로그 하나에 214초가 걸려 따로 튀었습니다. 답은 세 모델 모두 가운데 값이 83~94토큰으로, 1만 1천~1만 3천 토큰짜리 요청을 백분의 일 아래로 줄였습니다. 토큰 수는 각 로컬 모델의 토크나이저로 센 것입니다.

클라우드 에이전트에 붙인다면

클라우드 에이전트가 긴 로그를 직접 읽으면, 그 로그는 대화에 남습니다. Claude Code 같은 에이전트는 요청마다 대화 전체를 다시 보내므로(앞부분은 캐시로 싸게 읽더라도), 로그 한 번이 여러 번 값을 치릅니다. 로컬 모델이 세 줄로 줄여 주고 에이전트는 세 줄과 로그 파일 경로만 받으면, 대화에 남는 것은 세 줄뿐입니다. 클라우드 모델의 토큰으로 얼마인지는 이번에 재지 않았습니다.

이번 결과로 보면 이렇게 나눌 수 있습니다.

  • 소스 파일 이름이 로그에 나오는 실패(1, 2, 3, 6번과 4번의 짧은 로그)는 세 줄로 충분했다. 4번 긴 로그는 셋 가운데 하나만 맞혔다.
  • 빌드 결과물 안에서 난 실행 오류(5번)는 로그만으로는 원래 소스를 알 수 없었다. 이럴 때 세 줄은 증상만 말하고, 틀린 고칠 것을 내놓을 수 있다. 「모름」이 나오거나 파일이 dist/를 가리키면 에이전트가 로그를 직접 열게 하는 편이 낫다. 채점에서는 「모름」과 엉뚱한 파일을 똑같이 틀린 것으로 셌지만, 실제로 쓸 때는 「모름」이 그 신호가 된다.
  • 속도로는 Qwen3.6이 맞다. 긴 로그를 36초에 읽어, Qwen3.8(84초)과 Gemma 4(70초)보다 빨랐다. 쓸 만한 답은 두 번째 채점에서 Qwen3.8이 하나 많았지만, 첫 채점에서는 11개씩 같았다.

실제로 에이전트에 붙여 토큰을 얼마나 아끼는지는 아직 재지 않았습니다.

알게 된 것

  • 빌드 로그 읽기는 로컬 모델에게 맡길 만하다. 세 모델 모두 13문항 가운데 10~11개가 쓸 만했다.
  • 로그가 길어지면 조금 흐려졌다. 같은 고장인데 긴 로그에서만 쓸 만하지 않은 답이 Qwen3.6과 Gemma 4에서 하나씩 나왔다.
  • 로그에 없는 것은 못 짚는다. 빌드 결과물 안의 실행 오류는 세 모델 모두 증상만 말했다. 세 줄을 쓰는 쪽에서는 「모름」이나 dist/ 경로를 로그를 직접 열라는 신호로 다루면 된다.
  • 이번 결과는 한 번씩 잰 것이다. 이 블로그의 고장 여섯 가지와 실제 실패 하나뿐이고, 채점도 Claude 하나가 했다.
