문서 검색을 Ollama로

지난 연재 10단계에서 웹 UI에 연재 글을 넣고, 질문과 가까운 글 조각을 찾아 붙여 묻게 했습니다. 조각을 찾는 임베딩 모델은 Mac mini의 CPU에서 llama.cpp 서버로 따로 띄웠습니다. 이번에는 그 임베딩 모델을 Ollama로 돌리고, 같은 질문을 다시 물었습니다.

올린 날
2026-11-22
읽는 시간
약 8분

이번에 할 일

  1. 같은 bge-m3를 두 엔진으로 견준다. 지금 쓰는 llama.cpp 서버와 Ollama에서 글 조각을 찾은 순위와 속도를 잰다.
  2. 웹 UI가 Ollama로 질문을 벡터로 바꾸게 한다. 지난 연재 10단계의 질문 20개를 다시 묻는다.
  3. 대화 모델과 함께 올린다. 임베딩 모델이 대화 모델을 밀어내는지 보고, 밀어내지 않게 한다.

모두 Mac mini(24GB)에서 했습니다. Ollama 0.40.16은 7편에서 launchd에 맡긴 서비스 그대로입니다. 기억할 글 길이는 32,768토큰이고, 한 번에 모델 하나만 올리며, 쉬어도 모델을 내리지 않습니다. 대화 모델 Qwen3.8 27B가 늘 올라가 있습니다. 웹 UI는 Open WebUI 0.13.3입니다.

글은 10단계에서 넣어 둔 지식 「로컬 LLM 연재」입니다. 지난 연재 글 10편이 조각 170개로 나뉘어 PostgreSQL(pgvector)에 들어 있습니다. 질문은 10단계의 20개입니다. 18개는 글에 답이 있고, 2개는 글에 없는 것을 묻습니다. 웹 UI는 질문마다 가까운 조각 3개를 붙입니다. 웹 UI의 API를 관리자 API 키로 불렀고, 시험이 끝난 뒤 웹 UI와 Ollama 서비스의 설정은 원래대로 돌려놓았습니다.

Ollama의 bge-m3는 8편에서 웹 UI로 받아 둔 공식 라이브러리 태그입니다. 압축하지 않은 F16이라 llama.cpp 서버의 Q8_0보다 두 배쯤 큽니다. 글 전체를 벡터 하나로 줄이는 방식은 둘 다 첫 토큰의 값을 씁니다. 10단계에서 llama.cpp에 --pooling cls로 준 것과 같고, Ollama는 파일에 적힌 값을 따릅니다.

Ollama 서비스는 기억할 글 길이를 32,768로 주는데, bge-m3는 8,192까지만 배운 모델입니다. Ollama는 로그에 경고를 남기고 8,192로 줄여 올렸습니다. 그래도 글 하나를 한 번에 받는 한도는 따로 있어서, 실제로는 llama.cpp 서버와 같은 2,048토큰이었습니다(아래 「긴 조각은 2,048토큰까지였다」).

찾은 조각은 거의 같았다

조각 170개와 질문 20개를 두 엔진으로 벡터로 바꾸고, 답이 든 조각이 몇 위에 드는지 셌습니다. 10단계와 같은 방식입니다. 「저장된 벡터」는 10단계에서 웹 UI가 llama.cpp 서버로 만들어 데이터베이스에 넣어 둔 것입니다.

질문 벡터 조각 벡터 1위 3위 안 10위 안
llama.cpp 저장된 벡터 13 17 17
Ollama Ollama 13 17 17
Ollama 저장된 벡터 13 17 17
  • 10단계와 같은 13, 17, 17이 다시 나왔다. 같은 글을 두 엔진이 만든 벡터는 코사인 유사도가 가장 낮은 것도 0.9986이었다. 1이면 완전히 같은 방향이다.
  • 엔진을 바꾸고 다시 색인하지 않아도 맞힌 개수는 같았다. Ollama로 만든 질문 벡터를 저장된 벡터에 대도 1위, 3위 안, 10위 안의 개수가 같았다. 붙는 조각 3개가 같은 질문은 20개 중 18개였다.
  • 놓친 하나도 같다. 2단계의 기억할 글 길이 질문이다. 답이 든 조각이 12위(Ollama 질문 벡터와 저장된 벡터로는 11위)여서 3개 안에 들지 않는다.

조각은 웹 UI와 같이 8개씩 묶어 보냈습니다. GPU에서 도는 Ollama가 3.6배 빨랐습니다. llama.cpp 서버는 Ollama의 Qwen이 올라 있는 동안, Ollama는 Qwen이 내려간 뒤(다음 절) 잰 값입니다. 10단계에서는 같은 llama.cpp 서버가 조각 전체에 33초, 질문 하나에 0.02초였습니다. 글을 넣을 때만 차이가 나고, 질문 하나를 벡터로 바꾸는 시간은 둘 다 사람이 느낄 수 없을 만큼 짧습니다.

임베딩을 부르자 Qwen이 내려갔다

Ollama에 처음 임베딩을 부르자 1.8초 뒤 답이 왔습니다. 그 사이 Ollama는 늘 올려 두던 Qwen3.8을 내리고 bge-m3를 올렸습니다. 7편의 서비스가 한 번에 모델 하나만 올리게(OLLAMA_MAX_LOADED_MODELS=1) 해 두었기 때문입니다. 쉬어도 내리지 않게 한 설정(OLLAMA_KEEP_ALIVE=-1)은 이 경우 모델을 지켜 주지 않았습니다.

웹 UI에서 문서를 붙여 물으면 질문을 먼저 벡터로 바꾸고, 그다음 대화 모델에 묻습니다. 그 순서대로 세 번 불러 봤습니다.

차례 임베딩 이어서 대화 그중 Qwen 올리기
1 1.1초 14.6초 8.4초
2 0.8초 13.2초 8.5초
3 0.9초 11.3초 9.6초

대화는 한 단어로 답하게 한 짧은 질문입니다. 모델이 올라가 있으면 1초 안쪽에 끝나는 질문인데, Qwen을 다시 올리느라 매번 8초 넘게 더 걸렸습니다. 임베딩 쪽도 bge-m3를 다시 올리느라 1초쯤 걸렸습니다.

웹 UI로 다시 물었다

관리자 설정의 문서 화면에서 하는 것처럼, 웹 UI의 임베딩 엔진을 Ollama로 바꿨습니다. 답하는 모델은 세 번 모두 웹 UI의 Ollama 연결로 부른 Qwen3.8이고, 생각은 껐습니다. 마지막 줄은 Ollama 서비스를 모델 두 개까지 올리게 바꾼 뒤입니다(다음 절).

질문 벡터 함께 올릴 모델 맞힘 답 하나 평균
llama.cpp 1개 17/18 29.4초
Ollama 1개 17/18 45.7초
Ollama 2개 17/18 29.3초
  • 맞힌 수는 셋 다 같다. 글에 없는 2개는 셋 다 없다고 답했다. 놓친 하나는 위의 2단계 질문이다. 세 번 모두 자료에 나와 있지 않아 정확히 답하기 어렵다고 하면서, 다른 조각에 있던 16,384를 함께 적었다. 10단계처럼 틀린 것으로 셌다. 숫자만 보는 기계 채점으로는 셋 다 18/18이다. 10단계에서도 Mac mini의 Qwen이 같은 질문을 같은 식으로 놓쳤다.
  • 붙은 조각도 거의 같다. 웹 UI가 붙인 조각 3개는 지금 설정과 견줘 20개 중 19개에서 같았다.
  • 모델 하나만 올리면 답이 평균 16초 늦다. 질문마다 Qwen이 내려갔다 올라왔다. 질문별로는 7~24초 늦었고, 가장 빠른 답도 29.7초였다.
  • 모델 둘을 올리면 llama.cpp 때와 같다. 질문 벡터를 어디서 만들든 답 시간은 Qwen이 글을 읽고 쓰는 시간이 거의 전부다.

둘을 함께 올리면

7편에서 만든 서비스 시작 스크립트의 한 줄을 바꾸고 서비스를 다시 띄웠습니다. 다시 띄워 Qwen을 올리기까지 10초 걸렸습니다.

이번에는 bge-m3가 Qwen 옆에 올라갔습니다. Ollama가 보고한 크기는 Qwen 17.2GiB, bge-m3 0.64GiB였고, Qwen을 내리지 않았습니다. 바로 이어 물은 짧은 대화는 0.5초에 답했습니다.

임베딩을 CPU에만 두는 길도 시험했습니다. 10단계의 llama.cpp 서버가 --device none으로 CPU만 쓰는 것과 같은 모양입니다. GPU에 쓸 층 수를 0으로 정한 태그를 하나 만들었습니다.

bge-m3 보고한 크기 질문 하나 조각 170개
GPU 0.64GiB 0.02초 11.8초
CPU 태그 1.16GiB 0.11~0.18초 75.7초

크기는 Ollama가 /api/ps로 보고한 값입니다. 적재 로그를 보면 GPU판도 모델의 520MiB는 CPU 쪽 메모리에 둡니다. GPU판의 시간은 Qwen이 내려간 뒤에, CPU 태그는 Qwen 옆에서 잰 값입니다.

CPU 태그도 Qwen 옆에 올라갔지만, 조각을 벡터로 바꾸는 데 llama.cpp 서버(42.4초)보다도 오래 걸렸습니다. 24GB Mac mini에서도 GPU 쪽에 함께 들어가므로 이번 시험에서는 GPU 그대로 두는 편이 나았습니다.

한 가지가 달라졌습니다. 모델 하나만 올릴 때는 20문항 동안 스왑이 1.2~1.5GiB에 머물렀습니다. 모델 둘을 올리자 1.4GiB에서 8.8GiB로 늘었습니다. 지금 설정(llama.cpp)으로 물을 때도 1.1GiB에서 8.0GiB로 늘었습니다. 7편에서 본 대로 Ollama의 MLX 엔진은 대화를 할수록 메모리를 더 씁니다. 임베딩에 밀려 다시 올라온 Qwen은 19.7GiB에서 17.2GiB가 됐습니다. 질문마다 Qwen을 다시 올리면 늘어난 메모리가 처음으로 돌아가서 스왑이 늘지 않은 것으로 보입니다.

긴 조각은 2,048토큰까지였다

bge-m3는 8,192토큰까지 배운 모델입니다. 10단계에서 llama.cpp 서버는 글 하나를 2,048토큰까지로 정했습니다(-c 8192 -np 4, 묶음도 -b 2048 -ub 2048). Ollama는 로그에 8,192로 올렸다고 적었지만, 긴 글을 넣어 보니 같은 2,048토큰에서 멈췄습니다. 연재 글 앞부분 4,000자와 9,000자를 넣었습니다. 표의 「자름」은 웹 UI가 보내는 truncate: true, 「안 자름」은 truncate: false입니다.

토큰 llama.cpp Ollama 자름 Ollama 안 자름
2,060 오류 앞 2,048만 오류
4,434 오류 앞 2,048만 오류
  • llama.cpp 서버는 오류를 낸다. 10단계에서 정한 대로다. 「input (2060 tokens) is too large to process. increase the physical batch size」라고 알려 준다.
  • Ollama는 묶음이 2,048이다. 임베딩 모델이면 한 번에 계산하는 묶음을 2,048로 둔다(llm/llama_server.go의 DefaultEmbeddingNumBatch). 기억할 글 길이 8,192보다 이 묶음에 먼저 걸린다.
  • 웹 UI가 보내는 값으로는 오류 없이 자른다. 웹 UI는 Ollama에 truncate: true를 실어 보낸다. 그러면 Ollama는 앞의 2,048토큰만 벡터로 바꾸고 아무 말 없이 답한다. truncate: false로 보내면 「the input length exceeds the context length」라며 거절한다. 넘은 것은 기억할 글 길이가 아니라 묶음인데, 오류 문구는 길이라고 말한다.

지금 웹 UI는 조각을 1,024자 안으로 자르므로 이 한도에 닿지 않습니다. 조각 크기를 크게 늘리면, Ollama로는 조각의 뒷부분이 검색에서 빠지고도 오류가 나지 않습니다.

웹 UI에서 바꾸려면

관리자 설정의 문서 화면에서 임베딩 모델 엔진을 Ollama로, 주소를 Ollama 서비스로, 모델을 bge-m3:latest로 고르면 됩니다. API로는 아래 값을 보냈고, 나머지 값은 그대로 두었습니다. 묶음 크기(8)는 10단계 값 그대로입니다.

바꾸면 웹 UI는 Ollama의 /api/embed에 글과 모델 이름, truncate: true만 보냅니다. 내리지 말라는 값은 보내지 않으므로, bge-m3는 Ollama 서비스 설정대로 계속 올라가 있습니다. 함께 올릴 모델 수를 2로 바꾸지 않으면 위처럼 질문마다 대화 모델이 내려갑니다.

시험이 끝난 뒤 웹 UI의 임베딩은 llama.cpp 서버로, Ollama 서비스는 모델 하나로 되돌렸습니다. CPU 태그는 Mac mini에 남겨 두었습니다. 어느 엔진을 늘 켜 둘지는 10편에서 정합니다.

알게 된 것

  • bge-m3는 Ollama로 돌려도 거의 같은 조각을 찾는다. 질문 18개의 순위가 llama.cpp와 같았고, 이미 넣어 둔 벡터에 섞어 써도 맞힌 개수가 같았다.
  • 글을 넣는 속도는 Ollama가 빠르다. GPU에서 돌아서 조각 170개에 11.8초, llama.cpp 서버(CPU만)는 42.4초였다.
  • 모델 하나만 올리는 서비스에서는 임베딩이 대화 모델을 내린다. 문서를 붙인 질문마다 Qwen을 다시 올려 답이 16초 늦었다. 쉬어도 내리지 않게 한 설정은 소용없었다.
  • 문서 검색까지 Ollama에 맡기려면 모델을 두 개까지 올리게 한다. 24GB Mac mini에서도 bge-m3는 GPU 쪽에 함께 들어갔고, 답 시간은 llama.cpp 때와 같았다. 대신 Qwen이 내려가지 않으니, 지금 설정에서처럼 대화마다 메모리가 쌓여 스왑이 는다.
  • 한 조각은 2,048토큰까지다. 두 엔진 모두 그렇다. llama.cpp는 오류를 내고, 웹 UI를 거친 Ollama는 말없이 자른다.
