로컬 모델의 세 줄 요약은 클라우드 토큰을 얼마나 아낄까

1편은 「실패한 빌드 로그를 클라우드 에이전트에게 통째로 넘기면 대화에 남아 매번 다시 읽힌다」는 생각에서 시작해, 로그를 로컬 모델에게 세 줄로 줄이게 했습니다. 그때는 아끼는 양을 재지 않았습니다. 이번에는 실제 클라우드 에이전트에 붙여 토큰을 셉니다.

올린 날
2026-11-27
읽는 시간
약 6분

이번에 할 일

1편에서 이 블로그에 고장 여섯 가지를 심고, 실제 배포 로그 모양의 긴 로그를 받아 로컬 모델에게 세 줄로 줄이게 했습니다. 3편을 마치며 남긴 숙제는 「토큰을 얼마나 아끼는지는 재지 않았다」였습니다.

이번에는 같은 고장 여섯 개를 클라우드 코딩 에이전트에게 실제로 고치게 합니다. 로그를 어떤 모양으로 건네느냐만 바꿔 가며, 에이전트가 쓴 토큰과 비용, 턴, 시간을 봅니다.

시험 방법

에이전트

  • Claude Code 2.1.326을 Mac mini에서 claude -p(대화 없이 한 번 실행)로 돌렸다. 모델은 Sonnet 5.5다.
  • 도구는 여섯 개로 묶었다. Bash, Read, Edit, Write, Glob, Grep만 쓰게 하고, MCP 서버와 사용자 설정은 읽지 않게 했다. 샌드박스를 켜고 네트워크는 막았다. 최대 40턴이다.
  • 비용은 Claude Code가 알려 주는 값이다. 실행이 끝나면 total_cost_usd로 API 정가로 셈한 값을 준다. 실제로는 구독으로 돌렸기 때문에 따로 낸 돈은 없다.

고장 여섯 개

1편과 같은 고장입니다.

번호 심은 고장
1 국산 7편 글의 <Code>를 닫지 않음
2 국산 6편 머리말의 필수 칸을 뺌
3 국산 5편이 없는 컴포넌트를 import
4 series.ts 항목의 }를 뺌
5 posts.ts가 없는 칸을 읽음
6 버그 글의 분류 값에 오타
  • 고장은 커밋해 두었다. 실제 배포 실패는 푸시한 커밋에서 나므로, 고장을 마지막 커밋으로 넣고 시작했다. 커밋하지 않은 채 두면 git diff에 답이 그대로 보인다.
  • 로그는 1편의 긴 로그다. 이 블로그의 실제 GitHub Actions 배포 로그에 고장 난 빌드 출력을 끼운 것으로, 2만 3천 자쯤이다.
  • 고장마다 다섯 조건을 두 번씩 돌렸다. 모두 60번이다. 두 번째 바퀴는 조건의 순서를 뒤집었다.

다섯 조건

조건 에이전트가 받는 것
로그 파일 작업 폴더의 ci.log
파일 + 요약 ci.log와 지시문에 붙인 세 줄 요약
붙여 넣기 지시문에 붙인 로그 전체
요약만 지시문에 붙인 세 줄 요약
없음 배포가 실패했다는 말뿐

세 줄 요약은 1편에서 Qwen3.6 35B가 같은 긴 로그로 쓴 답을 그대로 썼습니다. 여섯 개 가운데 둘은 틀린 요약입니다. 4번은 고칠 줄을 한 줄 늦게 짚었고, 5번은 원인을 빌드 결과물(dist/.prerender/…) 안에서 찾았습니다.

다른 조건도 첫 문장만 바꿨습니다. 요약을 붙일 때는 「로컬 모델이 읽고 세 줄로 줄인 결과입니다. 틀릴 수 있습니다」라고 밝혔습니다.

결과

조건 비용 턴 시간 고침
로그 파일 $0.064 7.4 12.2초 12/12
파일 + 요약 $0.060 6.8 11.5초 12/12
붙여 넣기 $0.104 5.0 9.8초 12/12
요약만 $0.049 5.3 10.1초 12/12
없음 $0.053 6.3 10.6초 12/12

12번의 평균입니다. 시간은 Claude Code를 띄워서 끝날 때까지입니다. 60번 모두 고장을 고쳤고 빌드가 통과했습니다. 고친 내용도 diff로 하나씩 봤습니다. 빠진 머리말 칸을 새로 쓴 2번을 빼면, 모두 고장을 심기 전과 똑같이 돌려놓았습니다.

로그를 파일로 주면 요약은 거의 쓸모없다

로그 파일만 받은 Claude Code는 로그를 통째로 읽지 않았습니다. 12번 모두 첫 행동이 grep -n -i -E "error|fail" ci.log처럼 오류 낱말이 든 줄을 찾는 것이었고, 그다음 그 주변 수십 줄만 열었습니다. 2만 3천 자 가운데 실제로 읽은 양은 2.6~7.3KB였습니다.

요약을 더해도 이 순서는 바뀌지 않았습니다. 요약을 받은 12번도 모두 첫 행동으로 로그를 grep했습니다. 그래서 비용은 $0.064에서 $0.060으로 6%, 턴은 0.6번 줄었을 뿐입니다.

1편은 「로그를 통째로 넘기면 대화에 남아 매번 다시 읽힌다」는 생각에서 출발했습니다. 파일로 건네면 그런 일이 애초에 일어나지 않았습니다.

아무것도 주지 않아도 고쳤다

「배포가 실패했다」는 말만 들은 Claude Code는 12번 모두 첫 명령에 npm run build 2>&1 | tail -40을 넣었습니다. 로그가 없으니 실패를 직접 다시 만든 것입니다. 이 블로그의 빌드는 몇 초면 끝나고, 마지막 40줄에 오류가 그대로 나옵니다. 그 출력은 0.8~1.8KB로, 로그 파일에서 골라 읽은 2.6~7.3KB보다 짧았습니다.

그래서 아무것도 주지 않은 쪽이 로그 파일을 준 쪽보다 쌌습니다($0.064 → $0.053). 고장 여섯 개 가운데 다섯 개에서 그랬습니다. 로그 파일을 받으면 그것을 찾아 읽는 턴이 더 들었습니다.

붙여 넣으면 비싸다

로그를 지시문에 붙여 넣으면 사정이 달랐습니다. 비용이 파일로 줄 때보다 61%, 아무것도 주지 않을 때보다 94% 더 들었습니다($0.104). 턴은 오히려 5.0번으로 가장 적었습니다. 로그를 찾아 읽거나 빌드를 다시 돌리는 턴이 없기 때문입니다.

비싼 까닭은 프롬프트 캐시에 있습니다. Claude Code는 매 턴 앞선 대화를 다시 보내고, 앞에서 본 부분은 캐시에서 싸게 읽습니다. 처음 보는 부분은 캐시에 새로 올리는데, 캐시에서 읽을 때보다 훨씬 비쌉니다. 붙여 넣은 로그는 실행마다 처음 보는 글이라, 캐시에 새로 올린 토큰이 1만 1천에서 2만 2천으로 늘었습니다.

「요약만」이 싼 것은 로그를 뺀 덕이다

로그 대신 세 줄 요약을 붙이면 비용이 $0.049로, 붙여 넣을 때의 절반 아래가 됐습니다. 처음에는 이것을 요약의 몫으로 읽었습니다.

아무것도 주지 않은 결과를 놓고 보니 그렇지 않았습니다. 요약만 붙인 쪽($0.049)과 아무것도 주지 않은 쪽($0.053)의 차이는 8%이고, 고장 여섯 개 가운데 네 개에서만 요약 쪽이 쌌습니다. 고장마다 두 번씩 돌린 시험에서 이 정도는 흔들릴 수 있는 크기입니다. 절반 넘게 줄어든 몫의 대부분은 요약을 더해서가 아니라 로그를 빼서 생겼습니다.

로그 파일에 요약을 더한 쪽도 6%였으니, 세 줄 요약이 스스로 아낀 몫은 어느 쪽으로 견줘도 6~8%입니다.

틀린 요약에 속지 않았다

틀린 요약을 받은 4번과 5번도 모두 고쳤습니다. 5번에서 Claude Code는 이렇게 적었습니다.

요약만 받은 12번 가운데 11번은 첫 명령에 npm run build를 넣어 직접 돌렸습니다. 요약을 그대로 믿지 않고 오류를 스스로 다시 만들어 본 것입니다. 이 블로그처럼 빌드가 몇 초면 끝나는 저장소에서는, 요약이 틀려도 에이전트가 원인을 찾아갔습니다.

처음 두 번의 숫자는 틀렸다

본 시험 앞에 고장 1번으로 두 조건을 한 번씩 돌렸습니다. 요약을 더한 쪽이 턴 17 → 7, 비용 $0.122 → $0.061로 절반이 줄었습니다. 그대로 믿을 뻔했습니다.

들여다보니 두 가지가 잘못돼 있었습니다.

  • 샌드박스가 빌드를 막았다. 작업 폴더의 node_modules가 폴더 밖을 가리키는 링크라, 빌드가 그 안의 캐시를 지우려다 EPERM으로 멈췄다. 로그 파일만 받은 쪽은 이것을 피해 보려고 10턴쯤을 더 썼다. 절반 차이는 이 헛수고였다.
  • 고장이 커밋되지 않았다. 에이전트가 git diff를 보면 고장이 바로 보였다.

링크를 실제 폴더로 바꾸고 고장을 커밋한 뒤 다시 쟀고, 위 결과는 모두 고친 뒤의 것입니다. 한 번 잰 차이가 클수록, 그 차이가 어디서 왔는지 실행 기록을 먼저 열어 봐야 했습니다.

걸린 시간

Claude Code가 고장 하나를 고치는 데는 조건마다 평균 10~12초쯤이 걸렸습니다. 1편에서 Qwen3.6이 긴 로그 하나를 세 줄로 줄이는 데는 36초쯤 걸렸습니다. 요약을 기다리는 시간이 고치는 시간보다 세 배 깁니다.

6~8%를 아끼려고 고장마다 36초쯤을 더 기다리는 셈입니다. 로그를 붙여 넣던 습관을 버리는 것만으로 비용이 절반이 되고, 기다릴 것도 없습니다.

알게 된 것

  • 세 줄 요약이 아끼는 몫은 6~8%였다. 로그 파일에 더해도, 아무것도 없는 데 더해도 그 정도였다.
  • 로그가 없어도 고쳤다. 빌드를 직접 돌려 실패를 다시 만들었고, 로그 파일을 받을 때보다 쌌다.
  • 로그를 준다면 파일로 건네면 된다. Claude Code는 오류 줄 주변만 골라 읽었다.
  • 붙여 넣은 로그는 비싸다. 아무것도 주지 않을 때의 두 배 가까이 들었다. 처음 보는 글이 그만큼 프롬프트 캐시에 새로 올라가기 때문이다.
  • 틀린 요약은 에이전트가 걸렀다. 요약을 믿기 전에 로그를 보거나 빌드를 직접 돌려, 틀린 요약 둘에도 모두 고쳤다.
  • 첫 숫자를 의심해야 했다. 처음 잰 절반 차이는 샌드박스가 막은 빌드와 커밋하지 않은 고장 때문이었다. 「요약만」의 절반 차이도 기준 조건을 놓고 보니 요약이 아니라 로그를 뺀 덕이었다.
  • 이번 결과는 작은 고장 여섯 개다. 고장마다 한두 파일, 몇 줄이었고, 빌드가 몇 초면 끝나는 저장소였다. 빌드가 몇십 분 걸리거나 다시 만들 수 없는 실패라면 로그와 요약의 값이 달라질 수 있다.
