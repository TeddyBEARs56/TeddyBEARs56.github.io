커밋 메시지 맡겨 보기

지금까지 만든 서버를 실제 일에 붙여 봅니다. 고른 일은 커밋 메시지입니다. 매일 여러 번 하는 작은 일이고, Claude가 그동안 써 온 메시지가 있어서 견주기 쉽습니다. 실전에 바로 쓰기 전에, Claude와 함께 만든 지난 커밋 7개로 시험했습니다.

올린 날
2026-11-16
읽는 시간
약 9분

이번에 할 일

  1. 초안 도구를 만든다. 올려 둔 변경을 Mac mini의 로컬 모델에 보내고, 커밋 메시지 초안을 받는다.
  2. 지난 커밋으로 견준다. Claude와 함께 만든 커밋 7개를 골라, 로컬 모델의 초안과 Claude가 그때 쓴 메시지를 나란히 놓는다.
  3. 지시문을 고쳐 한 번 더 견준다. 첫 결과에서 모자란 점을 지시문으로 메운다.

왜 커밋 메시지인가

커밋 메시지는 변경을 저장소에 기록할 때 붙이는 설명입니다. 요즘 제 커밋 메시지는 대부분 Claude가 씁니다. 코드를 함께 고친 Claude Code가 커밋까지 하고, 메시지 끝에 Co-Authored-By: Claude 꼬리말을 붙입니다.

로컬 모델에 맡겨 보기 좋은 이유는 셋입니다.

  • 자주 하는 작은 일입니다. 하루에도 여러 번 합니다. 답이 짧아서, 느린 Mac mini 모델도 기다릴 만합니다.
  • 견줄 답이 이미 있습니다. 지난 커밋마다 Claude가 쓴 메시지가 남아 있습니다.
  • 코드가 내 네트워크 밖으로 나가지 않습니다. 변경 내용은 Mac mini에만 갑니다.

도구

~/llm-lab/commit_msg.py 파일 하나입니다. 4단계에서 띄운 OpenAI 호환 API로 Mac mini에 묻습니다. 필요한 패키지를 파일 맨 위에 적어 두어서, uv run이 알아서 설치하고 실행합니다.

초안은 표준 출력으로, 걸린 시간과 토큰 수는 표준 오류로 나갑니다. 그래서 세 번째 줄처럼 초안만 커밋에 넘길 수 있습니다.

모델에게는 세 가지를 보냅니다. diff는 무엇이 어떻게 바뀌었는지 줄 단위로 보여 주는 변경 기록입니다.

최근 커밋 제목을 함께 보내는 것은 저장소마다 다른 형식을 따르게 하려는 것입니다. fix(범위): …처럼 쓰는 저장소도 있고, 이 블로그처럼 「글:」로 시작하는 저장소도 있습니다.

API를 부르는 부분은 4단계와 같습니다. temperature는 답이 얼마나 들쭉날쭉한지 정하는 값입니다. 낮게 두어 같은 diff에는 비슷한 답이 나오게 했습니다.

SYSTEM이 지시문입니다. 시스템 프롬프트라고도 하며, 모든 질문 앞에 붙습니다. 처음 지시문은 이랬습니다.

같은 질문을 Claude에게도 보내는 --claude 옵션도 만들어 두었습니다. claude -p로 부르는데, 처음에는 연결해 둔 MCP와 스킬 목록이 함께 실려 요금이 다섯 배 넘게 나왔습니다. 그 이야기는 Cybug 글에 따로 적었습니다. 이번 시험에서는 Claude를 새로 부르지 않고, Claude가 그때 실제로 쓴 메시지와 견줬습니다.

먼저 이 블로그 저장소의 마지막 커밋으로 도구가 도는지 봤습니다.

내용은 거의 맞혔습니다. 이 저장소의 커밋은 「글:」로 시작하는데, 그 머리말만 빠뜨렸습니다. 28초 가운데 23초는 diff를 읽는 데 썼습니다.

시험 방법

실전에 바로 쓰기 전에 지난 커밋으로 시험하기로 했습니다.

  • 제가 개발하는 비공개 저장소 다섯 곳에서, 최근 60일 동안 Claude와 함께 만든 제 커밋 513개를 모았습니다.
  • 그중 diff가 2,000~15,000자인 것에서 저장소와 종류가 고르게 7개를 골랐습니다. 너무 작으면 볼 것이 없고, 너무 크면 diff가 잘립니다.
  • 7개마다 --rev로 로컬 초안을 받아, Claude가 그때 쓴 메시지와 견줬습니다. 모델은 Mac mini의 Qwen 3.8 27B입니다.
# 어떤 커밋 크기
1 링크 서버: 새 앱의 앱 링크 설정 파일 3개, 20줄
2 API 중계 서버: 로그인 쿠키를 연장하는 조건 파일 2개, 13줄
3 모바일 앱: 알림 읽음 표시가 늦게 온 응답에 덮이던 버그 파일 1개, 23줄
4 모바일 앱: 아이폰 애플 로그인을 시스템 창으로 파일 7개, 87줄
5 백엔드: 이름을 바꾸면 다른 표에 복사해 둔 이름도 함께 바꾸기 파일 3개, 36줄
6 관리자 웹: 화면에서 내부 코드 숨기기. PR 하나를 합친 커밋 파일 5개, 61줄
7 백엔드: DB 칸 형식을 엔티티에 맞추기 파일 3개, 9줄

조건이 같지는 않습니다

Claude는 작업하던 대화를 보면서 메시지를 썼습니다. 무엇을 왜 고쳤는지, 어떤 시험을 돌렸는지 다 아는 상태였습니다. 로컬 모델은 diff와 최근 커밋 제목만 봅니다. 그래서 세 가지로 나눠 봤습니다. 무엇을 바꿨는지 맞혔나, 저장소의 형식을 따랐나, 왜 바꿨는지 썼나.

공개하지 않는 코드라서 메시지를 그대로 싣지 않습니다. 아래 예시는 이름과 값을 바꾼 것입니다. 무엇을 쓰고 무엇을 빠뜨렸는지는 실제 결과 그대로입니다.

  • 제목은 7개 모두 쓸 만했다. 무엇을 바꿨는지 맞혔고, 저장소의 형식을 지켰고, 지어낸 내용이 없었다. 1번은 최근 커밋 가운데 같은 일을 다른 앱에 한 커밋이 있어서, 그 제목의 틀을 그대로 따랐다.
  • 본문은 2개뿐이었다. Claude는 7개 모두 본문을 썼고, 이유와 그대로 둔 것, 확인한 시험 같은 내용을 담았다. 로컬이 쓴 본문 2개는 바뀐 곳을 늘어놓은 것이었다.
  • diff에 있는 변경을 빠뜨리기도 했다. 6번은 네 곳 중 한 곳을, 7번은 시험 설정 한 줄을 빠뜨렸다.
  • 이유가 코드 주석에 있어도 쓰기도 하고 안 쓰기도 했다. 2번은 주석의 이유를 제목에 썼고, 5번은 쓰지 않았다. 7번은 어노테이션을 「주석」이라고 옮겼다.
  • 시간은 25~62초, 평균 41초였다. 첫 글자가 나오기까지 19~54초로, 대부분 diff를 읽는 시간이다.

지시문 고치기

두 줄을 바꿨습니다. 이유를 한두 문장 쓰게 하고, 바뀐 곳 목록은 네 줄까지 늘렸습니다.

본문까지 쓰면 300토큰에서 잘릴 수 있어서, 답의 상한도 500토큰으로 올렸습니다. 나머지 규칙은 그대로 두었습니다. 그래야 결과가 달라졌을 때 이 두 줄의 효과라고 말할 수 있습니다.

# 나아진 것 아직 Claude와 다른 것
1 바뀐 곳 3줄. Claude 본문의 3줄과 거의 같다 앱이 없을 때 어떻게 되는지는 없다
2 이유 문장. 주석에 있던 이슈 번호까지 그대로 둔 조건은 없다
3 제목에 증상을, 목록에 고친 방법 4줄을 썼다 주석에 있던 이슈 번호는 쓰지 않았다
4 「서버가 값을 줄 때만 시스템 창」, 「다른 플랫폼은 그대로」, 취소 안내 다른 저장소의 PR 번호. diff에 없었다
5 이유 문장 첫 번째에 있던 바뀐 곳 목록이 빠졌다
6 이유 문장 네 줄까지 쓸 수 있었는데 세 줄만 쓰고, 같은 한 곳을 또 빠뜨렸다. 목록이 화면 대신 컴포넌트 이름 위주다
7 이유가 Claude와 거의 같다. 빠졌던 한 줄도 썼다 실제 DB로 돌려 본 시험 결과. diff 밖이다

새로 들어간 내용은 하나하나 diff에서 찾아 확인했습니다. 지어낸 내용은 없었습니다. 4번의 취소 안내도 diff에 있던 문구입니다.

7번을 나란히 놓으면 이렇습니다.

시간은 한 개에 6초쯤 늘었습니다. 쓰는 양이 늘었기 때문입니다. 첫 예시만 88초가 걸렸는데, 그때 웹 UI에서 들어온 17,009토큰짜리 요청이 먼저 처리되고 있었습니다. Mac mini는 질문을 한 번에 하나씩 읽습니다. 평균 47초는 이 예시를 뺀 값이고, 넣으면 53초입니다.

알게 된 것

  • 제목 초안으로는 쓸 만하다. 두 번 모두 7개 다 무엇을 바꿨는지 맞혔고, 저장소의 형식을 지켰다.
  • 본문은 지시문에 따라 크게 달라진다. 두 줄을 더하자 본문을 쓴 초안이 2개에서 7개가 됐다.
  • 이유는 거의 다 코드 주석에서 왔다. 이 저장소들에서는 Claude가 코드를 쓰면서 이유와 날짜를 주석에 남겨 두었다. 그래서 로컬 모델도 이유를 쓸 수 있었다. 주석이 없는 코드라면 이만큼 쓰지 못할 것이다.
  • 작업하면서 알게 된 맥락은 여전히 Claude만 쓴다. 실제 DB로 돌린 시험, 다른 저장소의 PR, 따로 고친 데이터가 그렇다.
  • 고르지는 않다. 이유를 얻은 대신 목록을 잃은 예(5번), 같은 곳을 두 번 빠뜨린 예(6번)가 있었다. 주석에 있던 이슈 번호를 한 번은 쓰고(2번) 한 번은 뺐다(3번). 저장소는 「~한다」로 쓰는데, 두 번은 「해결합니다」로 썼다.

그래서 아직 실전에 바로 붙이지는 않았습니다. 쓴다면 로컬 초안을 받아 diff 밖의 맥락을 직접 채우는 방식이 될 것입니다. 바꾼 지시문은 이제 도구의 기본값입니다.

코드는 어디로 가나

  • 로컬 초안을 받을 때 diff는 같은 네트워크의 Mac mini에만 갑니다.
  • Mac mini 서버의 기록 파일에는 요청 시각, 보낸 컴퓨터의 주소, 읽은 토큰 수 같은 숫자만 남습니다. 보낸 diff 속 낱말로 기록을 찾아봤는데 나오지 않았습니다.
  • --claude를 붙이면 같은 질문이 Claude로 갑니다. 평소 Claude Code를 쓸 때와 같습니다.
  • 이번 시험에서는 Claude를 새로 부르지 않았습니다. 그때 남은 메시지와 견줬을 뿐입니다.

다음 단계로

이번에는 웹 UI가 아닌 다른 프로그램도 같은 Mac mini에 물었습니다. 그러자 웹 UI의 긴 요청 뒤에서 기다리는 일이 생겼습니다. 9단계에서는 여러 사람이 같은 서버를 쓸 때를 대비합니다. 사람마다 API 키를 나눠 주고, 누가 얼마나 쓰는지 보고, 요청을 한곳에서 받아 나눠 주는 게이트웨이를 둡니다.
