바꿀까, 말까

아홉 편에 걸쳐 지난 연재의 일을 Ollama로 다시 해 봤습니다. 마지막으로 하루 동안 할 법한 일을 두 엔진에 똑같이 시키고, 앞 편의 결과와 함께 놓고 Mac mini에 늘 켜 둘 엔진을 정했습니다.

올린 날
2026-11-23
읽는 시간
약 7분

이번에 할 일

  1. 하루 쓰기를 두 엔진에 똑같이 시킨다. 짧은 대화, 문서를 붙인 질문, 긴 글 요약을 차례로 보내고 메모리를 본다.
  2. 게이트웨이를 거쳐도 생각을 끌 수 있는지 본다. 8편에서 미뤄 둔 것이다.
  3. 앞 편의 결과와 함께 놓고 정한다. 정한 대로 Mac mini를 바꾼다.

시험 방법

Mac mini(24GB)에서 했습니다. 두 엔진 모두 Qwen3.8 27B를 쓰되, 각자 늘 쓰던 그대로 띄웠습니다.

MLX 서버 Ollama
프로그램 mlx-lm Ollama 0.40.16
압축 4비트 NVFP4 중심
설정 지난 연재 데몬 7편 서비스
생각 끄기 시작 옵션 요청마다

Ollama에는 요청마다 reasoning_effort: none을 실어 생각을 껐습니다. 두 파일은 압축 방식이 다릅니다. MLX 서버는 지난 연재부터 쓰던 mlx-community의 4비트 파일이고, Ollama가 Mac에 내려주는 qwen3.8:27b는 NVFP4 중심의 MLX 형식입니다. Ollama 쪽은 모델에 붙은 MTP 머리로 초안을 씁니다(5편). MLX 서버는 지난 연재 데몬과 같은 옵션으로 띄우되, 포트만 8090으로 바꿔 손으로 띄웠습니다. 그동안 Ollama는 켜 둔 채 모델만 내렸습니다.

두 엔진에 OpenAI 형식 API로 같은 요청을 같은 순서로 보냈습니다. 온도는 0입니다.

  1. 첫 답: Ollama는 모델을 내린 상태에서, MLX 서버는 막 띄운 뒤에 짧은 인사.
  2. 짧은 대화 5개: 200토큰까지, 스트리밍으로 받아 첫 글자까지 시간을 잰다.
  3. 문서 질문 20개: 지난 연재 10단계의 질문에, 웹 UI가 고르는 조각 3개와 지시문을 붙인다. 400토큰까지.
  4. 긴 글 요약 6번: 연재 글을 9,000자씩 잘라 세 문장으로 요약하게 한다. 7편과 같은 방식이다.
  5. 짧은 질문 3개.

단계마다 엔진 프로세스의 메모리(top), 스왑, 남은 메모리를 적었습니다. top이 보여 주는 G는 GiB입니다.

  • 첫 답은 MLX 서버가 빨랐다. 서버가 답하기 시작한 뒤 5.4초, 띄운 때부터는 9초쯤이었다. Ollama는 내려 둔 모델을 올리며 11.7초 만에 답했다. 늘 켜 둔 MLX 서버는 재부팅 뒤에만 이 시간이 들고, 30분 쉬면 내리는 Ollama는 쉴 때마다 든다.
  • 문서 질문은 Ollama가 빨랐다. 답을 평균 98토큰 쓰고도 26.4초에 끝냈다. MLX 서버는 79토큰에 33.7초였다. 답 길이가 비슷한 문항끼리 견줘도 5~7초 빨라서, 차이는 대부분 질문을 읽는 쪽에서 났다. 질문마다 같은 지시문이 앞에 붙으니 Ollama가 앞서 읽은 부분을 다시 쓴 것으로 보이지만, 확인하지는 못했다. 답을 쓰는 속도도 Ollama가 빨랐다. 5편에서 본 대로 Mac용 기본 태그가 초안을 쓴다.
  • 글을 많이 읽는 일은 비슷했다. 4,500~5,000토큰 안팎을 읽는 긴 요약은 두 엔진 모두 1분 반에서 2분 가까이 걸렸다. 6번 중 5번은 MLX 서버가 2~6초 빨랐다.
  • 맞힌 수도 같았다. 두 엔진 모두 글에 없는 2개는 없다고 답했다. 놓친 하나는 9편과 같은 2단계의 기억할 글 길이 질문이다. 자료에 나와 있지 않다고 하면서 16,384를 함께 적어, 10단계처럼 틀린 것으로 셌다. 숫자만 보는 기계 채점으로는 둘 다 18/18이다.

MLX 서버는 하루 쓰기 내내 15~17GiB에 머물렀고, 스왑을 늘리지 않았습니다. 지난 연재에서 저장해 두는 캐시를 1GB로 묶으려 한 서버입니다. 13단계에서 본 대로 이 한도는 저장할 때는 걸리지 않아, 이번에도 캐시가 2.42GB까지 찼습니다. 긴 코딩 대화에서는 메모리가 모자라 멈췄고, 그 가운데 다섯 번은 새 요청을 시작하며 대화 기억이 잠깐 두 벌이 되는 순간이었습니다(13단계).

Ollama는 짧은 대화부터 늘기 시작해, 13번째 문서 질문에서 25GiB에 이른 뒤로는 더 늘지 않았습니다. 7편에서 본 대로 Ollama의 MLX 엔진은 지난 대화를 8GiB까지 남겨 둡니다. 모델 17GiB(Ollama는 18GB로 보고합니다)에 8GiB를 더하면 25GiB로, 이번에 멈춘 크기와 맞습니다. 그동안 스왑은 1.3GiB에서 10.5GiB까지 늘었습니다. 스왑이 늘어난 뒤에도 긴 요약의 시간은 MLX 서버와 비슷했습니다.

게이트웨이를 거쳐도 생각을 끌 수 있다

8편에서 웹 UI를 Ollama에 바로 붙이면 게이트웨이의 사람별 사용량 기록이 빠진다고 적었습니다. 게이트웨이를 거칠 때 남는 걱정은 생각 끄기였습니다. Ollama는 Qwen3.8의 생각을 기본으로 켜고, 웹 UI는 Ollama 연결로 물을 때 생각에 대해 아무 값도 보내지 않았습니다(8편).

Ollama의 OpenAI 형식 API는 reasoning_effort가 none이면 생각을 끕니다(openai/openai.go의 ThinkingFromReasoningEffort). 게이트웨이 LiteLLM이 이 값을 넘기는지, 실제 게이트웨이와 같은 LiteLLM 설정(drop_params)으로 시험용 게이트웨이를 하나 더 띄워 물었습니다. 질문은 「한 문장으로 답해 주세요. 하늘은 왜 파란가요?」입니다.

요청 생각 걸린 시간
Ollama에 바로, 값 없음 471자 12.2초
Ollama에 바로, none 없음 2.9초
게이트웨이, 값 없음 471자 11.0초
게이트웨이, 묻는 쪽이 none 없음 2.8초
게이트웨이 항목에 none 없음 2.5초
항목에 none, 묻는 쪽이 high 471자 10.8초
  • 게이트웨이는 reasoning_effort를 그대로 넘긴다. 백엔드가 받지 않는 값을 버리게 해 둔 설정(drop_params)에서도 이 값은 버리지 않았다.
  • 게이트웨이의 모델 항목에 넣어 두면 기본으로 꺼진다. 웹 UI처럼 아무 값도 보내지 않는 프로그램도 생각 없이 답을 받는다.
  • 묻는 쪽이 원하면 다시 켤 수 있다. 묻는 쪽이 보낸 reasoning_effort가 항목의 값보다 앞섰다. Claude Code의 생각 요청으로는 이번에 시험하지 않았다.

코딩 과제는 같은 Mac mini에서 같은 모델 네 개로 돌린 2편의 결과입니다. MLX 서버는 메모리가 모자라 멈췄습니다. 네 모델 가운데 둘은 Ollama에서 llama.cpp 엔진으로 돌았고, 늘 켜 둘 Qwen3.8만 보면 MLX 서버가 6번 중 1번, Ollama가 6번 중 0번 멈췄습니다. 메모리는 이번 하루 쓰기의 값이고, 2편의 코딩 과제에서 Ollama의 Qwen3.8은 28GB까지 갔습니다. 모델 받기는 지난 연재 11단계와 8편에서 가져왔습니다.

MLX 서버의 문제는 멈추는 것이었습니다. 멈추면 프로세스가 살아 있어서 launchd가 다시 띄우지 않고, 모든 요청에 404를 돌려줍니다. 이를 잡는 감시는 지난 연재에서 시험용으로만 만들었습니다. Ollama의 문제는 메모리였습니다. 멈추지는 않았지만 스왑이 1.3GiB에서 10.5GiB까지 늘었습니다. 모델을 내리면 이것이 비워집니다. 이번에도 Ollama의 모델을 내리자 스왑이 7.1GiB에서 1.4GiB로 줄었습니다. 다만 Ollama도 살아 있는 채 멈춘 실행기는 알아채지 못하고(7편), 그런 감시는 아직 없습니다.

정한 것

Mac mini에 늘 켜 둘 엔진을 Ollama로 바꿨습니다.

  • 게이트웨이 뒤에 둔다. 웹 UI와 프로그램은 지금처럼 게이트웨이에 묻고, 게이트웨이가 Ollama에 넘긴다. API 키, 한도, 사람별 사용량 기록이 그대로 남는다.
  • 생각은 게이트웨이 항목에서 끈다. 생각을 원하는 쪽은 reasoning_effort를 실어 보내면 켤 수 있다.
  • 30분 쉬면 모델을 내린다. 쌓인 지난 대화가 그때 비워진다. 쉬지 않고 쓰는 동안에는 그대로다. 내린 뒤 첫 답은 12초쯤 걸린다. 7편에서 미뤄 둔 선택이다. 바꾼 뒤 마지막 요청(09:52:54)에서 꼭 30분 뒤인 10:22:54에 Qwen이 내려갔고, 남은 메모리가 92%가 됐다.
  • 임베딩은 llama.cpp 서버 그대로 둔다. 9편에서 본 대로, 모델 하나만 올리는 Ollama에 임베딩까지 맡기면 질문마다 Qwen이 내려간다.
  • 노트북은 바꾸지 않았다. 노트북의 llama-server는 그대로다.

게이트웨이의 Qwen 항목은 모델 이름과 주소 두 줄이 바뀌고, 생각 끄기 한 줄이 늘었습니다. auto와 코딩 에이전트용 agent-qwen3.8-27b 항목도 같은 식으로 Ollama로 돌렸습니다.

Ollama 서비스 스크립트(7편)에서는 세 가지를 바꿨습니다. 모델을 내리지 않던 OLLAMA_KEEP_ALIVE=-1을 30m으로 바꿨고, 시작할 때 모델을 미리 올리는 요청에서 keep_alive: -1을 뺐고, GPU 메모리 한도(22GiB)가 잡힐 때까지 기다리게 했습니다. Ollama는 시작할 때 본 GPU 메모리로 모델 크기를 가늠하므로(discover/runner.go), 재부팅 직후 한도가 늘기 전에 뜨면 안 되기 때문입니다. 지난 연재의 MLX 서버도 같은 이유로 기다렸습니다. 함께 올릴 모델 수는 1 그대로입니다.

바꾼 뒤 웹 UI의 API로 Qwen3.8에게 두 번 물었습니다. 웹 UI, 게이트웨이, Ollama를 거쳐 Ollama 기록으로 4.8초와 2.7초에 답했고, 생각은 없었습니다. MLX 서버 데몬은 재부팅 때 다시 뜨지 않도록 뺐습니다. GPU 메모리 한도를 정하는 데몬은 Ollama가 기다리므로 남겼습니다.

알게 된 것

  • 같은 Qwen3.8도 문서 질문은 Ollama가 빨리 답했다. 평균 33.7초가 26.4초가 됐다. 답 쓰기는 초안 덕에 빨랐고, 차이의 더 큰 몫은 같은 지시문을 다시 읽지 않은 데서 난 것으로 보인다. 글을 많이 읽는 일은 비슷했다.
  • 대신 Ollama는 메모리를 더 쓴다. 지난 대화를 8GiB까지 남겨 두어, 24GB Mac mini에서 스왑이 1.3GiB에서 10.5GiB까지 늘었다. 쉬면 내리게 해서 쌓인 것을 비운다. 쓰는 동안에는 그대로다.
  • 게이트웨이를 거쳐도 생각을 끌 수 있다. 모델 항목에 reasoning_effort: none을 넣으면 된다. 그래서 웹 UI를 Ollama에 바로 붙이지 않고 게이트웨이 뒤에 두었다.
  • 엔진을 고르는 기준은 멈추느냐였다. 메모리는 쉬는 동안 비우게 할 수 있었지만, 긴 대화에서 메모리가 모자라 멈출 수 있는 MLX 서버는 감시 장치 없이 늘 켜 두기 어려웠다.
