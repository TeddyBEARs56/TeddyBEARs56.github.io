Mac mini가 도중에 멈춘 이유

1편의 시험에서 Mac mini는 결과물을 다 만들어 놓고도 서버가 멈춰 통과하지 못한 일이 다섯 번 있었습니다. 이번 글은 왜 멈췄는지, 노트북은 왜 멈추지 않았는지, 멈춰도 시험이 이어지게 어떻게 했는지 적습니다.

올린 날
2026-11-18
읽는 시간
약 8분

이번에 할 일

  1. 멈춘 모습을 본다. Claude Code, 게이트웨이, MLX 서버가 각각 무엇을 남겼는지 본다.
  2. 언제 멈췄는지 모은다. 여섯 번이 어떤 모델, 어떤 순간이었는지 맞춰 본다.
  3. 메모리를 셈한다. 모델 파일 말고 무엇이 메모리를 차지했는지 본다.
  4. 노트북과 견준다. 같은 시험에서 llama.cpp는 왜 멈추지 않았는지 본다.
  5. 멈춰도 이어지게 한다. 멈춘 서버를 알아채고 다시 켜는 장치를 단다.

멈춘 모습

Claude Code는 하던 일을 멈추고 이렇게만 답했습니다.

모델 이름이 틀린 것처럼 보이지만, 원인은 Mac mini의 MLX 서버에 있었습니다.

  • GPU 메모리가 모자라 답을 만드는 스레드가 죽었다. MLX는 Apple의 GPU 프레임워크 Metal로 계산하는데, Metal이 메모리를 내주지 못했다.
  • 프로세스는 살아 있다. 그래서 서버를 늘 켜 두는 launchd는 다시 띄우지 않는다. 지난 연재 6단계에서 웹 UI를 붙였을 때와 같은 증상이고, Cybug에 따로 적었다.
  • 그 뒤로는 답을 달라는 요청에 모두 404를 돌려준다. 다시 켜기 전까지는 다른 모델, 다른 과제도 모두 실패한다. 게이트웨이는 실패가 이어지면 그 모델을 잠시 쉬게 해서 429를 돌려주기도 했다.

언제 멈췄나

시험 동안 Mac mini의 MLX 서버는 여섯 번 멈췄습니다. 앞의 둘은 17일 밤, 나머지 넷은 18일 새벽입니다.

시각 모델과 과제 대화 길이
21:10 Qwen3.8 더하기 7,279토큰
21:42 GLM 더하기 28,066토큰
03:14 Devstral 고치기 27,711토큰
03:29 Devstral 더하기 28,134토큰
03:45 GLM 더하기 21,141토큰
04:24 Qwen3.6 고치기 18,385토큰

대화 길이는 그 시도에서 서버가 답한 요청 가운데 가장 긴 것입니다. 멈춘 요청은 이보다 조금 더 길었습니다.

  • 다섯 번은 대화가 1만 8천~2만 8천 토큰으로 길어진 뒤였다. 결과물을 이미 맞게 만들어 놓고, 빌드하거나 결과를 다시 확인하던 중이었다.
  • 첫 번째는 첫 요청에서 멈췄다. 바로 앞의 고치기가 45분 한도에 걸린 지 2분여 뒤였다. 시험 프로그램은 고치기를 끊었지만, 서버는 그 요청의 답을 아직 만들고 있었을 수 있다. MLX 서버는 답 두 개를 함께 만들도록 설정해 두었다.
  • 다섯 번은 새 요청을 막 받았을 때였다. 서버 기록에 남은 오류 추적으로 가렸다. GLM 두 번과 Qwen3.6은 새 요청의 첫 2,048토큰 묶음을 계산하다가, Devstral 두 번은 새 글 220·290토큰을 다 계산하고 답 쓰기로 넘어가는 순간에 멈췄다. Qwen3.8만 답을 쓰는 도중에 멈췄다. 왜 그 순간인지는 아래 「새 요청을 시작할 때 두 벌이 된다」에 적었다.

메모리 셈

Mac mini는 24GB 통합 메모리 가운데 GPU가 22GB까지 쓰게 해 두었습니다(지난 연재 2단계). 모델 파일이 14~19GB이므로, 남는 자리는 3~8GB입니다. 이 자리에 대화 기억이 들어갑니다.

모델은 앞의 글을 매번 다시 계산하지 않으려고, 토큰마다 계산한 결과를 남겨 둡니다. 이것이 KV 캐시이고, 여기서는 대화 기억이라고 부릅니다. 대화가 길어질수록 커지고, 크기는 모델 구조에 따라 크게 다릅니다. 모델 설정 파일로 계산하면 이렇습니다.

모델 파일 1천 토큰마다 3만 토큰이면
Qwen3.6 35B-A3B 19GB 20MB 0.6GB
Qwen3.8 27B 15GB 66MB 2.0GB
GLM-4.7-Flash 16GB 54MB 1.6GB
Devstral Small 2 24B 14GB 164MB 4.9GB

파일 크기와 GPU 몫은 1GB를 1,024MB로, 대화 기억과 서버 기록은 1GB를 10억 바이트로 센 값입니다.

  • Devstral은 40층 모두 대화 기억을 쌓는다. 2만 7,711토큰에서 계산값은 4.5GB이고, 서버 기록에 남은 캐시 크기도 4.50~4.55GB였다.
  • Qwen3.6과 Qwen3.8은 층 네 개 가운데 하나만 쌓는다. 나머지 층은 대화가 길어져도 크기가 그대로인 상태만 둔다.
  • GLM은 압축해서 쌓는다. 2만 8,066토큰에서 계산값은 1.5GB이고, 서버 기록은 1.53GB였다.

Qwen3.6은 대화 기억이 작은 대신 파일이 19GB라 남는 자리가 3GB뿐입니다. Devstral은 남는 자리가 8GB로 넓은 편이지만, 대화 기억이 가장 빨리 늘어납니다.

새 요청을 시작할 때 두 벌이 된다

Claude Code는 답을 받을 때마다 지금까지의 대화를 통째로 다시 보냅니다(2편). MLX 서버는 요청을 마칠 때 그 대화의 기억을 저장해 두었다가, 다음 요청이 같은 대화로 시작하면 꺼내 이어 씁니다. 꺼낼 때 부르는 copy.deepcopy는 메모리를 새로 잡지 않습니다. 작은 배열로 시험해 보니 복사 직후에는 늘어난 메모리가 없었고, 값을 쓸 때 비로소 늘었습니다.

복사는 그 뒤에 일어납니다. 여러 요청을 함께 처리하는 자리로 옮길 때, 새 글을 붙이려고 자리를 늘릴 때(256토큰 단위), 다 계산하고 답 쓰기로 넘어갈 때마다 대화 기억 전체를 새 자리에 씁니다. 다 쓰기 전까지는 원래 것과 새것이 함께 있어서, 새 요청을 시작할 때 같은 대화의 기억이 잠깐 두 벌이 됩니다. 다섯 번이 멈춘 자리가 바로 이 단계였습니다.

Devstral이라면 모델 14GB에 4.5GB짜리 기억 두 벌을 더해 GPU 몫 22GB를 넘습니다. GLM과 Qwen3.6은 이 셈만으로는 22GB에 닿지 않습니다. 계산하는 동안 잠깐 쓰는 메모리 같은 다른 몫이 함께 쌓였을 텐데, 그것은 재지 않았습니다.

1GB 상한은 저장할 때는 걸리지 않았다

지난 연재 6단계에서 MLX 서버에 --prompt-cache-bytes 1073741824를 줘서, 저장해 두는 캐시를 1GB로 묶었다고 생각했습니다. 코드를 읽어 보니 이 값은 여러 요청을 묶어 처리하는 경로에서, 새 요청을 받을 때 저장된 캐시를 줄이는 데만 쓰입니다. 요청을 마치고 캐시를 저장할 때는 쓰이지 않습니다.

서버는 새 요청을 받을 때마다 그때 저장돼 있는 캐시 크기를 기록에 남깁니다. 시험 시간 동안 남은 979번 가운데 744번이 1GiB(기록 단위로 1.07GB)를 넘었고, 가장 클 때 4.62GB였습니다. 그 4.62GB가 찍힌 지 7초 뒤인 03:29:32에 Devstral이 멈췄습니다.

노트북은 왜 멈추지 않았나

노트북의 llama.cpp 서버는 36번 돌리는 동안 한 번도 멈추지 않았습니다.

  • 처음에 자리를 잡아 둔다. llama.cpp는 서버를 띄울 때 모델과 -c 49152만큼의 대화 기억 자리를 잡는다. 서버 기록에도 n_slots = 1, n_ctx_slot = 49152가 남았다. 대화가 길어져도 이 자리 안에서 쓴다.
  • 모자라면 대개 초반에 드러난다. 자리를 처음에 잡으니, 모자라면 띄우는 단계나 첫 계산에서 드러나기 쉽다. 다만 늘 그렇지는 않다. 지난 연재 2단계에서는 한도를 넘자 첫 계산에서 device lost로 멈췄고, 한도 가까이 잡으면 페이지 파일로 밀려 느려졌다. 시험 프로그램은 뜨지 않으면 대화 기억을 8비트로 줄여 다시 띄우게 해 두었는데, 네 모델 모두 처음 설정으로 떴다.
  • 지난 대화의 사본은 따로 두고 한도를 지킨다. llama.cpp도 지난 대화를 저장해 두지만, 잡아 둔 자리 밖에 두고 한도가 차면 오래된 것부터 지웠다. 기록에는 「removing oldest entry (size = 4124.053 MiB)」처럼 지운 크기가 남았다.

노트북은 GPU가 24GB까지 빌려 쓸 수 있고, llama.cpp는 그 안에서 모델과 4만 9천 토큰어치 대화 기억을 처음에 잡아 둡니다. 다른 차이도 있었습니다. 노트북은 한 번에 요청 하나만 받았고(-np 1), Mac mini는 답 두 개를 함께 만들 수 있게 해 두었습니다(--decode-concurrency 2). 그래서 노트북이 멈추지 않은 까닭을 하나로 단정하지는 못합니다. 분명한 것은 Mac mini의 MLX가 필요할 때마다 더 잡다가 모자란 순간에 멈췄다는 것입니다.

멈춰도 이어지게

멈춘 서버는 스스로 알리지 않습니다. 프로세스가 살아 있어 launchd도 모릅니다. /health에 물으면 503으로 답하지만, 이번에는 그것을 보는 장치가 없었습니다. 1회차의 시험 스크립트는 모델을 바꿀 때만 서버를 확인했습니다. 다행히 1회차의 두 번은 모두 그 모델의 마지막 과제에서 멈춰서, 다음 모델로 넘어갈 때 다시 켜졌습니다.

2회차부터는 과제마다 확인하게 바꿨습니다.

  • 과제마다 한 토큰을 먼저 묻는다. 200이 아니면 MLX 서버를 끈다. 서버는 launchd가 메모리 설정 그대로 다시 띄운다.
  • 45분 한도에 걸린 과제 뒤에도 다시 켠다. 끊긴 요청이 다음 과제까지 이어지지 않게 한다. 1회차의 첫 번째 멈춤이 이런 경우였을 수 있다.
  • 멈춘 일을 따로 적는다. 서버 기록에 「generation thread died」가 새로 생기면 시험 기록에도 남긴다. 1편의 표에서 「서버 멈춤」을 모델 실력과 따로 센 근거다. 1회차의 두 번은 서버 기록에서 직접 맞췄다.

2회차의 네 번은 모두 이렇게 넘어갔습니다. 알아챈 뒤 다시 켜져 200이 오기까지 26~31초가 걸렸고, 다음 과제는 처음부터 돌았습니다.

다음에 해 볼 것

이번에는 해 보지 않았고, 결과도 모릅니다.

  • Ollama로 같은 시험을 돌린다. 다음 시험은 Ollama로 정했다. 모델을 올리고 내리는 일과 기억할 글 길이를 Ollama가 맡을 때도 Mac mini가 도중에 멈추는지 본다.
  • 모델마다 기억할 글 길이를 따로 정한다. Devstral처럼 대화 기억이 빨리 느는 모델은 길이를 줄인다. 대신 2편에서처럼 요약이 잦아진다.
  • 늘 켜 둔 서버에도 감시를 단다. /health가 503이면 다시 켜게 한다.
  • 최신 mlx-lm을 확인한다. 대화 기억을 옮기고 늘리는 방식이 바뀌었는지 본다.

알게 된 것

  • 모델 파일 크기만 보고 고르면 안 된다. 대화 기억이 토큰 1천 개마다 Qwen3.6은 20MB, Devstral은 164MB로 8배 차이였다.
  • MLX 서버는 대화 기억을 필요할 때마다 늘리고, 새 요청을 시작할 때 새 자리로 옮긴다. 긴 대화에서는 그 순간 같은 기억이 잠깐 두 벌이 된다.
  • 1GB 상한은 기대만큼 듣지 않았다. 저장된 캐시가 4.62GB까지 찼다.
  • llama.cpp는 처음에 자리를 잡아 둬서, 이번 시험에서는 도중에 멈추지 않았다.
  • 멈춘 서버는 스스로 알리지 않는다. 과제마다 확인하고 다시 켜는 장치가 있어야 밤새 돌릴 수 있었다.

연재를 마치며

세 편에 걸쳐 Claude Code의 모델을 로컬 모델로 바꿔 봤습니다. 24GB Mac mini에서도 Qwen3.6 35B-A3B는 과제 세 개를 6분 만에 끝냈습니다(1편). 그렇게 하려면 주소, 형식, 기억할 글 길이, 대화 형식을 하나씩 맞춰야 했습니다(2편). 긴 대화에서는 메모리가 먼저 모자랐습니다(3편). 다음에는 Mac mini에서 Ollama로 같은 시험을 돌려 보려고 합니다.
