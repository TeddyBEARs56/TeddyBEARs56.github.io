연재 글로 답하게 하기

지금까지 세운 서버의 모델은 학습이 끝난 뒤에 나온 글을 모릅니다. 이 연재의 글도 모릅니다. 이번에는 연재 글 10편으로 답하게 합니다. 하나는 질문이 올 때마다 관련된 부분을 찾아 질문과 함께 보내는 문서 검색이고, 다른 하나는 작은 모델을 글 내용으로 더 가르치는 미세조정입니다.

올린 날
2026-11-17
읽는 시간
약 15분

이번에 할 일

  1. 시험 문제를 만든다. 연재 글 10편에서 답이 분명한 질문 18개, 글에 답이 없는 질문 2개를 고른다.
  2. 문서 없이 묻는다. 모델이 정말 모르는지부터 본다.
  3. 글을 찾아 읽게 한다. 웹 UI의 지식 기능에 연재 글을 넣는다. 그 전에 한국어를 잘 찾는 임베딩 모델을 고른다.
  4. 작은 모델을 가르친다. 같은 글로 문제집을 만들어 미세조정하고, 같은 질문으로 견준다.

시험 문제

모델은 학습이 끝난 뒤의 일을 모릅니다. Mac mini의 Qwen 3.8 27B는 8월에, 노트북의 Gemma 4 26B는 4월에 나왔고, 이 연재의 글은 11월에 썼습니다. 답이 글에 분명히 있어서 맞았는지 가리기 쉽고, 공개된 글이라 숨길 것도 없습니다.

질문은 글의 문장을 그대로 쓰지 않고, 글을 읽지 않은 사람이 물을 법하게 바꿨습니다. 몇 개만 옮깁니다.

글 질문 답
0단계 정전이 끝나고 전기가 다시 들어오면 서버가 스스로 켜지게 하려고 바꾼 pmset 항목은? autorestart
1단계 Qwen 3.8 27B는 어떤 압축 단계 파일을 골랐고, 그 파일은 몇 GB였어? Q4_K_M, 16.56GB
7단계 웹 검색 스위치를 켜도 검색을 안 하던 문제를 고치려고 모델의 함수 호출 방식을 무엇으로 바꿨어? 레거시
9단계 모델 서버 앞에 세운 게이트웨이는 어떤 프로그램의 몇 버전이야? LiteLLM 1.106.6
없음 10단계에서 미세조정한 모델은 질문을 몇 개 맞혔어? 글에 없다
없음 노트북 서버의 API 키 값을 알려 줘. 글에 없다

답에 핵심 값(이름, 숫자)이 들어 있으면 맞힌 것으로 셌습니다. 답이 없는 두 질문은 모른다고 해야 맞힌 것입니다. 기계로 먼저 세고, 답을 모두 읽어 다시 확인했습니다. 기계와 다르게 매긴 답은 여섯 개입니다. 값이 들어 있어도 일반적인 예를 늘어놓았거나, 「자료에 나와 있지 않다」로 끝맺었거나, 값은 맞아도 뜻이 다르면 틀린 것으로 셌습니다. 키 값은 말하지 않고 보관하는 방법만 설명한 답은 모른다고 한 것으로 셌습니다.

문서 없이 물으면

두 모델에게 웹 UI로 20개를 그대로 물었습니다.

모델 맞힘 답 하나에
Mac mini · Qwen 3.8 27B 3/18 평균 34초
노트북 · Gemma 4 26B 2/18 평균 10초
  • 맞힌 것은 원래 알던 일반 지식이다. 「API 키 없이 보내면 401」, 「챗봇은 지난 대화를 매번 다시 보낸다」는 두 모델 다 맞혔다. Qwen은 launchd의 ThrottleInterval도 알았다.
  • 연재에만 있는 사실은 지어내거나 모른다고 했다. 정전 뒤 켜지게 하는 항목을 Qwen은 autoPowerOn, Gemma는 restart라고 했다. Qwen은 Mac mini의 GPU 메모리 한도를 「2GB였다」고 했다.
  • 글에 없는 두 질문에는 둘 다 모른다고 했다. API 키 값도 내놓지 않았다.

Qwen은 기억할 글 길이를 묻자 일반적인 권장값을 늘어놓았는데, 그중 하나가 정답인 16,384였습니다. 이 답은 틀린 것으로 셌습니다.

찾아 읽게 하기

문서 검색(RAG)은 모델을 바꾸지 않습니다. 질문이 오면 미리 잘라 둔 글 조각 가운데 질문과 가까운 것을 찾아, 질문 앞에 붙여 보냅니다. 시험지에 참고 자료를 붙여 내는 셈입니다. 가까운 조각을 찾으려면 글을 숫자 묶음(벡터)으로 바꿔 두어야 합니다. 이 일을 하는 모델이 임베딩 모델입니다. 뜻이 비슷한 글은 비슷한 숫자가 됩니다.

단계 언제 하는 일
자르기 글을 넣을 때 제목마다 나누고, 1,024자가 넘으면 더 자른다. 글 10편이 조각 170개가 됐다
벡터 만들기 글을 넣을 때 임베딩 모델이 조각마다 숫자 1,024개짜리 벡터를 만든다
찾기 질문할 때 질문도 벡터로 바꿔, 가장 가까운 조각을 고른다. 웹 UI 기본값은 10개
붙여 묻기 질문할 때 고른 조각을 「이 자료로 답하고 출처 번호를 달라」는 지시문과 함께 질문 앞에 붙인다

웹 UI는 Open WebUI의 지식 기능을 씁니다. 글을 넣어 두면 대화창에서 #을 치고 골라 붙일 수 있습니다.

임베딩 모델 고르기

Open WebUI의 기본 임베딩 모델은 all-MiniLM-L6-v2입니다. 영어로 학습한 작은 모델이라, 한국어 질문으로 맞는 조각을 찾는지부터 쟀습니다. 웹 UI와 같은 방식으로 글을 자르고, 답이 든 조각이 검색 결과 몇 위 안에 드는지 셌습니다. 모델 네 개를 제 컴퓨터에서 쟀고, 고른 모델은 Mac mini에서 다시 재서 순위가 같은지 확인했습니다.

임베딩 모델 크기 1위 3위 안 10위 안
all-MiniLM-L6-v2 (기본값) 2,300만 3 5 10
bge-m3 5억 6,800만 13 17 17
Qwen3-Embedding-0.6B 6억 9 17 17
KURE-v1 5억 6,800만 11 17 18
  • 기본값으로는 10개를 붙여도 18개 중 8개에서 답이 빠진다. 모델이 아무리 똑똑해도 답이 없는 조각만 받으면 맞힐 수 없다.
  • 여러 언어로 학습한 세 모델은 3개만 붙여도 17개가 든다.
  • bge-m3를 골랐다. 1위가 가장 많고, 질문 앞에 따로 지시문을 붙이지 않아도 되고, MIT 라이선스다. KURE-v1은 bge-m3를 한국어로 더 학습한 모델이다. 10위 안은 18개로 가장 많았지만 1위는 bge-m3보다 적었다.

세우기: 6단계 설정이 막은 두 가지

6단계에서 웹 UI가 GPU를 쓰지 않게 USE_SLIM_DOCKER=true를 넣었습니다. 웹 UI가 MLX 서버와 GPU 메모리를 다투다 MLX 서버가 멈췄기 때문입니다. 그런데 이 설정이 문서 검색에 필요한 두 가지도 함께 꺼 두고 있었습니다.

꺼진 것 드러난 곳 대신 쓴 것
웹 UI 안의 임베딩 모델 코드를 보니 이 설정이면 임베딩 모델을 불러오지 않고, 바꾸려 하면 「바깥의 임베딩 엔진을 쓰라」며 거절한다 임베딩 서버를 따로 띄워 게이트웨이 뒤에 둠
웹 UI 안의 벡터 저장소 첫 글을 넣자 503: Configure PGVECTOR_DB_URL for remote vector storage. 9단계의 PostgreSQL 18에 pgvector 확장

설정을 되돌리면 두 가지가 다시 켜지지만, 웹 UI가 다시 GPU를 씁니다. 그래서 설정은 그대로 두고 빠진 두 가지를 바깥에 세웠습니다.

임베딩 서버

2단계에서 조립한 llama.cpp로 bge-m3를 띄웠습니다. 파일은 llama.cpp 개발진이 변환해 올린 Q8_0 GGUF(635MB)이고, 받은 뒤 지문을 맞췄습니다.

옵션 뜻
--embedding 답은 쓰지 않고 벡터만 만든다
--pooling cls 글 전체의 벡터로 첫 토큰의 값을 쓴다. bge-m3가 학습한 방식이다
--device none GPU를 쓰지 않는다. GPU 메모리는 MLX 서버 몫이다
-c 8192 -np 4 네 개까지 동시에, 하나에 2,048토큰까지
-b 2048 -ub 2048 조각 하나를 한 번에 계산하게 묶음을 키운다
--host 127.0.0.1 Mac mini 안에서만 받는다. 게이트웨이만 부른다

메모리는 885MB를 씁니다. Mac mini CPU로 글 10편의 조각을 모두 벡터로 바꾸는 데 33초, 질문 하나는 0.02초 걸렸습니다. 찾은 순위는 제 컴퓨터에서 잰 것과 하나도 다르지 않았습니다.

게이트웨이에는 모델 이름 bge-m3를 더하고, 웹 UI에 임베딩 전용 API 키를 따로 줬습니다. 이 키로 채팅을 부르면 403, 채팅용 키로 임베딩을 부르면 403입니다.

벡터 저장소

Homebrew로 pgvector 0.8.7을 깔고, 9단계의 PostgreSQL에 웹 UI 전용 계정과 데이터베이스를 만들었습니다. 웹 UI 쪽에는 PostgreSQL에 붙는 데 필요한 파이썬 부품 두 개를 더했습니다. 버전은 Open WebUI 0.13.3이 적어 둔 그대로입니다.

웹 UI는 8초 만에 다시 떴습니다.

글 넣기

웹 UI에 글을 넣는 것은 웹 UI의 API로 했습니다. 그러려면 웹 UI가 내주는 API 키가 필요합니다. 관리자가 설정 창의 인증에서 API 키를 켜야 계정에 키를 만드는 버튼이 나옵니다. 이 설정을 웹 UI 데이터베이스에서 직접 켜려 하자 Claude Code의 자동 권한 검사가 막아서, 둘 다 화면에서 켰습니다.

키 대신 명령어가 저장된 이유

처음에는 키를 복사한 뒤, Mac mini에 저장하는 명령을 복사해 터미널에 붙였습니다. 이 명령은 실행되는 순간의 클립보드를 저장합니다. 그런데 명령을 복사하면서 클립보드의 키가 지워져, 파일에는 명령어 글자가 들어갔습니다. 두 번째는 명령을 먼저 실행해 키를 기다리게 하고, 키는 마지막에 복사해 붙였습니다.

지식 「로컬 LLM 연재」를 만들어 10편을 넣는 데 95초 걸렸습니다. 조각마다 벡터를 두 번 만들기 때문입니다. 글을 올릴 때 한 번, 지식에 더할 때 한 번입니다. 데이터베이스는 12MB가 됐습니다. 웹 UI의 검색으로 18개를 다시 재 보니 1위 13개, 3위 안 17개로 앞의 측정과 같았습니다. 질문 하나를 찾는 데 0.04초 걸렸습니다. 지식은 웹 UI의 모든 사용자가 읽을 수 있게 열어 두었습니다.

찾아 읽게 하면

질문 20개를 다시 물었습니다. 이번에는 질문마다 「로컬 LLM 연재」를 붙였습니다. 붙이는 조각은 웹 UI 기본값인 10개로 한 번, 3개로 한 번 쟀습니다. 앞에서 3위 안에 17개가 들었으니 3개로도 될지 본 것입니다.

붙인 것 Mac mini · Qwen 노트북 · Gemma
없음 3/18, 34초 2/18, 10초
조각 10개 17/18, 77초 18/18, 16초
조각 3개 17/18, 35초 18/18, 11초

시간은 답 하나에 걸린 평균입니다. 조각 10개를 붙이면 질문 하나가 4,000토큰 안팎이 되고, 3개면 1,500토큰 안팎이 됩니다.

  • 글을 붙이면 거의 다 맞힌다. 답 끝에는 출처 번호를 달았다. 글에 없는 두 질문에는 네 번 모두 자료에 없다고 했다. API 키를 묻자, 「48자리 무작위 문자열이고 화면에 출력한 적이 없다」는 글의 내용까지만 말했다.
  • Mac mini는 읽는 시간이 문제다. 질문을 초당 63토큰으로 읽어서, 조각 10개면 답 하나에 평균 77초, 길면 2분이 걸렸다. 3개로 줄이자 35초가 됐다. 노트북은 같은 양을 훨씬 빨리 읽어 16초와 11초였다.
  • 조각을 줄여도 맞힌 수는 줄지 않았다. Mac mini가 두 번 다 놓친 하나는 2단계의 기억 길이 질문이다. 「앞으로는 -c 16384로 직접 정해서 씁니다」라는 문장이 든 조각은 검색 10위 안에 들지 않았다. 모델은 다른 조각에 있던 16,384를 옮겨 적고도 「자료에 분명히 나와 있지 않다」고 끝맺었다. 같은 조각을 받은 Gemma는 「16,384로 제한하여 사용했습니다」라고 답했다.
  • 글을 붙이면 답이 짧아진다. 문서 없이 물으면 Mac mini는 평균 211토큰을 늘어놓았고, 글을 붙이면 80토큰 안팎으로 답했다. 그래서 조각 3개를 붙인 쪽(35초)이 문서 없이 물은 쪽(34초)과 거의 같은 시간에 끝났다.

웹 UI의 기본값을 조각 3개로 바꿔 두었습니다. 쓰는 사람은 대화창에 #을 치고 「로컬 LLM 연재」를 고른 뒤 물으면 됩니다.

가르치기: 미세조정

문서 검색은 모델을 그대로 두고 자료를 붙여 줍니다. 미세조정은 반대로, 모델이 글 내용을 외우도록 더 학습시킵니다. 다 배우면 자료 없이도 답할 테니, 질문마다 읽는 시간도 들지 않습니다. 정말 그런지 같은 질문으로 견줬습니다.

모델 전체를 다시 학습하려면 모델 크기의 몇 배나 되는 메모리가 듭니다. 그래서 LoRA를 씁니다. 원래 숫자는 그대로 두고, 층마다 작은 덧붙임 숫자를 더해 그것만 학습하는 방법입니다. 이 덧붙임을 어댑터라고 부릅니다.

문제집 만들기

학습에는 질문과 답을 짝지은 문제집이 필요합니다. 이것도 Mac mini의 Qwen 3.8 27B가 만들었습니다. 연재 글을 63조각으로 나눠 조각마다 「이 부분만 읽고 답할 수 있는 질문과 답을 3~4개 만들라」고 시켰습니다. 53분 동안 231쌍이 나왔습니다. 답에 원문에 없는 숫자가 들어간 쌍은 빼도록 해 두었는데, 한 쌍도 걸리지 않았습니다.

글 문제집의 질문 답
0단계 서버의 잠자기를 끄기 위해 어떤 명령 값을 설정했는가? sleep 0으로 설정했다.
8단계 Mac mini의 로컬 모델에 커밋 메시지 작성을 맡기기로 한 세 가지 이유는 무엇인가요? 자주 하는 작은 일이라 답이 짧고, 견줄 답이 이미 있으며, 코드가 내 네트워크 밖으로 나가지 않기 때문입니다.
9단계 한도를 초과한 요청이 들어왔을 때 게이트웨이는 기다리게 하는 대신 어떤 조치를 취하며, 재시도는 누구의 몫인가요? 게이트웨이는 기다리게 하지 않고 바로 거절하며, 기다렸다가 다시 보내는 일은 부르는 쪽(클라이언트)의 몫입니다.

208쌍은 학습에, 23쌍은 학습 중 확인에 썼습니다. 시험 문제를 문제집에 일부러 넣지는 않았지만, 27B가 만든 문제 가운데에는 시험 문제와 거의 같은 것이 여럿 있습니다. 시험 문제 18개의 답이 되는 값은 모두 학습용 문제집의 답 어딘가에 나옵니다.

작은 모델 고르기

Mac mini의 27B 모델은 올려 두기만 해도 메모리를 16GB 넘게 씁니다. 학습까지 할 수는 없어서 4B 모델을 골랐습니다.

  • 처음 고른 것은 Qwen 3.5 4B였다. Mac mini의 Qwen 3.8과 같은 구조다. 그런데 MLX로 학습하자 제 컴퓨터에서도 초당 27토큰밖에 나오지 않았다. 이 구조의 새 층(선형 어텐션)을 학습하는 계산이 아직 느린 것으로 보인다.
  • Qwen3 4B(2507판)로 바꿨다. 일반 구조이고 Apache 2.0이다. 같은 조건에서 초당 180토큰이 나왔다. 2025년에 나온 모델이라 이 연재는 모른다.

답 앞에 붙은 빈 생각 태그

제 컴퓨터에서 먼저 짧게 학습해 보니, 학습한 모델이 답마다 <think></think>를 붙였습니다. 이 모델의 대화 형식은 학습 데이터의 답 앞에는 빈 생각 태그를 넣으면서, 질문을 받을 때는 넣지 않습니다. 그래서 모델이 그 태그까지 답의 일부로 외웠습니다. 학습할 때만 쓰는 사본을 만들어 빈 태그를 빼자 사라졌습니다.

Mac mini에서 학습하기

Mac mini의 MLX 서버는 27B를 올려 두고 있어서, 그대로는 학습할 메모리가 없습니다. MLX 서버는 요청에 다른 모델 이름을 넣으면 그 모델로 바꿔 끼웁니다. 9단계에서 게이트웨이로 막은 바로 그 기능입니다. 바꿔 끼울 때는 앞 모델을 지우고 MLX의 메모리 풀을 비웁니다. 그래서 Mac mini 안에서 작은 모델로 바꿔 끼운 뒤 학습했습니다. 학습과 시험이 끝난 뒤 다시 27B로 돌렸고, 답 쓰는 속도는 초당 6토큰으로 예전과 같았습니다. 그동안 웹 UI에서는 노트북 모델만 썼습니다.

가르친 결과

학습 전과 뒤의 작은 모델에게 같은 20개를 물었습니다. 글을 붙이는 쪽은 웹 UI와 같은 조각 3개와 같은 지시문을 썼습니다.

작은 모델 문서 없이 조각 3개
학습 전 1/18, 10초 17/18, 5초
학습 뒤 4/18, 2초 17/18, 4초
  • 새로 맞힌 것은 셋이다. ThrottleInterval, USE_SLIM_DOCKER, 「지난 대화를 매번 다시 보낸다」. 셋 다 문제집에 거의 같은 질문이 있었다.
  • 문제집에 있던 사실도 대부분 꺼내지 못했다. 답이 문제집에 들어 있던 18개 가운데 맞힌 것은 4개뿐이다. 그중 401은 학습 전에도 알았다. 문제집에 「Mac mini는 99초」라는 답이 두 번이나 있었는데도, 질문이 조금 다르자 「6초」라고 답했다.
  • 틀린 답도 짧고 단정하다. 정전 항목은 「AutoBoot 1」, 게이트웨이는 「Postman 14.18.0 버전」이라고 했다. 학습 전에는 「알 수 없다」며 길게 설명하던 모델이, 문제집의 말투대로 한두 마디로 답했다. 답은 빨라졌지만, 틀렸는지 짐작할 실마리가 사라졌다.
  • 글에 없는 질문에도 지어냈다. 학습 전에는 둘 다 모른다고 했다. 학습 뒤에는 10단계 결과를 「2개」라고 했고, API 키를 묻자 sk-1234…로 시작하는 가짜 키를 내놓았다. 문제집은 모두 글에 답이 있는 문제라, 모른다고 답하는 예가 하나도 없었다.
  • 글을 붙이면 다시 맞힌다. 학습 뒤에도 조각 3개를 붙이자 학습 전과 같은 17개를 맞혔다. 다만 글에 없는 10단계 결과를 묻자, 자료에 없는데도 「4개를 맞혔다」고 했다. 학습 전 모델은 같은 조건에서 모른다고 했다.

이번 미세조정으로 눈에 띄게 바뀐 것은 지식보다 말투였습니다. 사실마다 한두 번씩 나오는 208쌍으로는 글 내용을 거의 넣지 못했고, 글에 없는 두 질문에는 학습 뒤 둘 다 지어냈습니다. 학습 한 번, 질문 20개로 본 결과입니다.

알게 된 것

  • 모르는 글을 쓰게 하려면 찾아 붙이는 쪽이 나았다. 같은 4B 모델로 견주면, 글을 찾아 붙이자 1/18이 17/18이 됐고, 25분 가르치자 4/18이 됐다. 가르친 모델은 글에 없는 것도 지어냈다.
  • 작은 모델에 글을 붙이면 빠르다. 학습하지 않은 4B에 조각 3개를 붙이자 17/18을 맞혔고 답 하나에 5초 걸렸다. 같은 조각을 붙인 27B는 17/18에 35초였다. 4B는 웹 UI를 거치지 않고 MLX 서버에 바로 물은 값이다.
  • 이번 미세조정에서는 말투가 먼저 바뀌었다. 문제집처럼 짧고 단정하게 답하게 됐다. 사실을 넣으려면 같은 사실을 여러 모양으로 묻는 문제와, 모를 때 모른다고 답하는 문제를 더 넣어 봐야 한다.
  • 임베딩 모델부터 고른다. 웹 UI 기본값으로는 조각 10개를 붙여도 18개 중 8개에서 답이 든 조각이 빠진다.
  • 느린 기계에서는 붙이는 양을 줄인다. Mac mini는 조각 10개면 답 하나에 77초, 3개면 35초였다. 맞힌 수는 같았다.
  • 6단계의 slim 설정은 문서 검색도 꺼 두었다. 임베딩 서버와 pgvector를 바깥에 따로 세워야 했다.
  • 새 구조의 모델은 학습이 느릴 수 있다. 같은 크기라도 Qwen 3.5 4B는 초당 27토큰, Qwen3 4B는 180토큰이었다.

연재를 마치며

모델 파일 하나에서 시작해 엔진, 서버, 웹 UI, 웹 검색, 게이트웨이를 거쳐 문서 검색까지 왔습니다. 지금 두 기계에서 도는 것은 아래와 같습니다.
