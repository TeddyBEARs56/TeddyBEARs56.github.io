국산 LLM에게 코딩을 맡겨 보니

4편까지는 국산 모델에게 글을 읽고 쓰는 일을 맡겼습니다. 이번에는 코딩입니다. 「로컬 LLM 처음부터」 11단계에서 쓴 과제 세 개를, Claude Code를 노트북의 Ollama에 바로 붙여 국산 모델에게 풀게 했습니다.

올린 날
2026-11-22
읽는 시간
약 8분

이번에 할 일

  1. 지난 연재의 과제 세 개를 그대로 쓴다. 「로컬 LLM 처음부터」 11단계의 찾기, 고치기, 더하기다.
  2. Claude Code를 노트북의 Ollama에 바로 붙인다. 게이트웨이 없이, Ollama 4편과 같은 조건으로 붙인다.
  3. 국산 모델 넷을 두 번씩 돌린다. 해외 모델 둘은 Ollama 4편에서 같은 노트북, 같은 조건으로 돌린 결과와 견준다.

시험 방법

노트북(Arc 140V 내장 GPU, 메모리 32GB)의 Ollama 0.40.16에, Mac mini의 Claude Code 2.1.326을 같은 네트워크로 바로 붙였습니다. 조건은 Ollama 4편과 같습니다.

  • Ollama: 기억할 글 길이 49,152토큰, 한 번에 요청 하나, 모델 하나.
  • Claude Code: ollama launch claude가 넣는 설정에, 기억할 글 길이 49,152토큰과 한 번에 쓰는 답 4,096토큰을 더했다. 40번 주고받거나 45분이 지나면 멈춘다.
  • 과제: 과제마다 이 블로그의 11월 17일 원본을 새로 복사해 주었다. 지난 연재 1편과 같은 복사본이다.

Claude Code에 보낸 말의 원문은 지난 연재 1편에 있습니다.

모델은 2~4편과 같은 국산 넷입니다. Mi:dm 2.0 Base(KT), Kanana-2 30B(카카오), EXAONE 4.5 33B(LG), Tri-21B-Think(트릴리온랩스)이고, 모두 Q4_K_M으로 양자화한 GGUF입니다. 해외 모델은 Ollama 4편의 Qwen3.6 35B와 Gemma 4 26B(둘 다 UD-IQ4_XS) 결과를 썼고, 다시 돌리지는 않았습니다.

  • Mi:dm, Kanana, Tri는 32,768토큰으로 돌았다. 모델이 배운 길이가 32,768토큰이라 Ollama가 49,152를 그만큼으로 줄였다. 실행마다 Ollama 기록에서 프롬프트를 자른 줄(truncating input prompt)을 셌는데, 한 번도 없었다.
  • EXAONE은 그림 처리 부분을 뺀 판으로 돌렸다. EXAONE 4.5는 그림도 읽는 모델이라, 모델 파일 말고 그림 처리 부분(projector)이 2.4GiB(2편의 2.6GB) 따로 붙어 있다. 처음 49,152토큰으로 올릴 때 GPU 메모리가 모자라 실패했다. Ollama가 그림 처리 부분을 CPU로 옮겨 다시 해 보기 전에 멈췄다. 다시 시도하는 대신, 같은 모델 파일, 같은 대화 틀, 같은 멈춤 낱말로 그림 처리 부분만 뺀 태그를 만들어 썼다.

돌리기 전에, 도구를 부르는지

Claude Code는 파일을 찾고 읽고 고치는 일을 모두 도구 호출로 시킵니다. 모델이 도구를 부르지 못하면 아무 일도 못 합니다. 그래서 먼저 Read 도구 하나만 주고 「/tmp/a.txt 파일을 읽어서 무슨 내용인지 알려 줘. 반드시 Read 도구를 써.」라고 물었습니다. 한 번은 생각을 끄고, 한 번은 Claude Code가 보내는 것처럼 생각을 켜고 보냈습니다.

모델 생각 끔 생각 켬
Mi:dm 2.0 불렀다 불렀다
Kanana-2 부르겠다는 글만 생각만 쓰고 끝
EXAONE 4.5 메모리 부족 불렀다
Tri-21B-Think 생각 글이 길어 끊김 불렀다

생각을 끈 쪽의 EXAONE은 그림 처리 부분이 붙은 원래 태그이고, 생각을 켠 쪽은 뺀 태그입니다. Tri는 생각 끈 시험에서 답을 400토큰으로 묶어 두어, 생각을 글로 쓰다가 끊겼습니다. Claude Code와 같은 조건인 생각 켬에서는 넷 중 셋이 도구를 불렀습니다.

도구를 거의 쓰지 않았다: Mi:dm과 Tri

Mi:dm 2.0은 여섯 번 모두 1~2번 주고받고 1분 안팎에 끝냈습니다.

  • 찾기는 파일을 열지 않고 답했다. 1회차는 「블로그 플랫폼마다 이 정보를 계산하는 방식이 조금씩 다르지만」으로 시작하는 일반론이었다. 2회차는 읽기 시간을 페이지가 뜨는 데 걸리는 시간으로 알아듣고 답했다.
  • 고치기와 더하기는 주로 되물었다. 「혹시 Cybug의 어떤 버전을 사용 중인지 알 수 있을까요?」처럼 정보를 더 달라고 했다.
  • 도구는 여섯 번 중 두 번, 한 번씩 불렀다. 그중 하나는 작업 폴더 밖을 찾으려다 권한에 막혔고, 그러자 권한을 달라고 하고 끝냈다.

Mi:dm의 대화 틀은 Claude Code가 보낸 지시보다 앞에, 고정된 한국어 지시문을 길게 넣습니다. 그 안에 이런 문장이 있습니다.

되묻거나 도구 없이 답한 것이 이 지시와 맞아떨어지지만, 지시문을 빼고 다시 돌려 보지는 않았습니다. 같은 대화 틀로도 시험 요청에서는 도구를 바로 불렀습니다.

Tri-21B-Think는 Ollama가 생각하는 모델로 알아보지 못합니다. 그래서 생각이 따로 나뉘지 않고 <think>로 시작하는 보이는 글로 나왔습니다.

  • 네 번은 도구를 부르지 않고 한 번에 끝냈다. 찾기 두 번은 일반론으로 답했다. 1회차는 6.8분이 걸렸고, 한국어 질문에 영어로 답한 뒤 「분석할 파일이 있으면 경로를 알려 달라」로 마쳤다. 더하기 두 번은 먼저 파일을 확인하겠다고만 쓰고 멈췄다.
  • 고치기에서는 도구를 잘못 불렀다. 1회차에 Grep을 여섯 번 불렀다. 찾을 위치(path)에 **/*.vue 같은 파일 이름 패턴을 넣어 여섯 번 모두 「Path does not exist」가 났다.

도구 호출이 생각 속에 묻혔다: Kanana-2

이번에 쓴 Kanana-2는 생각하지 않는 Instruct 판입니다(2편). 그런데 Hugging Face가 붙여 보낸 대화 틀은 답을 쓸 자리 앞에 <think>를 미리 열어 둡니다. 시험 요청에서 Kanana-2는 생각을 쓰고, 생각을 닫는 </think> 없이 바로 도구 호출(<tool_call>)을 썼습니다. Ollama는 도구 호출까지 모두 생각으로 돌려주었고, 도구 호출은 비어 있었습니다.

생각을 끄고 Ollama 자체 API(/api/chat)로 보냈을 때는 도구 호출이 잡혔습니다. 하지만 앞의 표처럼 Claude 형식 API에 생각을 끄고 보냈을 때는 부르겠다는 글만 쓰고 끝났습니다. 한 번씩이라, 생각을 끄면 풀린다고 단정할 수는 없습니다. 어느 쪽이든 Claude Code는 생각을 끄는 요청을 보내지 않습니다(Ollama 4편).

실제 과제에서는 여섯 번 중 다섯 번이 2~3번 주고받고 끝났습니다. 그동안 도구 호출을 생각 속에 썼고, 그 형식도 <tools>, tool_call 코드 블록, tool_code 코드 블록처럼 그때마다 달랐습니다. 보이는 답이 없으면 Claude Code는 「보이는 답을 하라」는 말을 덧붙여 다시 묻는데, 그래도 달라지지 않았습니다.

고치기 1회차 하나만 달랐습니다. 21번 주고받는 동안 도구가 19번 실행됐습니다. 세 번째 Grep 결과에 고칠 줄(b.status)이 이미 나왔는데도 지나쳤습니다. 그 뒤로 데이터베이스와 .env 파일을 찾아다녔고, 없는 파일을 고치려 했습니다. Claude Code의 기억 파일 자리에 메모를 쓰려다 권한에 막히기도 했습니다. 끝내 아무것도 고치지 못했습니다.

대화 틀에서 생각 부분을 뺀 태그도 만들어 봤습니다. 그러자 Ollama가 그 태그에는 GGUF 안의 다른 대화 틀을 골랐고, 도구를 주자 「tools param requires –jinja flag」 오류로 멈췄습니다. 더 파지는 않았습니다.

EXAONE만 풀었고, 느렸다

EXAONE 4.5는 찾기를 두 번 모두 풀었습니다. 8~9번 주고받는 동안 Grep과 Glob으로 파일을 찾고 Read로 읽은 뒤, 계산 방식을 맞게 설명했습니다(10.3분, 11.0분). 고치기 1회차는 15번 주고받으며 원인을 찾아 고치고, 빌드한 뒤 결과 페이지까지 읽어 확인했습니다(30.5분).

나머지 셋은 45분 한도에 걸렸습니다. 이 셋은 시험 스크립트가 대화 기록을 옮겨 두지 않았지만, Claude Code가 남긴 세션 파일로 무엇을 하다 끊겼는지 봤습니다.

시도 한 일 끊길 때
고치기 2회차 34분에 고치고 35분에 빌드, 결과 확인 끝맺는 답을 쓰기 전
더하기 1회차 40분 가까이 파일을 찾아 헤맨 뒤 고치기 시작 앞부분만 고친 채
더하기 2회차 35분에 고치기 시작, 41분에 다시 씀 빌드는 한 번도 안 함

더하기 2회차는 글과 버그 기록을 날짜순으로 섞는 데까지는 맞았습니다. 하지만 글인지 버그 기록인지 가리는 조건(post.id.startsWith('posts'))이 틀려, 글 11편의 주소까지 모두 /bugs/…로 붙었습니다. 더하기 1회차는 가져오기 줄만 바꾼 채 끊겨, 피드에는 글만 들어 있었습니다.

같은 노트북에서 해외 모델은 과제 하나를 1~7분에 끝냈습니다. EXAONE 4.5는 33B dense 모델이고, 3편에서 이 노트북의 답 쓰는 속도가 초당 4.0토큰이었습니다. 생각도 길게 써서, 고치기 1회차에는 생각만 1만 6천 자였습니다. 다만 걸린 시간이 계산 방식만으로 갈리지는 않습니다. 토큰마다 일부만 계산하는 MoE인 Kanana-2도 더하기에서는 생각을 1만~2만 5천 자 썼고, 한 바퀴에 47~55분이 걸렸습니다.

과제 세 개를 한 바퀴 도는 데 걸린 시간(분)입니다. 실패한 시도도 들어 있고, 45분 한도에 걸린 시도는 45분으로 셌습니다.

알게 된 것

  • 도구를 부를 수 있는 것과 에이전트로 일하는 것은 다르다. 시험 요청 하나에는 넷 중 셋이 도구를 불렀다. 하지만 실제 과제에서 스스로 파일을 찾아 읽고 고친 것은 EXAONE 4.5뿐이었다.
  • Ollama에 붙일 때는 대화 틀부터 봐야 한다. Kanana-2는 대화 틀이 열어 둔 생각 속에 도구 호출을 쓰거나 형식을 틀려, 대부분 실행되지 않았다. Tri는 생각하는 모델로 알려지지 않아 생각이 보이는 글로 나왔다. Mi:dm은 대화 틀의 고정 지시문이 Claude Code의 지시보다 앞에 온다. Mi:dm과 Tri가 실패한 직접 원인이 대화 틀인지는 시험하지 않았다.
  • EXAONE 4.5는 풀지만 노트북에서는 느리다. 끝낸 과제는 10~31분이 걸렸고, 나머지 셋은 45분 한도에 걸렸다. 같은 일을 해외 모델은 1~7분에 했다.
  • 이 노트북에서 코딩을 맡긴다면 지금은 해외 모델이다. Gemma 4와 Qwen3.6이 더 많이, 훨씬 빨리 풀었다. 어떤 일에 어떤 모델을 쓸지는 6편에서 정리한다.
