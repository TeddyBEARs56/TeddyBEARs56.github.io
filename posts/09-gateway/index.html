게이트웨이 세우기

지금까지 Mac mini의 모델 서버는 같은 네트워크의 누구에게나 열려 있었습니다. API 키를 확인하지 않았고, 누가 물었는지는 보낸 컴퓨터의 주소로만 남았습니다. 이번에는 모델 서버 앞에 게이트웨이를 세웁니다. 요청을 한곳에서 받아 API 키를 확인하고, 알맞은 서버로 넘기고, 사용량을 남기는 프로그램입니다.

올린 날
2026-11-16
읽는 시간
약 14분

이번에 할 일

  1. 몰릴 때를 잰다. 4단계에서 미룬 숙제다. 서로 다른 긴 질문을 1개, 2개, 4개씩 한꺼번에 보낸다.
  2. 게이트웨이를 세운다. 요청을 한곳에서 받아 API 키를 확인하고, 알맞은 서버로 넘기는 프로그램이다.
  3. API 키를 나눠 준다. 프로그램마다 따로 주고, 쓸 수 있는 모델과 한도를 정한다.
  4. 누가 얼마나 쓰는지 본다.
  5. 모델 서버를 바깥에서 막는다. 4단계부터 API 키 없이 열려 있던 8080번 포트다.

지금까지는

Mac mini의 MLX 서버는 4단계부터 같은 네트워크 전체에서 질문을 받았습니다. API 키는 확인하지 않았습니다. 서버 기록에는 요청 시각과 보낸 컴퓨터의 주소만 남습니다. 사흘 치 기록을 보니 묻는 곳은 둘이었습니다.

  • 같은 기계의 웹 UI(127.0.0.1): 웹 UI로 들어온 질문은 누가 했든 이 주소 하나로 남는다.
  • 제 컴퓨터: 8단계의 커밋 메시지 도구가 보낸 요청이다.

막을 이유는 더 있었습니다. 이 서버는 요청 하나로 올려 둔 모델을 바꿔 끼웁니다. 8단계 도구의 --model이 그 기능을 썼습니다. 누구든 바꾸면 다른 사람도 그 모델을 쓰게 됩니다. 그리고 한 사람의 긴 질문 뒤에서 다른 사람이 기다립니다. 얼마나 기다리는지부터 쟀습니다.

몰리면 얼마나 느려지나

4단계에서는 같은 짧은 질문을 동시에 보냈고, 4명이 물어도 거의 느려지지 않았습니다. 이번에는 질문마다 다른 글을 넣었습니다. 1,500자짜리 글을 요약하게 했고, 질문 하나에 읽는 양은 750~860토큰, 답은 150토큰입니다. 질문 맨 앞에는 번호를 달았습니다. 서버가 앞서 읽은 질문을 임시로 저장해 두었다가 다시 쓰는 일(프롬프트 캐시)이 끼어들지 않게 하려는 것입니다.

동시에 보낸 질문 1개 2개 4개
Mac mini, 마지막 사람의 첫 글자 12.7초 25.5초 74.1초
Mac mini, 모두 끝남 35.3초 50.0초 99.0초
노트북, 마지막 사람의 첫 글자 4.9초 8.1초 30.1초
노트북, 모두 끝남 13.3초 19.3초 41.3초
  • 긴 질문은 묶이지 않는다. Mac mini는 6단계에서 메모리 부족으로 멈춘 뒤로 질문을 한 번에 하나씩 읽고, 답은 한 번에 둘까지 쓰게 해 두었다. 그래서 2개를 보내면 둘 다 읽은 뒤에야 쓰기 시작한다. 혼자일 때 12.7초 걸리던 첫 글자가 둘 다 25초쯤에 나왔다.
  • 셋째부터는 자리를 기다린다. 4개를 보내자 둘은 25초쯤에 첫 글자가 나왔고, 나머지 둘은 앞의 두 답이 거의 끝난 73~74초에야 나왔다. 노트북 서버도 답을 쓰는 자리가 둘이라, 4개 중 둘은 30초를 기다렸다.
  • 노트북이 두 배 넘게 빠르다. 4개를 모두 끝내는 데 Mac mini는 99초, 노트북은 41.3초가 걸렸다.

게이트웨이 고르기

게이트웨이는 여러 모델 서버 앞에 서서 요청을 먼저 받는 프로그램입니다. 견준 길은 셋입니다.

방법 좋은 점 아쉬운 점
Open WebUI의 API 키 이미 띄워 둔 웹 UI에 들어 있다. 계정마다 키를 만든다 요청 수나 동시 요청 수에 한도를 걸 수 없다. 프로그램도 웹 UI 계정이 있어야 한다
직접 만들기 작고, 하는 일이 다 보인다 키 관리, 사용량 기록, 한도를 모두 새로 짜야 한다. 보안 구멍도 혼자 책임진다
LiteLLM 가장 널리 쓰이는 공개 게이트웨이다. 키마다 쓸 모델과 한도를 정하고, 사용량을 남기고, 여러 서버로 나눠 보낸다 무겁다. PostgreSQL이 따로 필요하다. 기능이 많은 만큼 보안 공지가 잦다

고른 것은 LiteLLM입니다. 이 연재는 실제로 많이 쓰는 도구를 익히는 것이 목적이기도 합니다. 대신 설치는 조심했습니다. LiteLLM은 올해 두 번, PyPI(파이썬 패키지 저장소)에 비밀값을 훔치는 코드가 든 버전이 올라갔습니다. 3월에는 1.82.7과 1.82.8, 10월 21일에는 1.107.0입니다. 셋 다 PyPI에서 내려갔지만, 내려가기 전에 설치한 컴퓨터는 비밀값이 이미 빠져나갔을 수 있습니다. 그래서 네 가지를 지켰습니다.

  • 나온 지 2주가 넘은 버전: 10월 28일에 나온 1.106.6을 골랐다. 두 번째 사고 뒤에 나온 버전이다. GitHub에 공개된 LiteLLM 보안 공지 45개의 영향 범위를 모두 봤는데, 모두 이보다 앞선 버전이었다.
  • 함께 깔리는 패키지도 2주 전 것까지만: uv의 --exclude-newer는 그 날짜 뒤에 올라온 버전을 고르지 않게 한다.
  • 깐 뒤에 흔적을 찾는다: 10월의 악성 버전은 파이썬이 켜질 때마다 저절로 실행되는 cook.pth 파일을 심었다. 설치한 폴더에는 그런 .pth 파일도, 알려진 악성 파일 이름도 없었다.
  • 고정하지 못한 것도 적어 둔다: LiteLLM이 데이터베이스를 다룰 때 쓰는 Prisma는 처음 켤 때 Node와 실행 파일을 따로 내려받는다. 이 부분은 위의 고정에 묶이지 않는다.

세우기

게이트웨이는 Mac mini에 둡니다. 웹 UI도 이제 모델 서버에 직접 묻지 않고 게이트웨이를 거칩니다.

부분 하는 일 어디에
LiteLLM API 키 확인, 한도, 서버 고르기, 사용량 기록 Mac mini 4000번 포트
PostgreSQL 키와 사용량을 저장하는 데이터베이스 Mac mini 5432번 포트, Mac mini 안에서만 접속
비밀값 세 개 관리자 키(마스터 키), 저장할 비밀값을 암호화하는 키, 데이터베이스 암호 Mac mini의 파일. 주인만 읽을 수 있게 두고 화면에 출력하지 않음

설정 파일에는 비밀값을 적지 않고, 시작 스크립트가 파일에서 읽어 넘깁니다. 줄인 설정은 아래와 같습니다.

모델 이름을 서버 쪽 이름과 따로 둔 것이 중요합니다. 요청에 어떤 이름을 넣든 게이트웨이는 정해 둔 이름만 받고, MLX 서버에는 늘 default_model을 보냅니다. 이제 요청으로 Mac mini의 모델을 바꿔 끼울 수 없습니다.

처음 켤 때 두 번 멈춘 이유

처음에는 litellm[proxy]만 설치했습니다. 그러자 데이터베이스 도구 Prisma가 없다며 멈췄습니다. 안내대로 extra_proxy 묶음을 더했더니, 이번에는 마이그레이션 213개를 다 넣은 뒤 「Prisma 실행 파일을 찾을 수 없다」며 멈췄습니다. 마이그레이션은 데이터베이스에 표를 만들고 고치는 단계입니다. Prisma가 쓸 파이썬 코드를 만드는 prisma generate를 손으로 한 번 돌리자 15초 만에 켜졌습니다. 다시 설치하면 이것도 다시 해야 합니다.

무게는 디스크 590MB, 메모리는 LiteLLM이 0.6GB, PostgreSQL이 0.1GB 안팎입니다. 웹 UI(0.6GB)와 비슷합니다.

API 키 나눠 주기

키는 지금 쓰는 프로그램마다 줬습니다. 웹 UI를 쓰는 사람에게는 키를 주지 않습니다. 웹 UI가 자기 키 하나로 묻고, 묻는 사람의 이메일을 함께 보냅니다. 웹 UI 없이 자기 프로그램으로 쓰려는 사람이 생기면, 그 사람에게도 같은 방법으로 키를 하나 만들어 줍니다.

키 이름 쓰는 곳 쓸 수 있는 모델 한도
open-webui 웹 UI Mac mini, 노트북 없음
commit-tool 제 컴퓨터의 커밋 도구 Mac mini, 노트북, auto 분당 10회, 동시 1개
test-user 시험용. 다 쓰고 막음 Mac mini, auto 분당 2회, 동시 1개

키는 관리자 키로 LiteLLM에 요청해 만듭니다. Mac mini에 둔 작은 스크립트(gw-admin.py)가 이 요청을 보내고, 받은 키를 주인만 읽는 파일에 바로 저장합니다. 키는 화면에 나오지 않습니다. 커밋 도구의 키는 제 컴퓨터로 옮긴 뒤 Mac mini의 사본을 지웠습니다.

allowed_routes는 이 키로 부를 수 있는 주소입니다. 채팅과 모델 목록만 열었습니다. 처음에는 넣지 않았다가 검토에서 지적을 받고 더했습니다.

  • 한도를 넘으면 기다리게 하지 않고 바로 거절한다. 둘째 요청은 0.0초 만에 429를 받았다. 기다렸다가 다시 보내는 일은 부르는 쪽 몫이다.
  • 1분은 시계의 분이 아니라 첫 요청부터 잰다. 정각에 맞춰 보냈는데도 앞 요청에서 1분이 안 지나 막혔다.
  • 흘려 받다 끊어도 자리가 풀린다. 동시 1개 키로 답을 흘려 받다가 2초 만에 끊고 바로 다시 물었더니 200이었다.

누가 얼마나 쓰나

LiteLLM은 요청마다 키, 사람, 모델, 읽은 토큰과 쓴 토큰, 걸린 시간을 PostgreSQL에 남깁니다. Mac mini에서 gw-admin.py usage로 묶어 봅니다. 아래는 오늘 시험한 기록의 일부입니다.

  • 사람 칸은 웹 UI가 알려 준다. 웹 UI는 묻는 사람의 이메일을 X-OpenWebUI-User-Email 헤더에 실어 보낸다. 표의 open-webui 줄은 그 헤더에 시험용 이메일을 넣어 직접 보낸 것이다. 다만 다른 키를 가진 사람도 같은 헤더를 붙일 수 있다. 그래서 사람 칸은 open-webui 키 줄에서만 믿는다.
  • 질문과 답은 남기지 않는다. 지금까지 쌓인 기록 80줄 가운데 질문이나 답이 든 줄은 0이었다. 시험에 쓴 질문 문장을 게이트웨이의 로그 파일에서도 찾아봤는데 나오지 않았다. 다만 LiteLLM 코드에는 서버 오류 메시지가 요청 내용을 되풀이할 수 있다고 적혀 있다. 오류가 나면 로그 파일에 일부가 섞일 수 있다는 뜻이다. 대화 자체는 웹 UI가 자기 데이터베이스에 저장한다.
  • (상태 확인)은 게이트웨이 자신이다. 노트북이 깨어 있는지 1분마다 한 토큰짜리 질문으로 확인한다. 아래에서 다룬다.

덜 바쁜 쪽으로 보내기

auto는 Mac mini와 노트북을 한 이름으로 묶은 것입니다. 받은 요청은 처리 중인 요청이 적은 쪽으로 보냅니다. 서로 다른 긴 질문 4개를 한꺼번에 보내 봤습니다.

보낸 곳 나뉜 결과 마지막 사람의 첫 글자 모두 끝남
Mac mini만 4개 74.1초 99.0초
노트북만 4개 30.1초 41.3초
auto (Mac mini를 먼저 적음) Mac mini 3개, 노트북 1개 60.5초 84.5초
auto (노트북을 먼저 적음) 2개씩 25.0초 48.5초

처음에는 4개 중 3개가 느린 Mac mini로 갔습니다. LiteLLM 코드를 보니 이유가 있었습니다. 처리 중인 요청 수가 같으면 목록의 첫 서버를 고릅니다. 그리고 요청 수는 고른 뒤 서버로 보내는 순간에야 늘어납니다. 그래서 한꺼번에 들어온 요청은 서로를 다 세지 못한 채 고르게 되고, 첫 서버 쪽으로 쏠립니다. 노트북을 먼저 적자 이번에는 2개씩 나뉘었고, 모두 끝나는 시간이 84.5초에서 48.5초로 줄었습니다. 그래도 노트북에 4개를 다 보낸 41.3초보다는 느립니다. 이 방식은 서버가 얼마나 빠른지는 보지 않습니다. 둘 다 한가하면 언제나 첫 서버, 이제는 노트북으로 갑니다.

노트북은 잠들거나 꺼질 수 있습니다. 그런데 LiteLLM은 연결이 안 되는 오류가 나도 그 서버를 쉬게 하지 않습니다. 그래서 세 가지를 더했습니다.

  • 노트북만 1분마다 확인한다. 답하지 않으면 그 서버로는 보내지 않는다. Mac mini는 긴 질문 뒤에서 확인이 늦어질 수 있어 확인하지 않는다.
  • 답하지 않는 모델은 목록에서 숨긴다. 웹 UI의 모델 목록에서 노트북 모델이 빠진다. 6단계에서 노트북이 잠들면 목록에서 빠지던 것과 같다.
  • auto가 실패하면 Mac mini가 대신 답한다.

잠든 노트북은 연결을 거절하는 서버로 흉내 냈습니다. 시험용 이름을 잠시 세 개 만들었습니다.

  • 그 서버 하나만 묶은 이름: 첫 확인 뒤 모델 목록에서 사라졌다.
  • 그 서버를 Mac mini 앞에 묶은 이름: 3번 물었는데 3번 모두 Mac mini가 답했다. 확인에서 떨어진 서버를 건너뛴 것이다.
  • 확인하지 않는 그 서버 하나에, 실패하면 Mac mini로 넘기게 한 이름: 연결이 거절되자 Mac mini가 0.9초 만에 대신 답했다.

시험을 마치고 이 이름들은 지웠습니다.

모델 서버 막기

마지막으로 MLX 서버가 받는 주소를 0.0.0.0(모든 네트워크)에서 127.0.0.1(Mac mini 안)로 바꿨습니다. 그 전에 쓰는 곳 둘을 게이트웨이로 옮겼습니다.

  • 웹 UI: 연결을 게이트웨이 하나로 바꿨다. 모델 이름이 게이트웨이 쪽 이름(qwen3.8-27b, gemma-4-26b)으로 바뀌어서, 이름과 설명, 시스템 프롬프트를 새 이름에 다시 붙였다. 다시 켜는 데 6초 걸렸다.
  • 커밋 도구: 주소를 게이트웨이로 바꾸고, API 키는 제 컴퓨터의 파일에서 읽게 했다. 모델은 --model로 고른다. 전에는 노트북 방화벽이 Mac mini에서 온 연결만 받아서 제 컴퓨터에서는 노트북 모델을 쓸 수 없었다. 이제 게이트웨이를 거치니 쓸 수 있다.

MLX 서버에 바로 물으면 연결 자체가 안 됩니다. 게이트웨이는 API 키 없이는 답하지 않습니다. 키를 가진 커밋 도구는 게이트웨이를 거쳐 노트북의 답을 받았습니다.

이제 이 연재에서 띄운 프로그램 가운데 네트워크로 열린 것은 둘입니다. 웹 UI(3000번)와 게이트웨이(4000번)입니다. MLX 서버, PostgreSQL, 검색 서버 SearXNG는 Mac mini 안에서만 받습니다.

다른 Claude의 검토

다 세운 뒤, 이 작업을 모르는 새 맥락의 Claude에게 설정과 스크립트를 검토하게 했습니다. 서버에는 들어가지 않고 파일과 LiteLLM 소스만 읽게 했습니다. 지적은 9개였고, 하나씩 코드와 시험으로 확인했습니다.

가장 컸던 것은 첫째입니다. 게이트웨이는 막는 일에서보다 넘겨주는 일에서 구멍이 났습니다. API 키를 받은 사람 누구나, 요청 한 번으로 Mac mini가 다른 모델을 더 불러오게 할 수 있었습니다. 큰 모델이면 24GB 메모리가 모자라 서버가 멈출 수 있고, 그러면 모두가 못 씁니다. 키를 확인하는 것만으로는 부족했습니다. 검토자가 짚은 LiteLLM 코드는 다시 열어 확인했고, 직접 시험할 수 있는 것은 시험했습니다.

원격 접속

0단계에서 「원격 접속 모두 허용은 9단계에서 다른 사람을 받을 때 좁힌다」고 미뤘습니다. 지금 확인해 보니 Mac mini의 원격 로그인은 관리자 계정만 받게 되어 있고, 관리자 계정은 제 계정 하나입니다. 다른 사람에게는 macOS 계정 대신 웹 UI 계정과 API 키를 주니, 이 범위는 그대로 둬도 됩니다.

남은 것은 암호 로그인입니다. 지금은 SSH 키가 없어도 암호로 들어갈 수 있습니다. SSH 키로만 들어오게 바꾸는 스크립트는 만들어 두었습니다. 설정이 잘못되면 스스로 되돌리게 했습니다. 다만 아직 이 네트워크에 들어올 다른 사람이 없어서, 지금은 실행하지 않기로 했습니다.

알게 된 것

  • 서로 다른 긴 질문은 묶이지 않는다. 4개를 한꺼번에 보내면 마지막 사람은 첫 글자를 Mac mini에서 74초, 노트북에서 30초 기다렸다.
  • 게이트웨이의 구멍은 넘겨주는 쪽에 있었다. 키를 확인해도, 모르는 필드를 그대로 넘기면 모델 서버를 흔들 수 있다.
  • 「덜 바쁜 쪽」은 빠르기를 모른다. 한꺼번에 온 요청은 목록의 첫 서버로 몰렸다. 빠른 서버를 먼저 적는 것만으로 84.5초가 48.5초가 됐다.
  • 키는 프로그램마다, 사람은 웹 UI가 알려 준다. 사람 칸은 웹 UI 키 아래에서만 믿는다.
  • 한도는 줄을 세우지 않고 거절한다. 429를 받은 쪽이 다시 보내야 한다.
  • 무겁고 공지가 잦다. 디스크 590MB, 메모리 0.6GB에 PostgreSQL이 따로 필요하다. 버전을 고정하고 보안 공지를 챙겨야 한다.

다음 단계로

이제 여러 사람이 같은 서버를 써도, API 키가 있는 사람만 쓰고 쓴 만큼 남습니다. 연재는 마지막 10단계에서 이 서버로 실제 일을 해 봅니다. 문서를 찾아 읽고 답하게 하거나, 모델을 조금 더 가르쳐 봅니다. 그 밖에 남은 일은 셋입니다.

  • 늘 켜 두기: 게이트웨이와 PostgreSQL, 웹 UI, SearXNG는 지금 손으로 띄워 둔 상태입니다. 관리자 암호로 설치 스크립트를 실행해야 Mac mini가 다시 켜질 때 저절로 뜹니다. 그 전에 Mac mini가 다시 켜지면 웹 UI가 돌아오지 않습니다.
  • SSH 키로만 로그인: 스크립트는 준비해 두었고, 다른 사람이 이 네트워크에 들어오기 전에는 실행하지 않습니다.
  • HTTPS: 웹 UI와 게이트웨이는 평문 HTTP입니다. API 키도 같은 네트워크 안에서는 그대로 지나갑니다.
